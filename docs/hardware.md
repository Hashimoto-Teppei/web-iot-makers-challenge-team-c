### 表示 — LCD1602A（I2C 変換基板つき）

16文字×2行のキャラクタ LCD。表示できるのは**英数字と半角カタカナだけ**で、**漢字は出せない**
（`notifications/arbitration.md`「画面の割り付け（16×2）」）。**上下段に何を出すかもそこで決まっている。**

**半角カタカナは使う**（警告の記号が `ｾｯｷﾝ` / `ﾌﾞﾚｰｷ` など）。**そのために2つ効いてくる。**

- **内蔵フォントの ROM が A00 であることが前提**になる。`config.py` の値ではなく
  `hw/lcd.py` が `charmap="A00"` を渡している（**RPLCD の既定は `A02`** で、カナが無い方）。
  **実物が A00 であることは 2026-09-20 に実機で確かめた**（`!!! ﾌﾞﾚｰｷ` と `ｱｲｳｴｵ` を
  そのまま読めた）。**買い替えたときは A02 が来うる**ので、そのときは `config.py` の
  `symbols` を英字に戻すだけで戻せる（コードは変わらない）。
  **下段のラベルと生存のコマは ASCII で書いてあるので、A02 でもそのまま出る。**
- **濁点と半濁点はそれぞれ1マスを食う。** `ﾌﾞﾚｰｷ` は5マス、`ﾀｲｺｳｼｬ` は6マスである。

**配線は SDA / SCL / VCC / GND の4本だけ**（変換基板がはんだ付け済みの製品を使う）。

**5V（物理ピン 2）で駆動する。** **3.3V では読めない**——2026-09-19 に実機で確かめた。
HD44780 の濃さは `VDD − V0` だけで決まり、**3.3V では上限が足りない**（コントラストの
半固定を端まで回しても、うっすらとしか出ない）。**これは部品の個体差ではなく、この方式の帰結**
なので、同型を買い直しても変わらない。

**ただし 5V にすると、SDA / SCL にも 5V 側の電圧が乗る**——変換基板のプルアップ（4.7kΩ ×2）が
VCC につながっているため（`adr/0003`）。**そのままでは GPIO の定格を超える。**

**対処は、SDA / SCL から GND へ 10kΩ を1本ずつ足すこと**（下の結線表）。
レベル変換モジュールは要らない。**3つの抵抗の分圧で決まる**ためで、実測ではなく計算だが
**動作そのものが裏取りになっている**（下記）。

| SDA / SCL の電圧 | 条件 |
| --- | --- |
| 約 3.77V | 抵抗を足さないとき。**定格 3.8V の直前で、余裕が無い** |
| **約 3.34V** | **10kΩ を足したとき（採用）** |
| 約 2.28V | 2kΩ を足したとき。**PCF8574 が「高」と認めず、`i2cdetect` に出ない** |

**2kΩ で出なかったこと自体が、プルアップが 4.7kΩ である証拠**である。仮に 1kΩ なら
2kΩ でも 3.32V になって通っていた。**テスターを使わずに前提を1つ潰せている。**

**I2C アドレスは `0x27` で確定**（2026-09-19）。変換基板のチップの刻印が `PCF8574T`
——`PCF8574AT` なら `0x3F` だった。`config.py` の `LCD_I2C_ADDRESS` もこの値。

**5V へ移したら、コントラストの半固定は回し直す。** 3.3V 用に端まで回してあると、5V では
効きすぎて**全32マスが白く光り、文字が埋もれる**。逆向きに戻して、背景が濃い青に沈み、
文字だけが白く残るところで止める。**判断は必ず正面から**——このパネルは上下の視野角が狭く、
斜めから見ると淡く見える。

### 後方物体検知 — AE-NJR4265 J1

24GHz 帯のマイクロ波ドップラーセンサー。**接近と離反を区別して、それぞれデジタル出力に出す**
（データシート Rev.05j「6.1. 接続端子」）。**日本向けの J1 タイプは工事設計認証済み**（ARIB STD-T73）。

**UART を持っているが、使わない。** このモジュールは UART（9600bps）でも検知結果を通知でき、
キットには USB 変換も載っているが、**接近の検知出力を GPIO 1本で読めば足りる。**
UART を使えば **Bluetooth と取り合いになる**（下の「UART を使う部品を載せるとき」）ため、
**GPIO14/15 にはつながない。** ここを間違えると、BLE ——警告と心拍の唯一の経路—— が詰まる。

**離反の出力（CN2 3番）も使わない。** 遠ざかる物体は危険ではない。
**GPIO 1本で済ませ、必要になったら1本足す。**

**端子番号が2系統ある。** データシートが言う端子5（APPROACH）/ 端子6（AWAY）は**モジュール本体の番号**で、
**配線するのは基板の外部拡張端子 CN2 の 4番（接近）/ 3番（離反）**である
（キット取扱説明書「外部拡張端子と USB コネクタ」）。**下の結線表は CN2 の番号で書いている。**

**基板の micro USB には何も挿さない。** 説明書は**バスパワーとの共存はできない**としている
（CN2 の VDD は、USB 給電時は 5V の「出力」端子になる）。**ラズパイから 3.3V を入れている間に USB を挿すと、
3.3V と 5V がぶつかる。** USB は動作確認のときだけ、ラズパイから外した状態で使う。

**CN2（1×8 細ピンヘッダ）は自分ではんだ付けする。** キットは未実装で届く。ここを付けないと線が出せない。
**ラズパイとは USB ではなくこの CN2 でつなぐ**——CN2 もラズパイの GPIO ヘッダもオスなので、
**メス-メスのジャンパ線3本**（VDD / GND / 接近検知）で足りる。

**VDD は 3.3V にする。** キットの外部電源入力は 3.3〜5V を受ける。
**5V で駆動すると検知出力にも 5V 近くが乗って GPIO が壊れる**
（説明書「近接 / 離反外部出力について」の出力電圧レベル図は、5V 駆動で H が 3.0V 以上。
`unverified.md` 28。**配線する前にテスターで測る**）。

**検知出力は GPIO に直結してよい。** 説明書は**負荷抵抗 10kΩ〜100kΩ**を求めており
（LED やリレーの直接駆動は不可）、**マイコンのハイインピーダンス入力への直結は可**と明記している。
ラズパイの内部プルダウン（約 50kΩ。`hw/rear_sensor.py` で有効にしている）はこの範囲の中に入る。

**検知距離は基板の半固定抵抗 VR1 で決める**（`検知距離 = VTH / VDD × 10m`、約 0.7〜10m）。
**この値はコードの設定に出せない。**`config.py` にあるのは GPIO 番号だけで、
**距離はツマミの位置が正本**である。デモの距離に合わせたら、その値をここに書く（未調整）。

| 項目 | 値 | 出典 |
| --- | --- | --- |
| 検知可能速度範囲 | **0.25 〜 1.0 m/s** | データシート「4. 検知性能」 |
| 検知可能角度 | ±35°（アンテナ半値幅は H 面 70° / V 面 54°） | 同上 |
| 最大検知距離 | 10m（VR1 で調整） | 同上 |
| 消費電流 | 60mA（移動体検知モード） | データシート「2. 電気特性」 |

**速度範囲が自転車に合っていない。** 0.25〜1.0 m/s は時速 0.9〜3.6km で、**歩く速度向けの人感センサー**である。
**後方から来る自動車（約 11 m/s）も自転車（約 4 m/s）も範囲の外**にある。
**デモの条件（止まった自転車の後ろから人が歩いて近づく）はちょうど範囲の中**なので、
**この部品で進める**が、実走行では出ない可能性がある（`unverified.md` 92）。

### 光 — LED 2個

`notifications/arbitration.md` の `warn_light` と `link_light`。**走行中に情報が届く唯一の経路**
である（**走行中に LCD を読むのは注視**——`notifications.md`）。

| LED | チャンネル | 出すもの | GPIO |
| --- | --- | --- | --- |
| 警告 | `warn_light` | `lv` に応じて点滅・点灯（0.5Hz / 2Hz / 点灯） | GPIO22（物理 15） |
| `link` | `link_light` | `up` は点灯、`nofix` は 0.5Hz、`down` は 2Hz | GPIO17（物理 11） |

**2つは色を分ける。** 同じ色だと、**走行中の周辺視ではどちらが光ったのか分からない。**
色の組み合わせは決めていない（手に入ったもので割り当ててよい）が、**割り当てたらここに書く。**

**`link` の LED は正常時も点灯したままである。** 消灯を正常にすると、
**LED が切れていることに誰も気づけない**（`notifications/arbitration.md`「通信断の見せ方」）。

**電流制限抵抗は 150Ω。** GPIO が出すのは 3.3V なので、流れるのは
`(3.3 − 順電圧) ÷ 150` ——赤で約 9mA、黄で約 8mA、**2個で合計 17mA**。
**LED は抵抗を経由して GPIO に直結してよい**（`adr/0003`）。**2個に増えても直結のまま。**
`adr/0003` の上限は **1本あたり 16mA / 全体で 50mA** で、どちらにも当たらない。
**これを超える数を足すときはトランジスタか FET を挟む**
（同 ADR。ウインカー #24 とブレーキランプ #25 がそれに当たる）。

**青と白の LED は選べない。** 順電圧が 3.0〜3.4V あり、**電源の 3.3V とほとんど差が無い**ため、
抵抗を変えても明るくならない。**赤・黄・黄緑から2色を選ぶ。**

### 載せない・外すの切り替え

`config.py` の4つの値で、**部品が載っていない状態をそのまま表せる**ようにしてある。

```python
LCD_I2C_ADDRESS: int | None = 0x27   # None で表示しない
WARN_LIGHT_GPIO: int | None = 22     # None で警告を光らせない
LINK_LIGHT_GPIO: int | None = 17     # None で link を光らせない
REAR_SENSOR_GPIO: int | None = 27    # None で後方検知を止める
```

**`enabled` のフラグを別に持たない。** 1つの値で切れる方が、読む場所が増えない。
**実機を持たない開発者が動かすときも同じ経路**で、4つとも `None` にすれば
ハードウェアに触らずに起動できる（`adr/0002-development-lifecycle.md`）。

## ピン割り当て

**新しい部品をつなぐ前に、必ずこの表で空きを確認する。** 2人が別々に配線すると同じピンを取り合う。
使うことにしたら、実際に配線する前にこの表を埋めて PR を出す（早い者勝ちの予約として機能させる）。

**ピンを予約するのは接続方式が決まってから。** 決まる前に取ると、使わないピンが空かないまま残る。

**奇数ピンは内側の列**（基板の縁に近い外側が偶数）で、**ピン1だけランドが四角い**
——シルクに `1 / 2 / 39 / 40` が印刷してある（公式の機械図面 RP-008358-DS）。
**1列取り違えるとピン1とピン2、つまり 3.3V と 5V が入れ替わる。**

### I2C アドレス

I2C は1本の線に複数の部品をぶら下げられるが、**アドレスが重なると両方動かなくなる**。
部品を選ぶ前にここを見て、重複しないことを確認する。

| アドレス | モジュール | 状態 |
| --- | --- | --- |
| `0x27` | LCD1602A の I2C 変換基板 | **確定**（2026-09-19。チップの刻印が `PCF8574T`。`PCF8574AT` なら `0x3F` だった） |

同じアドレスの部品を2つ使いたい場合は、変更ピンで別アドレスにするか I2C マルチプレクサが要る（未検討）。

### UART を使う部品を載せるとき

**GPIO14/15 は空いているが、ただの空きピンではない。** 既定で Bluetooth が
性能の良い方の UART（PL011）を使っており、GPIO に出ているのは簡易版（ミニ UART）である。
ここに連続してデータが流れる部品（GPS・レーダー・シリアルのセンサー）を載せると、
**Bluetooth と取り合いになる。**

**BLE はいま警告の唯一の出口**（`interfaces/v2v.md`）なので、以前より痛い。
判断はスマホで行われるため、**BLE が詰まるとデバイスは警告を出せず、心拍も途切れる**
（`adr/0006-decision-layer-on-mobile.md`）。位置が通らなくなった代わりに、**止まったときの見え方が悪くなった。**
UART の部品を候補に挙げた時点で `adr/0003` の「UART を使う部品は Bluetooth と競合する」を読み、
**3つの選択肢のどれを採るかを先に決めてからピンを予約すること。**

**いま載っている部品に UART を使うものは無い。** ただし **AE-NJR4265 は UART も持っている**ので、
**「シリアルの口があるから挿す」をしないこと。**この部品は検知出力を GPIO で読む（上）。

## 測位はスマホが行う

デバイスに GPS モジュールを載せない（`adr/0004-v2v-transport.md`）。
**位置はデバイスに届きもしない。** 判断がスマホへ移ったため、位置を使うのはスマホの中だけである
（`adr/0006-decision-layer-on-mobile.md`）。

**それでもここに書くのは、測位性能が検知の前提そのものだから**であり、
デバイス担当が部品を選ぶときに知っておく必要があるためではない。**これは端末と置き場所で変わる。**

| 項目 | 見込み | 効いてくるところ |
| --- | --- | --- |
| 更新頻度 | **1Hz**（`FusedLocationProvider` に 1000ms を要求） | 時速 20km で**1秒あたり約 5.5m 進む**。急接近の検知には粗い |
| 水平位置精度 | **端末が `Location.getAccuracy()` でメートルで返す。値をそのまま使う** | 換算も係数も要らない。1通ごとに `hacc` として運ぶ（`interfaces/v2v.md`） |
| 置き場所の影響 | **ポケットや鞄の中では大きく劣化する** | **ハンドルにマウントし、画面は消す**運用を前提にする（`unverified.md`） |
| 起動から測位まで | A-GPS があるので通常は数秒 | 電源を入れ直しても待たされない |

**「スマホだから高精度」とは限らない。** 多衛星系（QZSS を含む）と A-GPS で有利な一方、
アンテナは金属筐体の中の小さなもので、外付けパッチアンテナを空に向けた専用受信機より不利になりうる。
**置き場所が精度を左右する**ため、運用の前提として決めておく必要がある。

## 電源

**手持ちのモバイルバッテリーから、micro USB でラズパイの PWR IN へ給電する。**
部品はすべてラズパイのピンから取るので、**電源の系統は1つだけ**である。

**容量よりオートオフの方が問題になる。** 消費が小さいと「充電が終わった」と判断して
給電を止めるバッテリーがある。**止まると走行中に丸ごと落ちる**ため、デモに使う個体で1回確かめる（`unverified.md` 7）。
**下の見積もりは 357mA** なので、止まる側の心配は小さい。

**5000mAh なら実効で 8 時間前後。** モバイルバッテリーの容量表示は**セルの 3.7V 基準**なので、
5V に換算すると 3,700mAh 相当まで落ちる（5000 × 3.7 ÷ 5）。357mA で割って理論 **約10時間**、
昇圧の損失を見て**その 8 割程度**が実際に使える時間である。
**2026-09-19 に 10〜11 時間から直した**——合計の 260mA が誤りだったため。
**デモには十分なので、容量の検討はしない。**

### 消費電流の見積もり

**部品を足すたびにここへ1行足す。** 稼働時間はバッテリー容量 ÷ 合計消費電流で概算できる。
デモの途中で電池が切れるのが一番まずいので、**実測値が取れたら見積もりを実測に置き換える**。

| 部品 | 見積もり | 実測 | 備考 |
| --- | --- | --- | --- |
| Raspberry Pi Zero 2 W（BLE 常時接続） | **250mA** | — | **BLE は走行中ずっとつながっている。**アイドル時の値で見積もらない。**Zero W より食う**（4コア。当初は Zero W の 150mA で見積もっていた。`unverified.md` 105） |
| LCD1602A + I2C 変換基板 | 30mA | — | ほぼバックライトのぶん。**5V レールから取る** |
| AE-NJR4265 J1 | 60mA | — | データシート「2. 電気特性」の移動体検知モード |
| LED ×2 | 17mA | — | 150Ω で決まる（赤 9mA + 黄 8mA）。点滅する間は平均がこれより小さい |
| **合計** | **357mA** | — | 5V 換算。**すべてデータシートと公表値で、実測は1つも無い**。**2026-09-19 に 260mA から直した**——ラズパイの見込みを 150mA から 250mA へ上げたとき、合計を直し忘れていた |

**実測はここでやらない。** 電流計を当てるのは実機を出す回に他の確認とまとめる
（#139「実機2台で1回走り、しきい値と連続稼働をまとめて測る」）。
**実機を出す機会は多くないので、1回にまとめる。**

## 結線表

**部品が2〜3個を超えたら、実物のどの線がどこに刺さっているかを追える形をここに置く。**
上の割り当て表は「そのピンを誰が取ったか」を答えるが、**「この部品から何本出て、どこへ行くか」には答えない。**

**4個になったので置いた。** ただし**写真や手描きの図ではなく、この表**にしている ——
絵は**実物と食い違ったときに更新されずに残る**ため。**実際に配線したら、この表の「状態」を更新する。**

**ブレッドボードを間に挟む。** 直結では足りないものが3つあるため ——
**線を3つに枝分かれさせる場所**（SDA にはラズパイ・LCD・引き下げ抵抗の3つがつながる）、
**LED の電流制限抵抗を直列に挟む場所**、**GND を1点にまとめる場所**。

| 部品 | 部品側 | ブレッドボード | ラズパイ側（物理ピン） |
| --- | --- | --- | --- |
| LCD1602A（I2C 変換基板） | VCC | 中継の列 | **2**（5V） |
| | GND | **&minus; レール** | 9 ※1 |
| | SDA | 列（**10kΩ で &minus; レールへ** ※2） | 3（GPIO2） |
| | SCL | 列（**10kΩ で &minus; レールへ** ※2） | 5（GPIO3） |
| 警告の LED | アノード（長い脚） | **150Ω を直列** | 15（GPIO22） |
| | カソード（短い脚） | **&minus; レール** | — ※1 |
| `link` の LED | アノード（長い脚） | **150Ω を直列** | 11（GPIO17） |
| | カソード（短い脚） | **&minus; レール** | — ※1 |
| AE-NJR4265 J1（CN2） | 2番 VDD | 中継の列 | **1**（3.3V） |
| | 1番 GND | **&minus; レール** | — ※1 |
| | 4番 接近検知 | 中継の列 | 13（GPIO27） |
| | 3番 離反検知 | — | **つながない** |

※1 **GND はラズパイのピン9 の1本だけ。** &minus; レールが残りをまとめるので、
以前使っていたピン 6 / 20 / 25 は空きに戻る。**ラズパイの GND ピンはどれも同じ線**なので、
まとめても分けても電気的には同じで、**ジャンパ線が3本減り、挿し間違いも減る**。

※2 **抵抗は SDA / SCL を GND へ引き下げるもの**で、線の途中に直列に入れるのではない。
**直列に入れると I2C は動かない**——`L` の電圧が持ち上がってしまうため。
**同じ列**に「ラズパイからの線」「LCD への線」「抵抗の片足」の3つを挿し、
抵抗のもう片足を &minus; レールへ落とす。理由と電圧は「表示」の項。

**どの列を使うかはここでは決めない。** 空いていればどこでもよく、
**決めるのは「同じ列に入るものの組み合わせ」だけ**である。実際の列番号を決めた作業用の図は別にある。

**電源はレールに載せない。** 5V（LCD）と 3.3V（センサー）の2種類があるため、
**「+」と書かれた1本のレールに載せると必ず混ざる。** 電源は列を1つずつ使って中継し、
**レールは GND 専用**にする。

**配線する前に `unverified.md` 28 のとおりテスターで測る。**
残っているのは **AE-NJR4265 の 4番**（3.3V 駆動になっているか）。
**LCD の SDA / SCL は片付いた**——5V 駆動にしたうえで 10kΩ で 3.34V に収めてある。
