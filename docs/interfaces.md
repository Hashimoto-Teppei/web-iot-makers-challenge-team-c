変更したら影響を受ける担当に伝わる形（PR の説明）で行うこと。

## デバイス ⇄ モバイル（BLE GATT）

デバイスがペリフェラル、モバイルアプリがセントラル。デバイスに蓄積された検知ログ・走行ログを吸い上げる。

**この節が唯一の正本。** Python 側は TypeScript の Zod スキーマを参照できないため、
デバイス担当とモバイル担当はここだけを見て実装する。スキーマを変えたら両実装を更新すること。

- [ ] Service UUID / Characteristic UUID
- [ ] Characteristic ごとの役割（走行ログ読み出し、検知ログ読み出し、時刻同期、設定書き込み など）
- [ ] ペイロードのエンコーディング（JSON / MessagePack / 独自バイナリ）
      — MTU が小さいため、レコード数が増えるものは分割転送の設計が要る
- [ ] 転送済みログの扱い（デバイス側で削除するか、既読位置を持つか）
- [ ] ペアリング・認証の要否

## デバイス ⇄ デバイス（メッシュ）

自転車に搭載した Raspberry Pi Zero W 同士が Wi-Fi でメッシュを構成し、位置情報を交換する。

- [ ] メッシュの構成方式（802.11s / adhoc / batman-adv など）
- [ ] ペイロード（緯度経度・速度・進行方角・タイムスタンプ・端末ID）
- [ ] 送信間隔 — 検知の即応性と Zero W の負荷・電力のトレードオフ
- [ ] シリアライズ形式 — 帯域と CPU 負荷を考えるとテキストより固定長バイナリが有利か
- [ ] 時刻同期の方法 — 相対速度の算出に必要。GPS の時刻が使えるか
- [ ] 端末IDの割り当てとプライバシーの扱い

## モバイル ⇄ API

**エンドポイントの型はコードが正本。** `apps/web/src/worker/` のルート定義から Hono RPC で型が伝播するため、
ここにリクエスト/レスポンスの構造を書き写さない（必ず実装とずれる）。
この節には型から読み取れないことだけを書く。

Web の画面は API と同じ Worker 内にあるため単一オリジンで、CORS の考慮は不要。
モバイルアプリはネイティブなので CORS の対象外。

- [ ] 認証・端末の識別方法
- [ ] D1 のテーブル設計（走行ログ、検知ログ、端末）
- [ ] ログ同期の設計 — 冪等性、重複送信の扱い
- [ ] Web アプリの「データを活かした見せ方」に必要な集計エンドポイント

## 危険検知アルゴリズム

3つの検知を**別々の担当が並行実装する**ため、これも境界として先に決める。
検知は1つ1ファイルに分け、下記のインターフェースに揃える。4つ目が増えたときの受け口も兼ねる。

| 検知 | 担当 | 状態 |
| --- | --- | --- |
| 急接近 | TODO | 未着手 |
| 前方急ブレーキ | TODO | 未着手 |
| 見えない曲がり角の対向車 | TODO | 未着手 |

- [ ] 入力の型 — 自車の状態（位置・速度・進行方角・時刻）と、メッシュで受信した周辺車両の状態のリスト
- [ ] 出力の型 — 警告の有無、種別、深刻度、通知に使う情報（方向など）
- [ ] 状態の持ち方 — 減速度の算出には過去の値が要る。各検知が履歴を自前で持つか、呼び出し側が渡すか
- [ ] しきい値の受け渡し方 — コードに直書きせず設定から注入する
- [ ] 複数の検知が同時に発火した場合の優先順位（表示は1つしかない）

**ハードウェアに触れないこと。** GPS の読み取りや LED の点灯を検知の中に書くと、開発機（Windows / macOS）で
テストできなくなる。入力を受けて結果を返す純粋な関数として書き、モックデータで pytest を回せる状態を保つ。
