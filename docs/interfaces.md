## デバイス ⇄ モバイル（BLE GATT）

デバイスがペリフェラル、モバイルアプリがセントラル。**この1本の接続が2つの役目を持つ。**

| | 向き | 目的 | いつ流れるか |
| --- | --- | --- | --- |
| **走行ログの吸い上げ** | デバイス → モバイル | 蓄積された検知ログ・走行ログを回収する | 走行後 |
| **測位の供給**（`uplink`） | モバイル → デバイス | **自車と周辺車両の位置**を渡す（下の「[車車間の位置共有](#車車間の位置共有)」） | **走行中ずっと** |

**設定の書き込みはまだできない**（`config` は UUID を予約しただけ。中身は #33）。
**書き込みの経路を実装しにいかないこと。**
サーバーは BLE を話さない。デバイスと直接やりとりするのはモバイルアプリだけで、
サーバーへはモバイルアプリが中継する。

**この節が唯一の正本。** Python 側は TypeScript の Zod スキーマを参照できないため、
デバイス担当とモバイル担当はここだけを見て実装する。スキーマを変えたら両実装を更新すること。

プロトコルバージョンは **1**。**この境界のバージョンはこれ1つ**で、`uplink` に別の番号を持たせない
（1つの境界に2つあると、どちらを上げるかで必ず迷う）。

**上げるのは互換性を壊す変更のときだけ。項目を足すだけなら上げない。**
足しただけで上げると、更新した側と古い側が互いに何もできなくなる。
項目の追加は「知らないキーは無視する」で吸収する。

**モバイルは `proto` が自分の想定と違えば、転送も `uplink` も行わない。** 画面に更新を促すだけにする。
デバイスだけ更新して古い APK が残る組み合わせは起こりうるので、
非互換のレコードをパースして壊れたログを Worker まで運ぶより、止まる方がよい。
**`uplink` を止めると位置が届かず検知が止まる**ので、**画面には「更新するまで検知が動かない」と出すこと。**

### 前提

- **接続できるセントラルは同時に1台**。つながるのは持ち主のスマホ1台だけなので、複数台を扱わない。
  **アドバタイズを止めても2台目は防げない**（アドレスを知っていれば接続できる）。
  防ぐ仕組みは持たないので、**セントラルは自分が `read` を書いたときだけ EOT を信じる。**
  書いていないのに EOT が来たら、それは他人の転送。既読位置を進めない。
- **デバイスは常時アドバタイズする**（**接続中を除く**。BlueZ は接続している間アドバタイズを止める）。
  ボタンで切り替える案もあるが、入力部品が未確定（#13）のため今は持たない。
  **スキャンで見つからない＝故障、とは限らない。** 他人がつなぎっぱなしにしている場合も同じに見える
  （下の「運用で気をつけること」）。
- **接続は走行中ずっと維持する。** `uplink` が測位の唯一の供給元なので、
  切れている間は**検知が動かない**。走行ログの回収だけを担っていた頃と違い、
  **この経路が遅れることは危険検知が遅れることを意味する。**
  Android では `connectedDevice` 型のフォアグラウンドサービスで保つ（`unverified.md`）。
- **切れたことをデバイスが自分で気づく必要がある。** 下の「[通信断を必ず見せる](#通信断を必ず見せる)」。
- **走行ログの転送（`log`）と `uplink` は同じ接続の上で同時に流れうる。** 転送は走行後が主なので
  重なるのは稀だが、**重なっても `uplink` を止めない**（止めると検知が止まる）。

### UUID

`0x1800` 台のような 16bit UUID は SIG が割り当てた仕様専用のため、独自のサービスには使えない。
128bit のランダム UUID を1つ作り、先頭 4 バイト目だけを変えて枝番にする。

| 役割 | UUID | プロパティ |
| --- | --- | --- |
| Service | `68666e00-58cc-4540-90ad-18bfae31615f` | — |
| `device-info` | `68666e01-58cc-4540-90ad-18bfae31615f` | Read |
| `control` | `68666e02-58cc-4540-90ad-18bfae31615f` | Write（応答あり / Write Request） |
| `log` | `68666e03-58cc-4540-90ad-18bfae31615f` | Notify |
| `status` | `68666e04-58cc-4540-90ad-18bfae31615f` | Read / Notify |
| `uplink` | `68666e06-58cc-4540-90ad-18bfae31615f` | Write（応答あり / Write Request） |
| （予約）`config` | `68666e05-58cc-4540-90ad-18bfae31615f` | — |

`config`（設定の書き込み）は **UUID だけ予約して実体はまだ作らない**。何を書き込むかが未確定（#33）のため。
決まるまで、設定はデバイス側の設定ファイルで変更する。

アドバタイズには 128bit の Service UUID と、**Local Name `bg-<device_id 下4桁>`**（`device_id` が `c3f1a20b` なら `bg-a20b`、7文字）を載せる。

**名前を7文字に縮めるのは、31 バイトに収めるため。**
Flags(3) + 128bit UUID(2+16) + 名前(2+7) = 30 バイトで、ぎりぎり収まる。
`bikeguard-a20b`（14文字）だと 37 バイトになって入らず、BlueZ の `LocalName` は
**入りきらないぶんを黙って切り詰める**ので、名前が中途半端に欠けたまま気づけない。

**`Includes`（`tx-power` など）・`Appearance`・`ServiceData` を設定しない。**
余白は1バイトしかなく、どれか1つ足すだけで溢れて名前が切り詰められる。しかも**エラーは出ない。**

**Scan Response に逃がす案は採らない。** BlueZ の `LEAdvertisement1` で scan response を指定する
プロパティ（`ScanResponseData` など）は experimental で、`bluetoothd --experimental` が要る。
デモ環境の前提を増やしたくない。Zero W の Bluetooth は 4.1 で Extended Advertising も使えない。

モバイルアプリは Service UUID でスキャンし、名前は人が見分けるためだけに使う。

### 接続してから転送するまで

**順番を守る。** 逆にすると原因の分かりにくい失敗になる。

1. Service UUID でスキャンして接続し、**MTU 247 を要求 → サービス探索**の順に行う。
   **重ねて実行しない。** GATT の操作は一度に1つしか出せず、`requestMtu` と `discoverServices` を
   同時に走らせると片方が黙って落ちる。**それぞれ完了のコールバックを待ってから次へ進む。**
   サービス探索が終わるまで Read も購読もできない。
   **ネゴシエートされた MTU が 163 未満ならここで止める**（下の「転送の約束」の 7）。
2. `device-info` を読んでデバイスを識別する。
3. **`log` と `status` の両方の Notify を購読する。**
4. **`uplink` を書き始める。** 測位が得られ次第、走行中はずっと書き続ける。
   **走行ログを回収しないときも、ここまでは必ず行う。**
5. 走行ログを回収するなら、**受信バッファを空にしてから** `control` に `read` を書く。

**3 と 5 も1つずつ順に行う。** 購読は CCCD への Write であり、`read` の Write と合わせて
3回の GATT 操作になる。まとめて発行すると**購読が黙って成立せず、0件で転送が終わる。**
`onDescriptorWrite` を待ってから次へ進むこと。

**購読より先に `read` を書かない。** デバイスはすぐ流し始めるが、購読していない Characteristic の
Notify は Android 側で捨てられ、**1件も届かないまま転送が終わる**。

**受信バッファを捨てるのは、接続直後だけでなく `read` を書くたび。** 前の転送が途中で切れていると
`\n` で終わっていない断片が残り、**そのままだと先頭の1レコードが壊れた JSON になる。**
`stop` のあとも、下の規則5で取り直すときも同じ。

**ペアリングは要らない**（下の「ペアリング・認証」）。接続したらそのまま読み書きできる。

### Characteristic の役割

#### `device-info`（Read）

接続直後に1回読む。JSON オブジェクト1つ。

```json
{ "proto": 1, "device_id": "c3f1a20b", "log_id": "9a1c...", "oldest_seq": 941, "latest_seq": 1284 }
```

- `device_id` — デバイスごとに固定。初回起動時に生成してファイルに保存する。
  **16進の小文字8文字**（`uuid4().hex[:8]` など）。`log_id` も同じ形。
  ハイフン付きの UUID を入れると、アドバタイズの名前もキーの長さも変わる。
  **ログとは別のファイルに置く。** ログと一緒に消えると `device_id` が変わり、
  取り込みの一意キー `(device_id, log_id, seq)` が総入れ替えになって、**履歴がまるごと重複する。**
- `log_id` — **ログの世代**。ログを消した・失った・`seq` を振り直したときだけ変わる。
  **これが前回と違えば、保存してある既読位置は無効**（下の「転送済みログの扱い」）。
- `oldest_seq` / `latest_seq` — デバイスが**今も持っている**レコード番号の範囲。
  あと何件あるかの目安。**1件も持っていないときは両方 `0`**（`seq` は 1 から始まる）。

#### `control`（Write）

モバイルからデバイスへのコマンド。1回の Write に JSON オブジェクト1つ。

**必ず Write Request（応答あり）で書く。** Write Without Response だと `stop` が届いたかを
セントラルが知れず、`stop` が落ちればデバイスは送り続ける。

| コマンド | 形 | 内容 |
| --- | --- | --- |
| 転送開始 | `{"cmd":"read","since":1200}` | `seq > since` のレコードを `log` に流し始める。`since` 省略で全件 |
| 中断 | `{"cmd":"stop"}` | 転送を止める。**EOT は送らない**（EOT の有無が「送り切った」と「途中でやめた」の区別になる） |

**知らないコマンドは無視する。** 断った理由は `status` の `last_error` に載せる。

**`state` が `sending` の間に来た `read` は断る**（`last_error` に載せる）。
受け付けて2つ目の転送を始めると、**同じ `log` の上で新旧のストリームが混ざる。**
ストリームを見分ける印がないためセントラルは区別できず、`seq` が逆行し、
**古い方の EOT で新しい転送が完了したことになる。**
やり直したいセントラルは、**先に `stop` を書き、`state` が `idle` に戻ってから `read` を書く。**

**切断されたらデバイスは転送を中止し、`state` を `idle` に戻す。**
戻さないと、アプリが同期中に落ちた端末は**つなぎ直しても以後ずっと `read` を断られる。**

#### `log`（Notify）

レコードを **JSON Lines**（1レコード = 1行の JSON + `\n`）のバイトストリームとして流す。
**Notify 1パケットとレコードの境界は一致しない。** セントラルは受信したバイトをバッファに連結し、
`\n` で区切って初めて1レコードとして扱うこと。1レコードが数パケットに分かれるのは正常。

区切りに使うため、**レコード内の JSON に生の改行を含めない**（`json.dumps` の既定どおり `\n` は `\\n` に
エスケープされる）。

転送の終わりは **`0x04`（EOT）1バイト**。**最後のレコードの `\n` の直後に、同じストリームの続きとして送る。**
単独のパケットで届く保証はないので、**パケットの区切りで判断しない**
（最後のレコードと同じ Notify に相乗りして届くことがある）。
セントラルは「`\n` で切り出したあとにバッファへ残った `0x04`」を見て完了と判断する。

**エラーを `log` に混ぜない**。ログの本文とエラーが同じ経路に来るとパースが壊れる。

#### `status`（Read / Notify）

**転送の進み具合を人に見せるためのもの。** JSON オブジェクト1つ。

```json
{ "state": "sending", "sent": 32, "remaining": 52, "last_error": null, "link": "up", "peers": 3, "dropped": 0 }
```

| 項目 | 内容 |
| --- | --- |
| `state` | `idle`（流していない） / `sending`（流している） |
| `sent` | 今回の `read` で送ったレコード数 |
| `remaining` | まだ送っていない残り |
| `last_error` | 直近で断った**コマンド**（`control`）の理由（例 `"unknown cmd"`）。なければ `null` |
| `link` | `up` / `nofix` / `down`（下の「[通信断を必ず見せる](#通信断を必ず見せる)」） |
| `peers` | いま近傍として持っている自転車の台数 |
| `dropped` | 起動してから **`uplink` で「壊れている」として捨てた数**（累計）。下を見ること |

**`dropped` に数えるのは、壊れているものだけ**（壊れた JSON・知らない `k`・必須の項目が欠けている・
値の範囲外）。**正常に起きる破棄を混ぜない** — 自分の `id`・古い `t`・`link` が `up` でない間の `peer` は、
何も壊れていなくても毎秒出る。**混ぜると異常に気づくための数として使えなくなる。**
どれをどちらに数えるかの線引きは実装時に決める。

**`uplink` のエラーを `last_error` に入れない。** `uplink` は毎秒何通も流れるので、
`hacc` が1つおかしいだけで**`read` を断った理由が毎秒上書きされ、転送の診断に使えなくなる。**
逆に `read` を受けると `last_error` は `null` に戻るので、**続いている `uplink` の異常が消える。**
向きも寿命も違うものなので、**`uplink` 側は `dropped` の数だけを出す**（理由は分けない）。

**`link` と `peers` は、モバイル側が「デバイスに届いているか」を確かめるためのもの。**
アプリが送ったつもりでもデバイスが受け取れていない、という状態を人が見つけられるようにする。

**`last_error` は `read` を受け付けた時点で `null` に戻す。** 残したままにすると、
前回断ったコマンドの理由が健全な転送中も表示され続け、**成功した同期が失敗に見える。**

**`sent` と `remaining` は目安であって、正確な数を約束しない。**
**転送が終わったかどうかを `status` で判定しない。完了の印は EOT だけ**（下の「転送の約束」）。
`status` を完了判定に使おうとすると、`read` を書いた直後のまだ `idle` な一瞬や、
中断したあとの `idle` と区別がつかず、**0件で成功したことになる。**

#### `uplink`（Write）

**モバイルからデバイスへ、自車と周辺車両の測位を渡す。** 1回の Write に JSON オブジェクト1つ。
**中身は下の「[車車間の位置共有](#車車間の位置共有)」が正本**で、ここには GATT の約束だけを書く。

- **必ず Write Request（応答あり）で書く。** Write Without Response は送信キューが埋まると
  **黙って落ちる**。位置が落ちれば検知が落ちるので、落ちたことが分かる方を選ぶ。
  1秒あたり数通なので、往復の遅さは問題にならない。
- **`control` と混ぜない。** 1秒に何通も流れるものと、たまに来るコマンドを同じ経路に置くと、
  片方の不具合がもう片方を巻き込む。
- **知らない `k` や壊れた JSON は無視する**（落ちない）。捨てたことは
  **`status` の `dropped` に数える。`last_error` には載せない**（下の `status`）。
- **`state` が `sending` の間も受け付ける。** 走行ログの転送中に断ると検知が止まる。

### ペイロードの形

**エンコーディングは JSON（UTF-8）。** MessagePack や独自バイナリの方が小さいが、
片側が Python・片側が TypeScript で担当も分かれるため、**目で見て食い違いが分かること**を優先する。
転送するのは走行ログ数千件程度で、サイズが問題になる規模ではない。足りなくなったら圧縮を足す。

レコードは**エンベロープだけをここで決める**。

```json
{ "seq": 1201, "type": "ride", "t": 1756123456789, "body": { } }
```

| 項目 | 内容 |
| --- | --- |
| `seq` | レコード番号。`log_id` の中で 1 から単調増加する。転送の位置と取り込みの一意キーを兼ねる |
| `type` | `"ride"`（走行ログ） / `"detect"`（検知ログ）。増える可能性がある |
| `t` | UTC のミリ秒。**常に入る** |
| `t_est` | `true` のときだけ入る。**`t` が実測ではなく単調時計からの推定**（下の「走行ログの `body`」） |
| `body` | 種別ごとの中身。`"ride"` は下の「走行ログの `body`」、`"detect"` は未確定（#8） |

#### 走行ログの `body`

**測位の値だけを入れる。** `uplink` の `self`（下の「[車車間の位置共有](#車車間の位置共有)」）と
**同じ名前・同じ単位・同じ意味**にする。同じ測位の値に2つの形を作らないため。

```json
{ "lat": 34.6617512, "lon": 133.9344061, "spd": 5.24, "crs": 118.4, "hacc": 4.0 }
```

速度は m/s、方角は度、`crs` は低速時 `null`。時刻はエンベロープの `t` にあるので入れない。

**測位がスマホから来るようになった以上、走行ログはスマホ側にもある。**
それでもデバイスに残すのは、**検知ログ（`type: "detect"`）が同じエンベロープと同じ転送経路を使う**ため。
走行ログだけを外しても仕組みは減らず、**「検知が起きたときに自車がどこにいたか」を
別経路で突き合わせる手間が増える。** 重複は承知のうえで、**取り込み時に同じものが2つ積まれないよう、
一意キー（下の「転送済みログの扱い」）で吸収する。**
将来スマホ側に寄せる判断はありうるが、**いまは経路を1つに保つ方を採る。**

**エンベロープの `t` には、`uplink` で受け取った `self` の `t` をそのまま入れる。**
デバイスのシステムクロックを使わない。**Zero W に RTC はなく、電源を入れた直後の時計は正しくない。**
時刻は**スマホの測位から来るものだけ**とする。

**`t` が常に入るのは、測位を受け取れるまでレコードを作らないため。**

**`self` を受け取っていない間は走行ログ（`type: "ride"`）を作らない。** 位置が無ければ中身が無いので、
**捨てているのは空のレコードだけ**。こうすると `t` が `null` のレコードが存在しなくなり、
時刻が無いレコードの並べ方（起動ごとの経過時間や起動 ID）を決めずに済む。
**屋内のデモでは測位できず走行ログが1件も出ない。** シミュレータが位置と時刻を流す前提で見せること。

**ただし検知ログ（`type: "detect"`）は別。** ローカル層の検知は通信が死んでいても発火する
（`adr/0004-v2v-transport.md`）ので、**`self` が来ていないときに起きた本物の検知イベントがある。**
これを「時刻が無いから」と捨てると、**通信が死んでも黙らない土台の検知結果だけが、
振り返りからも Worker からも丸ごと欠ける。** 一番残したいものが残らない。

**そこで、最後に採用した `self` の `t` に、単調時計（`time.monotonic()`）で測った経過を足して `t` を作る。**
採用した時点の単調時計を控えておき、その差を足すだけでよい。
**`link` が `down` や `nofix` になっても、この控えを捨てないこと。** 捨てると足す先が無くなる。

**推定なので、取り込み側は実測と同じ確からしさで扱わないこと。**
断に入る直前に変な `t` を拾えば、その断のあいだのログが全部おかしな時刻で積まれる。
**そこまでは守らない**（防ごうとすると、下の「受信側の約束」の 4 で避けたはずの
「1通の変な値が居座る」形に戻る）。
**推定した `t` には `"t_est": true` を添える**（エンベロープの追加項目。無ければ実測）。

**一度も `self` を受け取っていない間だけは、検知ログも作らない。** 足す先の `t` が無いため。
**警告は出す**（人に伝えることは時刻を必要としない）。記録が残らないだけ。

**一意キーは `seq` に持たせる**（`(device_id, log_id, seq)`）。レコード側に別の ID を振らない。
`log_id` を作り直すと `seq` は 1 から振り直されるが、キーに `log_id` が入っているので
前の世代とは別のレコードとして積まれる。

### 転送の約束

**ここに書くのは「守らないと片方の実装が壊れること」だけ。**
どう流すか（送信の間隔、タイムアウトの長さ、何回やり直すか、失敗をどう見せるか）は
**それぞれの実装が決めてよい。** 決めごとを増やすほど、噛み合わない場合が増える。

1. **`read` を受けた時点の `latest_seq` を控え、そこを送り終えるか追い越したら EOT を送る。**
   途中で止まって確認を待たない。送るものが0件でも EOT を送る。
   **「持っているぶん全部」にしない。** 同期中も走行は続き、検知が発火すればレコードは増えるので、
   **終わりが来ないまま流し続けることになる**（EOT が出ないので、セントラルは永久に未完了と見なす）。
   転送中に増えたぶんは次の `read` で送る。
   控えたレコード自体が溢れて消えることがあるので、**「追い越したら」も終わりの条件に入れる。**
2. **完了の印は EOT だけ。** EOT を受け取らずに終わった転送（切断、`stop`、取り込みの失敗）は
   **すべて未完了**として扱う。
3. **未完了なら、次に `since` から取り直す。取り直しは何度でも安全**
   （一意キーで冪等に取り込むため。下の「転送済みログの扱い」）。
   **だから、うまくいかないときは「やり直す」でよい。**
4. **アプリ層で再送やウィンドウ制御を作らない。** BLE は接続している間、
   リンク層で再送と順序保証を行う。二重に作ると噛み合わず、
   **双方が相手を待って止まる形になりやすい。**
   この前提は `docs/unverified.md` の 14 で確認する。
5. **`seq` が飛んでいたら、`stop` を書いて `idle` に戻してから、`since` を飛びの手前に戻して
   1回だけ取り直す。** 飛びは転送の最中に見つかるので、`stop` を挟まないと
   **`sending` 中の `read` として断られる**（上の `control`）。
   それでも同じところで飛ぶなら、**欠損として記録して先へ進む。**
   飛びの原因はリングバッファからの溢れ（もう無い）と通信の取りこぼし（まだ有る）の2つあるが、
   **1回取り直せば、原因を見分けなくても取れるものは取れる。**
   **既読位置は必ず前に進める。** 飛びの手前で止め続けると、
   **一度でも溢れた端末とは二度と同期できなくなる**（毎回同じ位置で飛ぶため）。
6. **MTU に依存しない。** デバイスはネゴシエートされた MTU を BlueZ から取得し
   （`GattCharacteristic1` の `MTU` プロパティ。**BlueZ 5.62 以降が要る**。
   Bookworm の 5.66 は満たすが、Bullseye の 5.55 では取れない）、
   Notify 1パケットを `MTU - 3` バイト以内に切る。セントラルは MTU を前提にした組み立てをしない。
7. **ネゴシエートされた MTU が 163 未満なら、接続を成立させない。**
   **下限を決めているのは `control` ではなく `uplink`。** `{"cmd":"read","since":1200}` は 27 バイトだが、
   `uplink` の1メッセージは**上限 160 バイト**（下の「[1回の Write に収める](#1回の-write-に収める)」）で、
   分割しない約束にしている。ATT の Write に載るのは `MTU - 3` なので **163 が下限**になる。

   **`control` に合わせて 64 などにしないこと。** MTU が 64〜162 で成立させると、
   **接続もログの転送も成功するのに測位の書き込みだけが毎回失敗し、
   「つながっているのに検知が一度も動かない」**という一番分かりにくい壊れ方になる。
   遅くなるのではなく**成立しない**ので、黙って続けずエラーとして見せる。
8. **デバイスの `ReadValue` は `options` の `offset` を必ず尊重する**（値を `offset` 以降でスライスして返す）。
   無視して毎回先頭から返すと、**セントラルは先頭 `MTU - 1` バイトが繰り返された壊れた JSON を受け取る。**

### 転送済みログの扱い

**デバイスはログを消さない。** モバイル側が「どこまで受け取ったか」を持つ。

- **`seq` は再起動をまたいで続く。** `log_id` が同じ間は 1 から単調増加し、
  電源を切っても振り直さない（次の番号もファイルに保存する）。
  **保存はレコードを書く前に行う。** 走行中に電源が落ちる前提の装置なので、
  順序を逆にすると**次の起動が同じ番号を別のレコードに振る。**
  一意キーが衝突し、上書きの規則によって**実在するレコードが黙って消える。**
  先に保存すれば、落ちたときに番号が飛ぶだけで済む（飛びは規則5で扱える）。
- デバイスは**容量上限のリングバッファ**として保持する（上限を超えたら古いものから捨てる。上限値は設定で決める）。
  捨てても `seq` は戻らず、`oldest_seq` が上がるだけ。
- ログを消した・失った・`seq` を振り直したときは、**デバイスは `log_id` を作り直す**。
- **モバイルが保存するのは `(device_id, log_id, どこまで取り込んだかの seq)` の1組だけ。**
  次回はここから `since` で再開する。
- **進めてよいのは、取り込みを終えたところまで。** 受け取った端から位置だけ進めると、
  アプリが落ちたときに**デバイスはまだ持っているのに二度と取りに行けなくなる。**
- **`log_id` が前回と違えば、保存済みの `seq` は捨てて `since` なしで全件取り直す。**
  `latest_seq` の大小では判断しない（振り直された側の番号が大きいこともあり、それだと取りこぼす）。
- **取り込みの一意キーは `(device_id, log_id, seq)`。** 同じキーが再び届いたら**上書きする**
  （増やしてはいけない）。**`log_id` をキーに入れるのは、世代が変わると `seq` が 1 に戻るため。**
  入れずに `(device_id, seq)` にすると、作り直した世代の 1 番が前の世代の 1 番を潰す。
- **重複は正常に起こる。** 途中で切れて `since` から取り直せば、同じ区間がもう一度流れてくる。
  同じキーで上書きされるだけなので、何度取り直しても二重に積まれない。

デバイス側で消す方式にしなかったのは、**取り込みに失敗したときに元に戻せなくなる**ため。
デモ中に同じログを何度でも取り直せることを優先した。

### ペアリング・認証

**ペアリングしない。** BLE のリンク層の暗号化・認証を使わず、**誰でも接続して読み書きできる。**
Characteristic に暗号化のフラグ（`encrypt-read` / `encrypt-write` / `encrypt-notify`）を付けない。

| Characteristic | 付けるフラグ |
| --- | --- |
| `device-info` | `read` |
| `control` | `write` |
| `log` | `notify` |
| `status` | `read`, `notify` |
| `uplink` | `write` |
| `config` | **実体を作るとき（#33）に決める。今は作らない** |

#### なぜ外したか

**ハッカソンの期間内では、守ることより動くことを優先する。**

ペアリングを入れると、**動かなくなる要因の方が増える**。初回は購読が
`GATT_INSUFFICIENT_AUTHENTICATION` で失敗するのでボンド完了を待って張り直す処理が要り、
ボンドを受け付ける窓（`Pairable` のタイマー）を作る必要があり、
**片側だけペア設定を解除すると `/var/lib/bluetooth` を手で消すまで直らない**。
デモ当日にこれが起きると復旧に時間を取られる。

**書けるのは `control`（`read` / `stop`）と `uplink` だけ。** `control` は他人に書かれても
勝手に転送が始まる程度の害しかない。検知を無効化できる `config` はまだ作らない。

**`uplink` は他人に書ける。** できることは2つあり、**どちらも「検知を止める」側にも効く。**

- **偽の位置を書き込んで、居ない自転車で警告を出させる。**
- **検知を止める。** 接続枠を1つ占有すれば持ち主のスマホがつながらず、測位が1つも届かない。
  **`self` を上書きし続けて自車の位置を偽ることもできる**（`self` は届いた最後のものを採るため。下の「受信側の約束」の 4）。

**「偽の警告は出せるが、止めることはできない」ではない。** 止められる。

**そして、気づけるとも限らない。** 攻撃者が接続枠を取って `self` を書き続けている間、
デバイスから見れば `self` は新しく届き続けるので **`link` は `up` のまま**で、
偽の位置で検知が動く。持ち主のスマホは接続できないので**スマホ側では気づける**が、
**デバイスの表示は健全に見える。** この方式で一番避けたい「静かに壊れる」が、ここには残っている。
**接続枠が1つであることが、そのまま「奪えば止まる」を意味している。**

走行中に狙って行うのは難しく、ペアリングを入れる代償（下）に見合わないと判断した。
**やらないと決めただけで、要らないわけではない。**
**`config`（#33）でペアリングを戻すかを判断するときは、ここも一緒に見直すこと。**

#### 割り切っていること

- **近くにいる誰でも、汎用の BLE アプリで走行ログ（位置情報）を読める。**
- **常時アドバタイズし、名前と `device-info` に固定の `device_id` が出る**ので、
  **特定の自転車がいつどこにいたかを記録できる**。これも持ち主の位置情報にほかならない。
- **この経路に秘密値を流さない。** API トークンや Wi-Fi の PSK を `control` で書き込む設計にしないこと。

実利用に出すなら、ペアリング必須化・Characteristic への暗号化要求・
アドバタイズする識別子を定期的に変えること（Resolvable Private Address）が要る。**やらないと決めただけで、
要らないわけではない。**

#### `config`（#33）を作るときは、ここを決め直す

**設定を書き込める経路を開けると、他人にしきい値を書き換えられ、検知を無効化できる。**
危険を知らせる装置としてそれは成立しないので、**`config` の実体を作るときにペアリングを戻すかどうかを
必ず判断すること**（この節を「決めたから終わり」として素通りしない）。

戻す場合に要るのは3つ。**GATT の構造は変わらない。**

- Zero W の BlueZ に Agent を `NoInputNoOutput` で登録する（Just Works を無人で受けるため）。
- `device-info` 以外に暗号化フラグを付ける。**Notify は `encrypt-read` では効かず `encrypt-notify`**
  （`log` は `read` プロパティを持たないため。付け間違えると CCCD が保護されず、ボンドなしで購読できる）。
- モバイルはボンド完了（`ACTION_BOND_STATE_CHANGED`）を待って購読を張り直す。

なお **Zero W の Bluetooth は 4.1 で LE Secure Connections（4.2 以降）が使えない**ため、
戻したとしても Just Works になり、**中間者攻撃には守られない**。防げるのは
「ボンドしていない端末からの読み書き」まで。

#### 書き込みを受ける側の約束

**ペアリングの有無と関係なく、「何を書かれるか」は受け取る側で検証する。**

- 知らないコマンド・知らない `k`・知らないキーは**無視する**（落ちない）。
- 数値は範囲を検証してから採用する。**範囲外は捨てて `status` の `last_error` に載せる。**
  **これは `control` の話。** `uplink` の範囲は下の
  「[受信側（デバイス）の約束](#受信側デバイスの約束)」で決めており、
  捨てたことは `last_error` ではなく `dropped` に出す。
  **`state` は変えない**（不正なコマンドが1つ来ても、流れている転送は止めない）。
- 検知のしきい値を無効化する値（極端に大きい距離など）も範囲で弾く。

#### 運用で気をつけること

- **接続を占有されると検知が動かない。** つなげるセントラルは1台で、BlueZ は接続中アドバタイズを止める。
  デモ会場で他の人のスキャンアプリがつながったままになると、持ち主のスマホが接続できない。
  **`uplink` が唯一の測位の供給元なので、これは「ログ同期が後回しになる」ではなく
  「走行中ずっと車車間の検知が動かない」ことを意味する。**
  ただし**デバイスは黙らない。** `link` が `down` のまま出続けるので（下の
  「[通信断を必ず見せる](#通信断を必ず見せる)」）、乗っている人は気づける。
  ローカル層の検知も動き続ける。
  つながらないときは**まずデバイスを再起動して接続を切る**（原因を探す前にこれを試す）。

## 車車間の位置共有

**自転車どうしが直接つながるのをやめ、スマホと Worker を経由して位置情報を配る。**
Zero W の内蔵 Wi-Fi は 802.11s（mesh point）を持たず ad-hoc（IBSS）も実質動かないため、
メッシュは成立しない。**Zero 2 W に替えても無線チップが同じなので解決しない。**
経緯と却下した案は `adr/0004-v2v-transport.md`。

```
[デバイス] --BLE 常時接続--> [スマホ] --HTTPS/LTE--> [Worker]
     ^                                                  |
     └──── 自車の位置・周辺車両の位置 ←─────────────────┘
```

| | 担当 | 仕様 |
| --- | --- | --- |
| スマホ | 測位（GNSS）と中継。**判断しない** | この節 |
| Worker | 近くにいる相手を選んで配る | 未確定（[#7](https://github.com/Hashimoto-Teppei/web-iot-makers-challenge-team-c/issues/7)） |
| デバイス | 受け取った位置で危険を判断し、その場で人に伝える | この節と #8 |

**ここで決めたペイロードがそのまま検知アルゴリズム（#8）の入力になり、
シミュレータ（#12）が流し込むデータの形もこれに揃える。**

**位置はスマホの GNSS から取る。デバイスに GPS モジュールを載せない。**
デバイスが自車の位置を知る唯一の経路もこの BLE である。

### 経路はデバイス ⇄ モバイルの BLE に相乗りする

**新しい通信路を作らない。** 上の「デバイス ⇄ モバイル（BLE GATT）」で決めた接続の上に、
`uplink`（Write）を1本足すだけにする。プロトコルバージョンもその節の `proto` を使い、
**この節で別のバージョン番号を持たない**（1つの境界に2つのバージョンがあると、どちらを上げるかで必ず迷う）。

**接続は常時維持する。** 走行後にまとめて同期する `log` と違い、この経路は走行中ずっと流れる。
スマホ側はフォアグラウンドサービスで接続を保つ（`unverified.md`）。

### メッセージ

`uplink` への 1回の Write に **JSON オブジェクト1つ**。`k` が種別を表す。

```json
{"k":"self","t":1756123456789,"lat":34.6617512,"lon":133.9344061,"spd":5.24,"crs":118.4,"hacc":4.0}
{"k":"peer","id":"7d02e5b1","t":1756123456650,"lat":34.6618891,"lon":133.9345121,"spd":6.11,"crs":300.2,"hacc":5.5}
```

**上の2行は2つの例であって、1回に2行書くという意味ではない。**
`log` の JSON Lines とは別物で、**この経路に `\n` の区切りは無い。1回の Write に1つ。**

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `k` | 文字列 | `"self"`（自車の測位） / `"peer"`（周辺車両1台ぶん） / `"nofix"`（測位が無い。**下の「[通信断を必ず見せる](#通信断を必ず見せる)」**。`k` 以外の項目を持たない） |
| `id` | 文字列 | 端末ID。**`k` が `"peer"` のときだけ入る**（`"self"` は自分なので要らない） |
| `t` | 整数 | **測位した時刻**（UTC ミリ秒）。スマホが測位を得た時刻であって、書き込んだ時刻ではない |
| `lat` / `lon` | 小数 | 緯度・経度（度、WGS84） |
| `spd` | 小数 | 対地速度（**m/s**） |
| `crs` | 小数 or `null` | 進行方角（度、真北 0、時計回り 0〜360未満）。**低速時は `null`** |
| `hacc` | 小数 | 水平位置精度（メートル）。小さいほど確か |

- **`id` は BLE の `device_id` と同じ形**（16進の小文字8文字）。同じデバイスを2つの名前で呼ばない。
- **単位は m/s と度で統一する。** km/h とノットを混ぜない。
  検知のしきい値（`config.py`）も同じ単位で書く。
- **`crs` は速度が出ていないと意味を持たない。** 止まっている自転車の進行方角は測位では決まらず、
  Android は直前の値を返したり `hasBearing()` が `false` になったりする。
  **`spd` が設定のしきい値（既定 1.0 m/s）未満なら `crs` に `null` を入れる。**
  受信側は `crs` が `null` の相手を「向きの分からない相手」として扱う（扱い方は #8）。
- **`hacc` はスマホが返す推定精度をそのまま入れる。** Android の `Location.getAccuracy()` は
  **メートルで返る**ので、換算も係数も要らない。
  **桁は丸める**（下の「[1回の Write に収める](#1回の-write-に収める)」）。換算が要らないだけで、
  `getAccuracy()` の戻り値をそのまま `JSON.stringify` に渡してよいという意味ではない。

  **`hasAccuracy()` が `false` のときは、その位置を送らない。**
  0 や適当な既定値で埋めると、**精度が分からない位置が「誤差 0 の確かな位置」として検知に届く。**
  デバイス側では見分けられないので、**送らない側で止める。**
  **`self` の場合は、代わりに `nofix` を送る**（黙ると「スマホは測位できているのにデバイスは永久に
  `nofix`」になり、原因が追えない。下の「[通信断を必ず見せる](#通信断を必ず見せる)」の不変条件を守る）。
  `peer` の場合はその1台を送らないだけでよい。
- **減速度・加速度は送らない。** 受信側が `t` と `spd` の履歴から出す。
  送る側で出すと**端末ごとに算出方法が違ってしまい**、検知の担当が前提をそろえられない。
  受信側は急接近の検知にも相手の履歴を持つので、**履歴を持つ仕組みはどのみち要る。**
- **知らないキーは無視する。** 項目が増えても古い実装が落ちないようにするため。
- **必要な項目が欠けているメッセージは捨てる。** 何が必要かは `k` ごとに違う。
  **上の表全体を「必須の一覧」として実装しないこと**（`id` は `peer` にしか無いので、
  表どおりに存在チェックすると**`self` が1通残らず捨てられ、自車の位置が永久に入らない**）。

  | `k` | 必須の項目 |
  | --- | --- |
  | `self` | `k` / `t` / `lat` / `lon` / `spd` / `crs` / `hacc`（**`id` は入らない**） |
  | `peer` | 上に加えて `id` |
  | `nofix` | `k` **だけ**。他は入らない |

  `crs` の `null` は「欠けている」うちに入らない。
- **知らない `k` は無視する。** エラーにしない。

#### 1回の Write に収める

**1メッセージの上限を 160 バイトとする。** 分割して組み立てる仕組みは持たない
（`log` の JSON Lines のような組み立ては、この経路では作らない）。
下の桁で丸めたときの最悪でも 119 バイト。**余白を持たせて 160 とする。**

**この 160 が、接続を成立させる MTU の下限（163）を決めている**（上の「転送の約束」の 7）。
**項目を足して 160 を超えるときは、MTU の下限も一緒に上げること。**
片方だけ直すと、超えた瞬間に**測位の書き込みだけが黙って失敗する。**

**送る前に丸める。桁数を決めておく。**

| 項目 | 小数の桁 | 例 |
| --- | --- | --- |
| `lat` / `lon` | **7桁**（約 1cm 刻み。測位の精度より十分細かい） | `34.6618891` |
| `spd` | 2桁 | `6.11` |
| `crs` | 1桁。**丸めた結果が `360.0` になったら `0` にする** | `300.2` |
| `hacc` | 1桁 | `5.5` |

**丸めないと上限を超える。** JavaScript の数値は倍精度で、`JSON.stringify` は最大17桁まで出す。
`getAccuracy()` が返す float をそのまま入れると `"hacc":5.500000238418579` のようになり、
**全項目がこの調子だと 160 を超える。**超えれば ATT の Write に載らず、
**測位の書き込みだけが黙って失敗する。**

**丸めた `crs` が `360.0` になったら `0` にする。** 受信側の範囲は **0 以上 360 未満**なので、
そのままだとその1通が丸ごと捨てられる。

**周辺車両は1回の Write に1台。** まとめて配列で送らない。台数が増えると必ず MTU を超え、
**超えた瞬間に「周辺が1台も見えない」形で壊れる**（一部が欠けるのではなく全部が届かなくなる）。
1台ずつなら、多すぎるときは**遠い相手から落とすだけ**で済む。

**同時に扱う周辺車両の数に上限を置く**（スマホ側の設定。既定 8台）。上限を超えたぶんは
**遠い相手から落とす。** 検知に効くのは近い相手だけであり、遠い相手を捨てても失うものはない。
**捨てた台数を数えて画面に出せるようにしておく**
（黙って捨てると、見えない自転車がいることに誰も気づけない）。

### 送る間隔

| 何を | いつ |
| --- | --- |
| `self` | **スマホの測位が更新されたとき。**時間で回さず測位に合わせる（実質 毎秒1通） |
| `peer` | **Worker から届いたつど。**自分の測位の更新を待たない |
| `nofix` | 測位が無い間、`self` と同じ間隔で |

**`self` を測位より速く送っても中身は前と同じ**で、BLE の帯域と両側の CPU を使うだけ増える。

**`peer` を自分の測位のタイミングまで溜めない。** 溜めると最大1秒ぶん古い位置を渡すことになり、
**この経路がもともと抱えている遅れ（150〜350ms）に上乗せされる。**
届いたものをそのまま流せば、デバイス側は `t` を見て正しい時刻の位置として扱える。

**送っていない間を埋めない。** 前回の位置をそのまま送り直す、といったことはしない。
受信側は下の失効で「居なくなった」と判断する。

**測位できていない間は `self` を送らない**（代わりに `nofix` を送る）。
位置か時刻のどちらかが欠けた `self` を作らない。
**屋内のデモでは `self` が1通も飛ばない。** 見せるときはシミュレータを使うこと。

### 受信側（デバイス）の約束

**ここに書くのは「守らないと検知が壊れること」だけ。**
受け取ったあとどう検知に渡すかは #8、何秒ぶんの履歴を持つかは実装が決めてよい。

1. **自分の `id` を持つ `peer` は捨てる。** Worker が自分の位置を配り返すことがある。
   捨てないと**自分自身を「距離 0 で並走する自転車」として検知する。**
2. **必要な項目が欠けているメッセージは捨てる。** 何が必要かは `k` ごとに違う。

   | `k` | 必須の項目 |
   | --- | --- |
   | `self` | `k` / `t` / `lat` / `lon` / `spd` / `crs` / `hacc`（**`id` は入らない**） |
   | `peer` | 上に加えて `id` |
   | `nofix` | `k` **だけ**。他は入らない |

   **上の表全体を「必須の一覧」として実装しないこと**（`id` は `peer` にしか無いので、
   表どおりに存在チェックすると**`self` が1通残らず捨てられ、自車の位置が永久に入らない**）。
3. **数値は範囲を検証してから使う。範囲外は捨てる。壊れた1通で落ちないこと。**

   | 項目 | 通してよい範囲 |
   | --- | --- |
   | `lat` | -90 〜 90 |
   | `lon` | -180 〜 180 |
   | `spd` | 0 以上、**設定の上限（既定 30 m/s ＝ 108km/h）以下** |
   | `crs` | **`null`**、または 0 以上 360 未満 |
   | `hacc` | 0 より大きく、**設定の上限（既定 50 m）以下** |

   **`crs` の `null` を範囲外として捨てない。** `null` は「止まっていて向きが分からない」という
   正常な値であり、捨てると**止まっている自転車と低速の自転車が丸ごと消える。**
   急接近の検知（#9）が一番見たい相手がこれなので、**検知が静かに効かなくなる。**
   Python で `0 <= crs < 360` を `None` に対してそのまま書くと `TypeError` で
   **受信のループごと止まる**ので、`null` かどうかを先に見ること。

   **`spd` と `hacc` に上限を置くのは、壊れた1通を検知に届かせないため。**
   桁違いの `spd` は相対速度も外挿した位置も桁違いにする。
   `hacc` が数十〜数百メートルの相手を「そこにいる自転車」として渡すと、**居ない自転車で警告が鳴る。**
4. **`peer` の新旧は `t` で判定する。同じか古い `t` は捨てる。`id` ごとに覚える。**
   1つの変数で持つと**一番新しい1台ぶんしか残らず、他の自転車を全部捨てる。**
   近傍が常に1台になり、検知は静かに発火しなくなる。

   **経路は TCP なので、詰まると古いものが「まとめて順番どおり」届く。**
   位置情報は古ければ捨てたいデータなので、**この判定が無いと、過ぎ去った位置で検知が走る。**

   **`self` には適用しない。** `self` は BLE 1本しか通らず、ATT が順序を保証するので入れ替わらない。
   **届いた最後のものを常に採る。**
   新旧判定を入れると、逆に**「1通の変な値が居座って、以後の正しい `self` を全部古いとして捨てる」
   という戻れない壊れ方**を作り込む。
5. **時刻の妥当性は「推定の現在時刻」を基準に見る。**
   デバイスには時計が無い（RTC が無く、システムクロックは信用できない）ので、
   **最後に採用した `self` の `t` に単調時計の経過を足したものを「いま」とする。**

   **`self` の `t` そのものを基準にしないこと。** それは測位が更新された時刻であって、いまではない。
   測位が数秒抜けている間、正常に届く `peer` が全部「未来」として捨てられ、
   **`link` は `up` のまま近傍だけが空になる**（この節が一番避けたい形）。

   **どれだけ先／どれだけ古い `t` まで通すかは設定で持つ**（`config.py`）。
   **既定値と、境界での細かい挙動は実装時に決める。** 実測しないと妥当な値が出ないため
   （`unverified.md`）。
6. **再送・ACK・順序の作り直しをアプリ層に作らない。** BLE のリンク層と TCP のどちらも再送する。
   三重に作ると噛み合わず、**待ち合って止まる形になりやすい。**
7. **最後に受信してから設定の時間（既定 3 秒）が過ぎた相手を、近傍から消す。**
   **消さないと、届かなくなった自転車が「その場に止まっている自転車」として残り続け、
   通り過ぎたあとも警告が鳴る。**
   **近傍から消すときは、覚えていた `t` も一緒に捨てる**（残すと戻ってきた相手を捨て続ける）。
   **既定の 3 秒は仮の値。** 短すぎると**近づいている最中の相手が消えて警告が途切れる。**
   実測して調整する（`unverified.md`）。
8. **`link` が `up` でない間は、`peer` を近傍として持たない。**
   自車の位置が無ければどの検知も成立しないので、持っても意味がない。
   **判定を別に作らず `link` を見る**（下）。しきい値を2か所に持つと、`peers` の中身と表示が食い違う。
9. **相手の位置を、受信した時刻ではなく `t` の時刻の位置として扱う。**
   届くまでの遅れを 0 と見なすと、速い相手ほど実際の位置とずれる。
   **この経路の遅れは 150〜350ms、詰まればそれ以上**あるので、直接通信より効いてくる。

### 通信断を必ず見せる

**この方式で一番危ないのは、静かに止まることである。**

直接通信なら、経路が死ねば全員がつながらず**全員が気づく**。スマホ経由では、
**1人のスマホが落ちてもその人だけ警告が来ず、他の全員からは正常に見える。**
落ちたことに気づかないまま「今日は危険が無いのだな」と思って走ることになる。

そこで**デバイス側にウォッチドッグを置き、`status` の `link` として出す。**

**「経路が死んだ」と「測位がまだ出ていない」を分ける。** どちらも検知は動かないが、
**人がすべきことが違う**（前者は端末を見る、後者は待つか外に出る）。同じ表示にすると、
待てば直るものと直らないものが区別できない。

そのために、**スマホは測位が無い間も書き続ける。**

| スマホの状態 | 書くもの | デバイスの `link` |
| --- | --- | --- |
| 測位できている | `self`（と `peer`） | `up` |
| **測位できていない** | **`{"k":"nofix"}`** を同じ間隔（毎秒）で | `nofix` |
| アプリが落ちた / BLE が切れた | 何も来ない | `down` |

**`nofix` に位置も時刻も入れない。** 入れるものが無いから送る通知であり、
**`self` の代わりにならない**（受け取っても自車の位置は更新しない）。

#### `link` を決めるときに外してはいけないこと

**秒数と判定の細かい形は実装時に決める**（`config.py`。実測しないと決まらない）。
ただし**次の5つを外すと、この仕組みが目的を果たさない。**

- **`up` から始めない。** `self` を一度も採用していない間は `up` にしない。
  `nofix` を送らない実装のスマホが `peer` だけ流すと、**自車の位置が無いまま近傍を持つ。**
- **「何か書き込みが来たか」だけで決めない。** `peer` だけ流れて `self` が止まる状態がありうる。
  書き込みは届くので `up` のままになり、一方で「受信側の約束」の 8 が `peer` を全部捨てる。
  **表示は健全なのに検知が1つも動かない**という、この節が防ぎたい形そのもの。
- **「受け取った」ではなく「採用した」で測る。** 範囲を外れた `self` が届き続けている間、
  到達だけを見ると `up` のままだが、自車の位置は入っていない。
- **`nofix` を「一度来たら立つ旗」にしない。** 見るのは**直近がどちらだったか**。
  旗にすると**再起動するまで `up` に戻らず**、停止中の情報表示が一度も出ない。
  また `peer` が挟まるたびに判定が変わらないよう、**見る対象は `self` と `nofix` だけ**にする
  （混ぜると `link` が毎秒ばたつき、**走行中の画面に文章が点滅して出る**）。
- **`t` が進んでいるかも見る。** `self` は上書きするだけなので、時計や測位が固まって
  同じ `t` を送り続けられても値の検証では気づけない。
  **ただし「控えた1点の `t` より進んだか」で実装しないこと。**
  変な値を1通採用した瞬間に基準がそこで固まり、**再起動まで戻らなくなる。**
  一定の窓の中で見るなど、**自然に回復する形にする。**

#### `up` でない間にすること

- **その旨を出力に出し続ける。** 出し方は `notifications.md`。
  **一度きりの通知にしない。** 見逃した人はそのまま走り続ける。
- **車車間の検知は「相手が居ない」ではなく「分からない」として扱う。**
  近傍を空にして黙るのは、この表示とセットで初めて成立する。
- **速度が分からないので、表示は「走行中」として扱う**（`notifications.md`）。
  止まっているように見えても、走行中の画面に文章を出さない。
- **ローカル層（センサーによる検知）は `link` に関係なく動き続ける**（`adr/0004`）。
- **屋内のデモでは `nofix` が出続けるのが正常。** これを故障として扱わないこと。

**スマホ側にも同じ問題がある**（デバイスが落ちても気づかない）が、そちらは画面があるので
アプリの表示で足りる。仕様はモバイル側に委ねる。

### 端末ID とプライバシー

`id` は BLE の `device_id` と同じ固定値で、**変わらない。**

- **経路上の位置情報は、BLE の区間では誰でも読める**（ペアリングしないため。上の「割り切っていること」）。
  スマホと Worker の間は HTTPS で守られる。
- **なりすましを防ぐ仕組みは持たない。** Worker に偽の位置を送る端末を止められない。
  ハッカソンの期間内では、署名や端末認証を入れるより動くものを優先する。
  **やらないと決めただけで、要らないわけではない**（BLE 側と同じ）。
- **この経路に秘密値を流さない。** 位置と速度以外を載せない。
- **実走行のログをコミットしない。** 流れているのは個人の移動そのもの。
  テストとシミュレータには合成したデータを使う（`CLAUDE.md`）。

### シミュレータ・検知との関係

**検知は、データがどこから来たかを知らない。**

| | `self` と `peer` の出どころ |
| --- | --- |
| 実機 | スマホ（`uplink` への Write） |
| 開発機 | **シミュレータが「スマホ役」になり、同じ形の JSON を渡す** |

- **シミュレータ（#12）は自車と周辺車両の両方を流す。** 自車を含めるのは、
  **3つの検知がどれも自車の状態を入力に取る**ため。周辺車両だけでは1つも走らせられない。
- **受け取って近傍の状態を保つところまで**が車車間通信の責務で、
  **そこから先（何を危険と見なすか）は #8。**
- **層を分ける。** BlueZ を触る部分は Linux 専用なので `src/device/hw/ble.py` に置き、
  **受け取った JSON を検証して近傍の状態を保つ部分は `src/device/v2v.py`** に置く
  （`apps/device/README.md` のディレクトリ表）。
  `v2v.py` は BLE を知らないので、**開発機で pytest から直接叩ける。**
  差し替えるのは `main.py` の配線であって、**メッセージも検知の入力も変わらない。**
  具体的な渡し方は #12 で決める。

## モバイル ⇄ API

**エンドポイントの型はコードが正本。** `apps/web/src/worker/` のルート定義から Hono RPC で型が伝播するため、
ここにリクエスト/レスポンスの構造を書き写さない（必ず実装とずれる）。
この節には型から読み取れないことだけを書く。

Web の画面は API と同じ Worker 内にあるため単一オリジンで、CORS の考慮は不要。
モバイルアプリはネイティブなので CORS の対象外。

**この境界は走行後の同期だけでなく、走行中の中継も担う**（上の「[車車間の位置共有](#車車間の位置共有)」）。
自分の位置を送り、近くにいる相手の位置を受け取る経路がここに要る。
**流れるペイロードの中身は上の節が正本**で、Worker がどう受けてどう配るか（近さの決め方、
つなぎ方、配る間隔）が未確定（#7）。

## 危険検知アルゴリズム

3つの検知を**別々の担当が並行実装する**ため、これも境界として先に決める。
検知は1つ1ファイルに分け、共通のインターフェースに揃える。4つ目が増えたときの受け口も兼ねる。

インターフェースは未確定（#8）。**これが決まるまで3つの検知（#9 / #10 / #11）は着手できない。**
担当と進捗は各 Issue の assignee を見ること。

**入力の出どころが2種類あることを前提に決める**（`adr/0004` の「2つの層に分ける」）。

| | 入力 | 通信への依存 |
| --- | --- | --- |
| 車車間の検知（#9 / #10 / #11） | 自車と周辺車両の状態 | **依存する。**通信断の間は動かない |
| ローカルの検知（#26 など） | デバイスに載せたセンサーの値 | **依存しない** |

**共通インターフェースを前者だけに合わせて決めない。** 後者が入る受け口を最初から見ておかないと、
