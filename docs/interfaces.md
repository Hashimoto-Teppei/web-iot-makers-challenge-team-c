## デバイス ⇄ モバイル（BLE GATT）

デバイスがペリフェラル、モバイルアプリがセントラル。デバイスに蓄積された検知ログ・走行ログを吸い上げる。

**今この経路で書けるのは `read` / `stop` だけ**で、設定の書き込みはまだできない
（`config` は UUID を予約しただけ。中身は #33）。**書き込みの経路を実装しにいかないこと。**
サーバーは BLE を話さない。デバイスと直接やりとりするのはモバイルアプリだけで、
サーバーへはモバイルアプリが中継する。

**この節が唯一の正本。** Python 側は TypeScript の Zod スキーマを参照できないため、
デバイス担当とモバイル担当はここだけを見て実装する。スキーマを変えたら両実装を更新すること。

プロトコルバージョンは **1**。互換性を壊す変更をしたらこの数字を上げ、`device-info` の `proto` にも反映する。
**モバイルは `proto` が自分の想定と違えば転送しない。** 画面に更新を促すだけにする。
デバイスだけ更新して古い APK が残る組み合わせは起こりうるので、
非互換のレコードをパースして壊れたログを Worker まで運ぶより、止まる方がよい。

### 前提

- **接続できるセントラルは同時に1台**。走行後に持ち主のスマホが1台つながるだけなので、複数台を扱わない。
  **アドバタイズを止めても2台目は防げない**（アドレスを知っていれば接続できる）。
  防ぐ仕組みは持たないので、**セントラルは自分が `read` を書いたときだけ EOT を信じる。**
  書いていないのに EOT が来たら、それは他人の転送。既読位置を進めない。
- **デバイスは常時アドバタイズする**（**接続中を除く**。BlueZ は接続している間アドバタイズを止める）。
  ボタンで切り替える案もあるが、入力部品が未確定（#13）のため今は持たない。
  **スキャンで見つからない＝故障、とは限らない。** 他人がつなぎっぱなしにしている場合も同じに見える
  （下の「運用で気をつけること」）。
- **転送はモバイルアプリが起動している間だけ**。走行中の通知はデバイス側で完結するので（`notifications.md`）、
  この経路が遅れても危険検知には影響しない。

### UUID

`0x1800` 台のような 16bit UUID は SIG が割り当てた仕様専用のため、独自のサービスには使えない。
128bit のランダム UUID を1つ作り、先頭 4 バイト目だけを変えて枝番にする。

| 役割 | UUID | プロパティ |
| --- | --- | --- |
| Service | `68666e00-58cc-4540-90ad-18bfae31615f` | — |
| `device-info` | `68666e01-58cc-4540-90ad-18bfae31615f` | Read |
| `control` | `68666e02-58cc-4540-90ad-18bfae31615f` | Write（応答あり / Write Request） |
| `log` | `68666e03-58cc-4540-90ad-18bfae31615f` | Notify |
| `status` | `68666e04-58cc-4540-90ad-18bfae31615f` | Read / Notify |
| （予約）`config` | `68666e05-58cc-4540-90ad-18bfae31615f` | — |

`config`（設定の書き込み）は **UUID だけ予約して実体はまだ作らない**。何を書き込むかが未確定（#33）のため。
決まるまで、設定はデバイス側の設定ファイルで変更する。

アドバタイズには 128bit の Service UUID と、**Local Name `bg-<device_id 下4桁>`**（`device_id` が `c3f1a20b` なら `bg-a20b`、7文字）を載せる。

**名前を7文字に縮めるのは、31 バイトに収めるため。**
Flags(3) + 128bit UUID(2+16) + 名前(2+7) = 30 バイトで、ぎりぎり収まる。
`bikeguard-a20b`（14文字）だと 37 バイトになって入らず、BlueZ の `LocalName` は
**入りきらないぶんを黙って切り詰める**ので、名前が中途半端に欠けたまま気づけない。

**`Includes`（`tx-power` など）・`Appearance`・`ServiceData` を設定しない。**
余白は1バイトしかなく、どれか1つ足すだけで溢れて名前が切り詰められる。しかも**エラーは出ない。**

**Scan Response に逃がす案は採らない。** BlueZ の `LEAdvertisement1` で scan response を指定する
プロパティ（`ScanResponseData` など）は experimental で、`bluetoothd --experimental` が要る。
デモ環境の前提を増やしたくない。Zero W の Bluetooth は 4.1 で Extended Advertising も使えない。

モバイルアプリは Service UUID でスキャンし、名前は人が見分けるためだけに使う。

### 接続してから転送するまで

**順番を守る。** 逆にすると原因の分かりにくい失敗になる。

1. Service UUID でスキャンして接続し、**MTU 247 を要求 → サービス探索**の順に行う。
   **重ねて実行しない。** GATT の操作は一度に1つしか出せず、`requestMtu` と `discoverServices` を
   同時に走らせると片方が黙って落ちる。**それぞれ完了のコールバックを待ってから次へ進む。**
   サービス探索が終わるまで Read も購読もできない。
   **ネゴシエートされた MTU が 64 未満ならここで止める**（下の「転送の約束」の 7）。
2. `device-info` を読んでデバイスを識別する。
3. **`log` と `status` の両方の Notify を購読する。**
4. **受信バッファを空にしてから**、`control` に `read` を書く。

**3 と 4 も1つずつ順に行う。** 購読は CCCD への Write であり、`read` の Write と合わせて
3回の GATT 操作になる。まとめて発行すると**購読が黙って成立せず、0件で転送が終わる。**
`onDescriptorWrite` を待ってから次へ進むこと。

**購読より先に `read` を書かない。** デバイスはすぐ流し始めるが、購読していない Characteristic の
Notify は Android 側で捨てられ、**1件も届かないまま転送が終わる**。

**受信バッファを捨てるのは、接続直後だけでなく `read` を書くたび。** 前の転送が途中で切れていると
`\n` で終わっていない断片が残り、**そのままだと先頭の1レコードが壊れた JSON になる。**
`stop` のあとも、下の規則5で取り直すときも同じ。

**ペアリングは要らない**（下の「ペアリング・認証」）。接続したらそのまま読み書きできる。

### Characteristic の役割

#### `device-info`（Read）

接続直後に1回読む。JSON オブジェクト1つ。

```json
{ "proto": 1, "device_id": "c3f1a20b", "log_id": "9a1c...", "oldest_seq": 941, "latest_seq": 1284 }
```

- `device_id` — デバイスごとに固定。初回起動時に生成してファイルに保存する。
  **16進の小文字8文字**（`uuid4().hex[:8]` など）。`log_id` も同じ形。
  ハイフン付きの UUID を入れると、アドバタイズの名前もキーの長さも変わる。
  **ログとは別のファイルに置く。** ログと一緒に消えると `device_id` が変わり、
  取り込みの一意キー `(device_id, log_id, seq)` が総入れ替えになって、**履歴がまるごと重複する。**
- `log_id` — **ログの世代**。ログを消した・失った・`seq` を振り直したときだけ変わる。
  **これが前回と違えば、保存してある既読位置は無効**（下の「転送済みログの扱い」）。
- `oldest_seq` / `latest_seq` — デバイスが**今も持っている**レコード番号の範囲。
  あと何件あるかの目安。**1件も持っていないときは両方 `0`**（`seq` は 1 から始まる）。

#### `control`（Write）

モバイルからデバイスへのコマンド。1回の Write に JSON オブジェクト1つ。

**必ず Write Request（応答あり）で書く。** Write Without Response だと `stop` が届いたかを
セントラルが知れず、`stop` が落ちればデバイスは送り続ける。

| コマンド | 形 | 内容 |
| --- | --- | --- |
| 転送開始 | `{"cmd":"read","since":1200}` | `seq > since` のレコードを `log` に流し始める。`since` 省略で全件 |
| 中断 | `{"cmd":"stop"}` | 転送を止める。**EOT は送らない**（EOT の有無が「送り切った」と「途中でやめた」の区別になる） |

**知らないコマンドは無視する。** 断った理由は `status` の `last_error` に載せる。

**`state` が `sending` の間に来た `read` は断る**（`last_error` に載せる）。
受け付けて2つ目の転送を始めると、**同じ `log` の上で新旧のストリームが混ざる。**
ストリームを見分ける印がないためセントラルは区別できず、`seq` が逆行し、
**古い方の EOT で新しい転送が完了したことになる。**
やり直したいセントラルは、**先に `stop` を書き、`state` が `idle` に戻ってから `read` を書く。**

**切断されたらデバイスは転送を中止し、`state` を `idle` に戻す。**
戻さないと、アプリが同期中に落ちた端末は**つなぎ直しても以後ずっと `read` を断られる。**

#### `log`（Notify）

レコードを **JSON Lines**（1レコード = 1行の JSON + `\n`）のバイトストリームとして流す。
**Notify 1パケットとレコードの境界は一致しない。** セントラルは受信したバイトをバッファに連結し、
`\n` で区切って初めて1レコードとして扱うこと。1レコードが数パケットに分かれるのは正常。

区切りに使うため、**レコード内の JSON に生の改行を含めない**（`json.dumps` の既定どおり `\n` は `\\n` に
エスケープされる）。

転送の終わりは **`0x04`（EOT）1バイト**。**最後のレコードの `\n` の直後に、同じストリームの続きとして送る。**
単独のパケットで届く保証はないので、**パケットの区切りで判断しない**
（最後のレコードと同じ Notify に相乗りして届くことがある）。
セントラルは「`\n` で切り出したあとにバッファへ残った `0x04`」を見て完了と判断する。

**エラーを `log` に混ぜない**。ログの本文とエラーが同じ経路に来るとパースが壊れる。

#### `status`（Read / Notify）

**転送の進み具合を人に見せるためのもの。** JSON オブジェクト1つ。

```json
{ "state": "sending", "sent": 32, "remaining": 52, "last_error": null }
```

| 項目 | 内容 |
| --- | --- |
| `state` | `idle`（流していない） / `sending`（流している） |
| `sent` | 今回の `read` で送ったレコード数 |
| `remaining` | まだ送っていない残り |
| `last_error` | 直近で断ったコマンドの理由（例 `"unknown cmd"`）。なければ `null` |

**`last_error` は `read` を受け付けた時点で `null` に戻す。** 残したままにすると、
前回断ったコマンドの理由が健全な転送中も表示され続け、**成功した同期が失敗に見える。**

**`sent` と `remaining` は目安であって、正確な数を約束しない。**
**転送が終わったかどうかを `status` で判定しない。完了の印は EOT だけ**（下の「転送の約束」）。
`status` を完了判定に使おうとすると、`read` を書いた直後のまだ `idle` な一瞬や、
中断したあとの `idle` と区別がつかず、**0件で成功したことになる。**

### ペイロードの形

**エンコーディングは JSON（UTF-8）。** MessagePack や独自バイナリの方が小さいが、
片側が Python・片側が TypeScript で担当も分かれるため、**目で見て食い違いが分かること**を優先する。
転送するのは走行ログ数千件程度で、サイズが問題になる規模ではない。足りなくなったら圧縮を足す。

レコードは**エンベロープだけをここで決める**。中身（`body`）はメッシュ（#6）と検知（#8）が決まってから確定する。

```json
{ "seq": 1201, "type": "ride", "t": 1756123456789, "body": { } }
```

| 項目 | 内容 |
| --- | --- |
| `seq` | レコード番号。`log_id` の中で 1 から単調増加する。転送の位置と取り込みの一意キーを兼ねる |
| `type` | `"ride"`（走行ログ） / `"detect"`（検知ログ）。増える可能性がある |
| `t` | UTC のミリ秒。**常に入る** |
| `body` | 種別ごとの中身。未確定（#6 / #8） |

**`t` が常に入るのは、測位できるまでレコードを作らないため。** Zero W に RTC はなく、
電源を入れた直後は正しい時刻を知らない。時刻は **GPS から得るものだけ**とし、モバイルから合わせない。

**測位していない間はレコードを作らない。** 位置が無ければ検知も走行ログも成立しないので、
**捨てているのは中身のないレコードだけ**。こうすると `t` が `null` のレコードが存在しなくなり、
時刻が無いレコードの並べ方（起動ごとの経過時間や起動 ID）を決めずに済む。
**屋内のデモでは測位できずログが1件も出ない。** シミュレータが位置と時刻を流す前提で見せること。

**一意キーは `seq` に持たせる**（`(device_id, log_id, seq)`）。レコード側に別の ID を振らない。
`log_id` を作り直すと `seq` は 1 から振り直されるが、キーに `log_id` が入っているので
前の世代とは別のレコードとして積まれる。

### 転送の約束

**ここに書くのは「守らないと片方の実装が壊れること」だけ。**
どう流すか（送信の間隔、タイムアウトの長さ、何回やり直すか、失敗をどう見せるか）は
**それぞれの実装が決めてよい。** 決めごとを増やすほど、噛み合わない場合が増える。

1. **`read` を受けた時点の `latest_seq` を控え、そこを送り終えるか追い越したら EOT を送る。**
   途中で止まって確認を待たない。送るものが0件でも EOT を送る。
   **「持っているぶん全部」にしない。** 同期中も走行は続き、検知が発火すればレコードは増えるので、
   **終わりが来ないまま流し続けることになる**（EOT が出ないので、セントラルは永久に未完了と見なす）。
   転送中に増えたぶんは次の `read` で送る。
   控えたレコード自体が溢れて消えることがあるので、**「追い越したら」も終わりの条件に入れる。**
2. **完了の印は EOT だけ。** EOT を受け取らずに終わった転送（切断、`stop`、取り込みの失敗）は
   **すべて未完了**として扱う。
3. **未完了なら、次に `since` から取り直す。取り直しは何度でも安全**
   （一意キーで冪等に取り込むため。下の「転送済みログの扱い」）。
   **だから、うまくいかないときは「やり直す」でよい。**
4. **アプリ層で再送やウィンドウ制御を作らない。** BLE は接続している間、
   リンク層で再送と順序保証を行う。二重に作ると噛み合わず、
   **双方が相手を待って止まる形になりやすい。**
   この前提は `docs/unverified.md` の 14 で確認する。
5. **`seq` が飛んでいたら、`stop` を書いて `idle` に戻してから、`since` を飛びの手前に戻して
   1回だけ取り直す。** 飛びは転送の最中に見つかるので、`stop` を挟まないと
   **`sending` 中の `read` として断られる**（上の `control`）。
   それでも同じところで飛ぶなら、**欠損として記録して先へ進む。**
   飛びの原因はリングバッファからの溢れ（もう無い）と通信の取りこぼし（まだ有る）の2つあるが、
   **1回取り直せば、原因を見分けなくても取れるものは取れる。**
   **既読位置は必ず前に進める。** 飛びの手前で止め続けると、
   **一度でも溢れた端末とは二度と同期できなくなる**（毎回同じ位置で飛ぶため）。
6. **MTU に依存しない。** デバイスはネゴシエートされた MTU を BlueZ から取得し
   （`GattCharacteristic1` の `MTU` プロパティ。**BlueZ 5.62 以降が要る**。
   Bookworm の 5.66 は満たすが、Bullseye の 5.55 では取れない）、
   Notify 1パケットを `MTU - 3` バイト以内に切る。セントラルは MTU を前提にした組み立てをしない。
7. **ネゴシエートされた MTU が 64 未満なら転送しない。** 既定の MTU 23 では ATT の Write に
   20 バイトしか載らず、`{"cmd":"read","since":1200}`（27 バイト）が書けない。
   遅くなるのではなく**成立しない**ので、黙って続けずエラーとして見せる。
8. **デバイスの `ReadValue` は `options` の `offset` を必ず尊重する**（値を `offset` 以降でスライスして返す）。
   無視して毎回先頭から返すと、**セントラルは先頭 `MTU - 1` バイトが繰り返された壊れた JSON を受け取る。**

### 転送済みログの扱い

**デバイスはログを消さない。** モバイル側が「どこまで受け取ったか」を持つ。

- **`seq` は再起動をまたいで続く。** `log_id` が同じ間は 1 から単調増加し、
  電源を切っても振り直さない（次の番号もファイルに保存する）。
  **保存はレコードを書く前に行う。** 走行中に電源が落ちる前提の装置なので、
  順序を逆にすると**次の起動が同じ番号を別のレコードに振る。**
  一意キーが衝突し、上書きの規則によって**実在するレコードが黙って消える。**
  先に保存すれば、落ちたときに番号が飛ぶだけで済む（飛びは規則5で扱える）。
- デバイスは**容量上限のリングバッファ**として保持する（上限を超えたら古いものから捨てる。上限値は設定で決める）。
  捨てても `seq` は戻らず、`oldest_seq` が上がるだけ。
- ログを消した・失った・`seq` を振り直したときは、**デバイスは `log_id` を作り直す**。
- **モバイルが保存するのは `(device_id, log_id, どこまで取り込んだかの seq)` の1組だけ。**
  次回はここから `since` で再開する。
- **進めてよいのは、取り込みを終えたところまで。** 受け取った端から位置だけ進めると、
  アプリが落ちたときに**デバイスはまだ持っているのに二度と取りに行けなくなる。**
- **`log_id` が前回と違えば、保存済みの `seq` は捨てて `since` なしで全件取り直す。**
  `latest_seq` の大小では判断しない（振り直された側の番号が大きいこともあり、それだと取りこぼす）。
- **取り込みの一意キーは `(device_id, log_id, seq)`。** 同じキーが再び届いたら**上書きする**
  （増やしてはいけない）。**`log_id` をキーに入れるのは、世代が変わると `seq` が 1 に戻るため。**
  入れずに `(device_id, seq)` にすると、作り直した世代の 1 番が前の世代の 1 番を潰す。
- **重複は正常に起こる。** 途中で切れて `since` から取り直せば、同じ区間がもう一度流れてくる。
  同じキーで上書きされるだけなので、何度取り直しても二重に積まれない。

デバイス側で消す方式にしなかったのは、**取り込みに失敗したときに元に戻せなくなる**ため。
デモ中に同じログを何度でも取り直せることを優先した。

### ペアリング・認証

**ペアリングしない。** BLE のリンク層の暗号化・認証を使わず、**誰でも接続して読み書きできる。**
Characteristic に暗号化のフラグ（`encrypt-read` / `encrypt-write` / `encrypt-notify`）を付けない。

| Characteristic | 付けるフラグ |
| --- | --- |
| `device-info` | `read` |
| `control` | `write` |
| `log` | `notify` |
| `status` | `read`, `notify` |
| `config` | **実体を作るとき（#33）に決める。今は作らない** |

#### なぜ外したか

**ハッカソンの期間内では、守ることより動くことを優先する。**

ペアリングを入れると、**動かなくなる要因の方が増える**。初回は購読が
`GATT_INSUFFICIENT_AUTHENTICATION` で失敗するのでボンド完了を待って張り直す処理が要り、
ボンドを受け付ける窓（`Pairable` のタイマー）を作る必要があり、
**片側だけペア設定を解除すると `/var/lib/bluetooth` を手で消すまで直らない**。
デモ当日にこれが起きると復旧に時間を取られる。

**今この経路で書けるのは `read` / `stop` だけ**で、他人に書かれても
勝手に転送が始まる程度の害しかない。検知を無効化できる `config` はまだ作らない。

#### 割り切っていること

- **近くにいる誰でも、汎用の BLE アプリで走行ログ（位置情報）を読める。**
- **常時アドバタイズし、名前と `device-info` に固定の `device_id` が出る**ので、
  **特定の自転車がいつどこにいたかを記録できる**。これも持ち主の位置情報にほかならない。
- **この経路に秘密値を流さない。** API トークンや Wi-Fi の PSK を `control` で書き込む設計にしないこと。

実利用に出すなら、ペアリング必須化・Characteristic への暗号化要求・
アドバタイズする識別子を定期的に変えること（Resolvable Private Address）が要る。**やらないと決めただけで、
要らないわけではない。**

#### `config`（#33）を作るときは、ここを決め直す

**設定を書き込める経路を開けると、他人にしきい値を書き換えられ、検知を無効化できる。**
危険を知らせる装置としてそれは成立しないので、**`config` の実体を作るときにペアリングを戻すかどうかを
必ず判断すること**（この節を「決めたから終わり」として素通りしない）。

戻す場合に要るのは3つ。**GATT の構造は変わらない。**

- Zero W の BlueZ に Agent を `NoInputNoOutput` で登録する（Just Works を無人で受けるため）。
- `device-info` 以外に暗号化フラグを付ける。**Notify は `encrypt-read` では効かず `encrypt-notify`**
  （`log` は `read` プロパティを持たないため。付け間違えると CCCD が保護されず、ボンドなしで購読できる）。
- モバイルはボンド完了（`ACTION_BOND_STATE_CHANGED`）を待って購読を張り直す。

なお **Zero W の Bluetooth は 4.1 で LE Secure Connections（4.2 以降）が使えない**ため、
戻したとしても Just Works になり、**中間者攻撃には守られない**。防げるのは
「ボンドしていない端末からの読み書き」まで。

#### 書き込みを受ける側の約束

**ペアリングの有無と関係なく、「何を書かれるか」は受け取る側で検証する。**

- 知らないコマンド・知らないキーは**無視する**（落ちない）。
- 数値は範囲を検証してから採用する。**範囲外は捨てて `status` の `last_error` に載せる。**
  **`state` は変えない**（不正なコマンドが1つ来ても、流れている転送は止めない）。
- 検知のしきい値を無効化する値（極端に大きい距離など）も範囲で弾く。

#### 運用で気をつけること

- **接続を占有されると転送できない。** つなげるセントラルは1台で、BlueZ は接続中アドバタイズを止める。
  デモ会場で他の人のスキャンアプリがつながったままになると、持ち主のスマホが接続できない。
  つながらないときは**まずデバイスを再起動して接続を切る**（原因を探す前にこれを試す）。

## 危険検知アルゴリズム

3つの検知を**別々の担当が並行実装する**ため、これも境界として先に決める。
検知は1つ1ファイルに分け、共通のインターフェースに揃える。4つ目が増えたときの受け口も兼ねる。

インターフェースは未確定（#8）。**これが決まるまで3つの検知（#9 / #10 / #11）は着手できない。**
担当と進捗は各 Issue の assignee を見ること。

検知の結果を**どう人に伝えるか**はここでは決めない。`notifications.md` に分けている。

**ハードウェアに触れないこと。** GPS の読み取りや LED の点灯を検知の中に書くと、開発機（Windows / macOS）で
テストできなくなる。入力を受けて結果を返す純粋な関数として書き、モックデータで pytest を回せる状態を保つ。
