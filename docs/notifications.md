# 通知の設計

- ステータス: **仮**（出し分けを決める作業は [#29](https://github.com/Hashimoto-Teppei/web-iot-makers-challenge-team-c/issues/29)）
- 最終更新: 2026-08-31（判断層がモバイルへ移った。`adr/0006-decision-layer-on-mobile.md`）

検知した危険を**どうやって人に伝えるか**を決める。検知アルゴリズムが増えるほど出力の取り合いになるため、
「何を検知するか」（`interfaces.md`）とは別に、ここで境界を引く。

**判断はスマホ、出力はデバイス**（`adr/0006-decision-layer-on-mobile.md`）。
スマホが `alert` に `warn` を書き、デバイスがそれを出力に割り当てる
（運び方は `interfaces/v2v.md`「デバイスへ渡すもの」）。
**このファイルが決めるのは「何を、どの出力で、どう出すか」**であって、運び方ではない。

**このファイルには決まったことだけを書く。** 未確定の論点は #29 で管理する。

## 決まっていること

### 走行中の通知はデバイス側で完結させる

**走行中にスマホを見る行為は取り締まり対象。** モバイルアプリの画面を走行中に見る前提の通知は設計として不可。
警告は LED・ブザー・ディスプレイなど、**デバイスに載っている出力だけ**で伝わる形にする。

モバイルアプリは走行前後の確認・振り返りに使う。**走行中に鳴らすものではない。**

### 走行中と停止中で、出せるものが違う

**デバイスのディスプレイにも「ながら運転」の制約がかかる。**
2024年11月施行の改正道路交通法で、自転車の「ながら運転」は**画像表示用装置に表示された画像の注視**も
対象になっている（6か月以下の懲役または10万円以下の罰金、事故を起こせば1年以下／30万円以下。
2026年4月からは青切符の対象）。条文は携帯電話に限らないため、
**ハンドルに付けた自作ディスプレイが対象外である保証はない。**

Worker が集約した情報をデバイスに出せるようになった（`adr/0004-v2v-transport.md`）ことで、
**画面を「読ませるもの」にしてしまう余地ができた。** それはこのプロジェクトが防ごうとしている行為そのものなので、
**速度で出し分ける。**

| 状態 | 出してよいもの |
| --- | --- |
| **走行中** | **警告と、通信断の表示だけ。**一瞥で終わる記号と色。**文章を出さない** |
| **停止中** | Worker から来た情報を出してよい |

**速度が分からないときは「走行中」として扱う。**
速度を持っているのはスマホだけなので、**走行中かどうかの判定もスマホが行い、
`beat` の `mv` として届く**（`interfaces/v2v.md`「デバイスへ渡すもの」）。
**心拍が途切れている間・測位が出ていない間は、止まっているのか走っているのか分からない。**
ここを既定で「停止中」にすると、**通信が切れた瞬間に走行中の画面へ文章が出る。**
防ごうとしている「ながら運転」をこちらから作り込むことになるので、**迷ったら走行中に倒す。**

具体的には、**`link` が `up` で、かつ直近の `beat` の `mv` が偽のときだけ「停止中」**とする。
`up` でなければ、前に受け取った `mv` が残っていても走行中として扱う。
**判定を2か所に持たない**こと。デバイスは受け取った `mv` に従うだけで、
**速度からの判定をデバイス側に作らない**（そもそも速度が届かない）。

「走行中」と「停止中」の境目（速度のしきい値と、切り替えのちらつきを防ぐ幅）は #29 で決める。
**しきい値はスマホ側に置く**（判定する側に置く）。

### 通信断は走行中も出し続ける

**車車間の検知はスマホの中で動き、スマホ経由の通信に依存する**
（`adr/0004-v2v-transport.md` / `0006-decision-layer-on-mobile.md`）。
経路が死んでも、**スマホが落ちても**、**自分だけが静かに警告を受け取れなくなり、
他の全員からは正常に見える。**
**判断そのものが向こう側へ移ったぶん、`0004` の時点より重い。**

- **心拍が途切れている間・測位が届かない間は、その旨を出力に出し続ける**（`interfaces/v2v.md` の `link`）。
- **「スマホが落ちた」と「測位がまだ出ていない」を分けて見せる。** どちらも検知は動かないが、
  **人がすべきことが違う**（前者は端末を確認する、後者は待つか屋外に出る）。
  同じ表示にすると、待てば直るものと直らないものが区別できない。
- **一度きりの通知にしない。** 見逃した人はそのまま走り続ける。
- **これは警告ではない**（危険が起きたわけではない）。警告の優先順位を奪わない形で、
  常時見える場所に置く。**上の表で走行中に出してよい例外にしているのはこのため。**
- **デバイスの後方物体検知は通信断でも動く**ので、そちらの警告は止めない。

### ディスプレイは 16×2 のキャラクタ LCD を前提に設計する

**部品そのものは未確定**（#13。`hardware.md` の「搭載するモジュール」が正本で、そこでは「未定」）。
**決まっているのは「16×2 のキャラクタ LCD を前提に設計する」ことと、下の「固定して割り当てる」ことだけ。**

部品が決まる前にここへ書くのは、**この前提が文言の設計を縛るから**である。
**もし OLED や LED だけに落ち着いたら、下の「漢字が出せない」の結論は消える**
（固定割り当ての方は、どの出力でも成立するので残る）。

**表示できるのは英数字と半角カタカナだけで、32文字。**
16×2 のキャラクタ LCD は HD44780 互換が大半で、内蔵フォント（A00 ROM）に**漢字は無い**。
カスタム文字は 5×8 ドットで8文字まで登録できるが、**それで漢字を読める形にするのは無理がある。**

**したがって「止まれ」は漢字で出せない。** `トマレ` か `STOP` になる。
**実装を始める前にこれを知らないと、フォントを探して時間を溶かす。**

**上下段に役割を固定して割り当てる。**

一瞥で読めることの条件は、文字が大きいことではなく**毎回同じ場所に出ること**である。
出る場所が変わると、**探すために画面を見続けることになり**、それがこのファイルが避けようとしている
「注視」そのものになる。

**上段と下段に何を割り当てるか、その中身は未確定**（#29）。
**決まっているのは「固定して割り当てる」ことだけ**で、
**実装のたびに空いている行へ出す、という書き方をしない。**

**上段に出せるのは同時に1つだけ。** 一時停止が近いこと（#27）と後方の物体（#26）が同時に起きうるので、
**優先順位を先に決める必要がある**（#29）。決めないと、**実装した人の書き順で勝った方が出る。**

### 出力を2系統に分ける

向き先が違うものを1つの仕組みで扱うと、優先順位の議論が噛み合わなくなる。**混ぜない。**

| 系統 | 向き先 | 例 | 性質 |
| --- | --- | --- | --- |
| **警告** | 乗っている本人 | 急接近（#9）・急ブレーキ（#10）・対向車（#11）・**一時停止の事前通知**・後方物体（#26） | 危険が起きたときだけ出る。複数が競合する |
| **表示** | 周囲の人・車 | ウインカー（#24）・ブレーキランプ（#25） | 本人の操作や動作に連動する。競合しない |

**表示は警告の優先順位に関与しない。** ウインカーが点いている間も警告は出るし、逆も同じ。

### 調停はハードウェアに触らない場所に置く

複数の警告が同時に出たときに「結局どれをどう出すか」を決める処理は、
**発火中の警告のリストを受け取って出力の指示を返す関数**として書く（`src/device/notify.py`）。
**これはデバイス側に残る。** 判断はスマホへ移ったが（`adr/0006-decision-layer-on-mobile.md`）、
**出力を持っているのはデバイス**であり、後方物体検知の警告もここで合流する。
スマホから届くのは「何が起きたか」（`warn` の `kind`）までで、
**どの出力に割り当てるかはデバイスが決める。**

LED を直接叩く形で書くと、開発機（Windows / macOS）で確かめられなくなる。
出し分けは**誤ると人が気づけない**部分なので、モックだけでテストできる状態を保つ。

## 未確定

- **16×2 の上段・下段に何を割り当てるか**（固定割り当てにすることは決定済み。中身が未確定）。
  **部品が 16×2 の LCD に確定していないこと自体が #13**
- **`warn` の `kind` の一覧と、`lv`（強さ 1〜3）の意味**。スマホ側と揃える必要がある

出力の部品自体が未確定（#13）だが、**「どういう区別が必要か」は部品が決まる前に決められる。**
先に区別を決めておけば、部品が決まった時点で割り当てるだけで済む。
