# 通知の設計

- ステータス: **仮**（出し分けを決める作業は [#29](https://github.com/Hashimoto-Teppei/web-iot-makers-challenge-team-c/issues/29)）
- 最終更新: 2026-08-24

検知した危険を**どうやって人に伝えるか**を決める。検知アルゴリズムが増えるほど出力の取り合いになるため、
「何を検知するか」（`interfaces.md`）とは別に、ここで境界を引く。

**このファイルには決まったことだけを書く。** 未確定の論点は #29 で管理する。

## 決まっていること

### 走行中の通知はデバイス側で完結させる

**走行中にスマホを見る行為は取り締まり対象。** モバイルアプリの画面を走行中に見る前提の通知は設計として不可。
警告は LED・ブザー・ディスプレイなど、**デバイスに載っている出力だけ**で伝わる形にする。

モバイルアプリは走行前後の確認・振り返りに使う。**走行中に鳴らすものではない。**

### 走行中と停止中で、出せるものが違う

**デバイスのディスプレイにも「ながら運転」の制約がかかる。**
2024年11月施行の改正道路交通法で、自転車の「ながら運転」は**画像表示用装置に表示された画像の注視**も
対象になっている（6か月以下の懲役または10万円以下の罰金、事故を起こせば1年以下／30万円以下。
2026年4月からは青切符の対象）。条文は携帯電話に限らないため、
**ハンドルに付けた自作ディスプレイが対象外である保証はない。**

Worker が集約した情報をデバイスに出せるようになった（`adr/0004-v2v-transport.md`）ことで、
**画面を「読ませるもの」にしてしまう余地ができた。** それはこのプロジェクトが防ごうとしている行為そのものなので、
**速度で出し分ける。**

| 状態 | 出してよいもの |
| --- | --- |
| **走行中** | **警告と、通信断の表示だけ。**一瞥で終わる記号と色。**文章を出さない** |
| **停止中** | Worker から来た情報を出してよい |

**速度が分からないときは「走行中」として扱う。**
速度はスマホから届く `self` にしか入っていないので（`interfaces.md`）、
**通信が切れている間・測位が出ていない間は、止まっているのか走っているのか判断できない。**
ここを既定で「停止中」にすると、**通信が切れた瞬間に走行中の画面へ文章が出る。**
防ごうとしている「ながら運転」をこちらから作り込むことになるので、**迷ったら走行中に倒す。**

具体的には、**`link` が `up` の間だけ「停止中」になりうる**とする（`interfaces.md`）。
`up` でなければ、速度の値が残っていても走行中として扱う。
**「受け取れているか」ではなく `link` を見る**こと。判定を2か所に持つと、
表示とデバイスの内部状態が食い違う。

「走行中」と「停止中」の境目（速度のしきい値と、切り替えのちらつきを防ぐ幅）は #29 で決める。

### 通信断は走行中も出し続ける

**車車間の検知はスマホ経由の通信に依存する**（`adr/0004-v2v-transport.md`）。
経路が死んでも**自分だけが静かに警告を受け取れなくなり、他の全員からは正常に見える。**

- **測位が届かない間は、その旨を出力に出し続ける**（`interfaces.md` の `link`）。
- **「経路が死んだ」と「測位がまだ出ていない」を分けて見せる。** どちらも検知は動かないが、
  **人がすべきことが違う**（前者は端末を確認する、後者は待つか屋外に出る）。
  同じ表示にすると、待てば直るものと直らないものが区別できない。
- **一度きりの通知にしない。** 見逃した人はそのまま走り続ける。
- **これは警告ではない**（危険が起きたわけではない）。警告の優先順位を奪わない形で、
  常時見える場所に置く。**上の表で走行中に出してよい例外にしているのはこのため。**
- **センサーによるローカル検知は通信断でも動く**ので、そちらの警告は止めない。

### 出力を2系統に分ける

向き先が違うものを1つの仕組みで扱うと、優先順位の議論が噛み合わなくなる。**混ぜない。**

| 系統 | 向き先 | 例 | 性質 |
| --- | --- | --- | --- |
| **警告** | 乗っている本人 | 急接近（#9）・急ブレーキ（#10）・対向車（#11）・後方接近（#26 アイデア）・一時停止（#27 アイデア） | 危険が起きたときだけ出る。複数が競合する |
| **表示** | 周囲の人・車 | ウインカー（#24）・ブレーキランプ（#25） | 本人の操作や動作に連動する。競合しない |

**表示は警告の優先順位に関与しない。** ウインカーが点いている間も警告は出るし、逆も同じ。

### 調停はハードウェアに触らない場所に置く

複数の警告が同時に出たときに「結局どれをどう出すか」を決める処理は、
**発火中の警告のリストを受け取って出力の指示を返す関数**として書く（`src/device/notify.py`）。

LED を直接叩く形で書くと、開発機（Windows / macOS）で確かめられなくなる。
出し分けは**誤ると人が気づけない**部分なので、モックだけでテストできる状態を保つ。

## 未確定

以下は #29 で決める。決まったらこの節を表に置き換える。

- どの警告をどの出力（LED / ブザー / ディスプレイ / 振動）で出すか
- 同時に発生したときの優先順位。重ねるのか、1つに絞るのか
- 出し続ける時間と、止まる条件
- 同じ警告が繰り返されたときの抑制
- 音や光の違いだけで意味が区別できるか
- 「走行中」と「停止中」を分ける速度のしきい値と、境目でのちらつきの防ぎ方
- 通信断をどの出力で常時見せるか（警告と取り合わない置き方）

出力の部品自体が未確定（#13）だが、**「どういう区別が必要か」は部品が決まる前に決められる。**
先に区別を決めておけば、部品が決まった時点で割り当てるだけで済む。
