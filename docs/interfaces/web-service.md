# 蓄積したデータの見せ方（Web サービス）

走行後に集まったデータを、**どこが危ないかが一目で分かる形**にして公開する。
`../interfaces.md` から分割した。**境界の一覧は [`../interfaces.md`](../interfaces.md)。**

**このファイルには決まったことだけを書く。** **#7 で残っていた論点は全部決まった**
（2026-09-01。しきい値の既定値・端末の識別・再計算の経路・場所の見せ方）。
**既定値は暫定で、実データを見て動かすもの**である——動かすことを見越して設定に外へ出してあるので、
**変えるときにこのファイルの決定を覆す必要はない**（数字だけを直す）。

## 言葉

**この4つを混ぜない。** 混ざると、集計の話とリアルタイムの話が同じ言葉で語られて噛み合わなくなる。

| 言葉 | 意味 | 誰が作るか |
| --- | --- | --- |
| **検知** | 走行中にその場で発火した警告。急接近・急ブレーキ・対向車・一時停止の事前通知・後方物体 | **スマホ**（前4つ）と**デバイス**（後方物体） |
| **不停止** | **走行ログと標識を突き合わせて、あとから計算した**「一時停止の標識に従わなかった」という判定 | **Worker**（走行後） |
| **セル** | 地図を区切った升目。集計の単位 | Worker |
| **通過** | ある走行がセルに入ったこと。**率の分母**（回数ではなく**走行の数**で数える） | Worker（走行ログから数える） |

**「違反」という言葉をこのファイルでは使わない。**
`README.md` と `CLAUDE.md` の「違反」は**交通ルール違反全般**を指す既存の語で、
一時停止に限らない。**同じ語を狭い意味で再定義すると、どちらの意味か読み手に分からなくなる。**
ここで扱うのは一時停止だけなので、**不停止**と呼ぶ。

**「セル」も他の場所で使われている。** `../adr/0005-realtime-transport.md` は
**Durable Object を地理で分割する話**として同じ語を使い、**そちらは採らないと決めている**
（境界をまたいだ自転車が互いに見えなくなるため）。
**ここで言うセルは走行後の集計の升目**で、リアルタイムの経路とは何の関係もない。
**混同すると「集計をセルで切るなら DO もセルで切れるのでは」という誤解が生まれる。**

### 検知と不停止は別物である

同じ交差点を指していても、出どころも、作られる時刻も、**あとから作り直せるかどうかも違う。**

- **検知は端末側で確定している。** しきい値を変えても、**過去のデータは変わらない。**
- **不停止はサーバーが持っている生ログから何度でも計算し直せる。**
  「何 km/h 以下なら停止と見なすか」を、データを集め直さずに変えられる
  （`../adr/0007-keep-raw-ride-logs.md`）。

**この2つを1つのテーブルに混ぜると、後者の利点が消える**——
どのしきい値で作られた行なのかが分からなくなり、作り直せなくなる。
表も、地図のレイヤーも、最初から分けておく。

## 集計

### セルの切り方

**緯度と経度を小数第3位で切り捨てる。**

- **切り捨てで統一する。** 四捨五入と混ぜると**セルの境界が半セルずれ**、
  地図の円・ランキング・詳細画面が別のセルを指す
- 大きさは岡山（北緯 34.6°）で**南北およそ 111m × 東西およそ 92m**。
  **正方形ではない**（経度の間隔は緯度によって縮む）。円で描くので実害は無いが、
  「110m 四方」と書かない

**GPS の誤差が数 m ある**ので、これより細かく切ると**同じ交差点の検知が隣のセルに割れる。**
逆に粗くすると、交差点と、その手前の直線が同じ升目に入る。
**「交差点1つがだいたい1つのセルに収まる」大きさ**を狙っている。

**升目の境界に交差点が乗る問題は解けない。** ハッカソンの範囲では受け入れる
（解くなら、点の集まりから中心を求める方式に変えることになる）。

### 率で見る

**件数をそのまま並べると、交通量の多い道が上位に来るだけになる。**
知りたいのは「そこを通ると危ない確率」なので、**通過で割る。**

```
率 = そのセルで1件以上あった走行の数 ÷ そのセルを通った走行の数
```

**分子も分母も「走行の数」で数える。件数で数えない。**

**分子を件数にすると 100% を超える。** 後方物体検知のように**連続して発火するもの**があるため、
1回の走行が同じセルで何件も出しうる。
**8秒滞在して8件出たセル（800%）が、100走行のうち5走行で危険が出たセル（5%）を必ず上回る**——
順位が「危ない確率」ではなく「そこで何秒詰まったか」の順位になる。

**分母は追加のデータを必要としない。** 走行ログは測位の連続点なので、
**そのセルに入った走行を数えれば通過になる。**

**通過が少ないセルは順位に出さない。** 1回しか通っていない場所で1件出れば率は 100% になり、
**ランキングの上位が「1回しか通っていない場所」で埋まる。**
**下限を設定として外に出す**（コードに直書きしない。実データを見て調整する）。
**既定は5走行**（下の「しきい値の既定値」）。

**指標を件数に変えることはいつでもできる**（生ログが残っているため。
`../adr/0007-keep-raw-ride-logs.md`）。**率で始めるのは、そちらの方が説明として正しいから**であって、
覆せない決定だからではない。

### 集計を配る経路

**`GET /api/stats/cells`。** 上の数え方でセルごとの率を出し、**率の高い順に返す**（実装は
`apps/web/src/worker/stats/`。クエリの一覧は [`../../apps/web/README.md`](../../apps/web/README.md)）。

**マップとランキングは同じ応答を見る**（[`web-ui.md`](./web-ui.md)「マップとランキングを1ページに
並べる理由」）。**2本に分けない**——同じ数字の2つの見せ方なので、経路が2つあるとずれる。

**返すのはセルに丸めたものだけ。** 生の測位点も `device_id` も返さない
（`../adr/0007-keep-raw-ride-logs.md`）。**時刻の次元も持たない**——時間帯の内訳を出すのは
場所の詳細画面（#87）で、そちらだけが時刻を扱う。

**認証を置かない。** 読むだけで、丸めた値しか出さない（下の「割り切っていること」）。

**集計結果のテーブルはまだ無い。** 読むときに走行ログを数えている（下の「テーブル（D1）」）。
**読む量が上限に当たったら 503 を返して落とす**——**途中まで読んで数えると、分母だけが小さい率、
つまり実際より危険に見える順位が出る。**その 503 が、集計表を足す時期が来たという合図である。

### 検知を場所に結びつける

**デバイス発の検知（後方物体）には位置が入っていない。**
デバイスは位置を知らないので、入れられない（`ble-log-transfer.md`）。

**`t`（時刻）で、同じ走行の測位点に突き合わせてセルを決める。**

- **`t_est` が立っている検知を、実測の時刻と同じに扱わない。**
  BLE が切れている間、デバイスは**単調時計から推定した時刻**を打つ（`ble-log-transfer.md`）。
  切断が長いほどずれ、**ずれた時刻に一番近い点＝別のセル**に積まれる。
  **`t_est` の検知は、地図とランキングの集計から除く**（詳細画面には出してよい）
- **突き合わせる点が見つからない検知を、黙って捨てない。**
  BLE は生きているが測位が出ていない（`nofix`）間の検知がこれに当たる。
  **「場所不明」として数だけ残す**——捨てると、**集計に出ていないことが「起きていない」に見える**
- **スマホ発の検知には位置が入っている**ので、この突き合わせは要らない

### 不停止の判定

**走行ログの点列と、一時停止の標識の位置を突き合わせる。**

- 標識の手前を通ったか
- そのとき**速度が停止と見なせる値を下回った瞬間があったか**

**進入方向も見る。** 標識は方向ごとに1行になっており（`mobile-api.md`「進入方向を一緒に配る」）、
**その方向から入った走行だけを対象にする。**
**走行の側の方角は、測位点の並びから出す**——`ride_points` に入っている端末の方角を使わない。
**方角の無い測位が `0`（真北）として入っている**ことがあり（`../unverified.md` 57）、
**それを信じると、東西に走った不停止が北向きの標識に付く。** 見ないと、**対向車線や交差する道路を走っただけで
不停止と判定される**——一時停止の事前通知（#27）が進入方向を見るのと同じ理由が、
**あとから計算する側にもそのまま当てはまる。**

**走行の方角は「半径に入る手前の点」から「標識に一番近づいた点」へ引く**（決定済み・2026-09-02）。
**止まっている間の点だけで方角を出すと、数十 cm のゆらぎがそのまま方角になる**ため、
**方角が意味を持つ最小の距離（5m）だけ離れた点までさかのぼる。**
**さかのぼる範囲は距離で切る**ので、**周回して同じ標識を2度通っても前の周まで戻らない。**
**それだけ離れた点が見つからなければ、その通過は判定しない**——**見逃す側に倒す。**

**進入方向が登録されていない標識（`approach` が `null`）は対象にしない**（決定済み・2026-09-02）。
**`null` は「全方向が対象」ではなく「元データに登録が無い」**（`stop-signs-source.md`）。
**向きを確かめずに不停止にすると、対向車線を走っただけで濡れ衣になる。**

**精度の悪い測位点は判定から外す**（決定済み・2026-09-02）。**しきい値の1つとして受け取る。**
**取り込みは足切りをしない**（下の「1回の送信は分割してよい」）ので、**切るのはここだけ**である。

**1回の走行が同じ標識を2度通れば2件になる**（周回すれば起こる）。
`stop_violations` が代理キーを持つのはこのため（下の「テーブル（D1）」）。

**しきい値（速度・標識からの距離・進入方向のずれ・測位精度）は設定として外に出す。**
**サーバー側で持つ意味は、あとから変えて計算し直せること**にある。埋め込むとその利点が消える。
既定値は下の「しきい値の既定値」。

**「止まった」の判定は完璧にはならない。** 測位が 1Hz なので、
**1秒より短い停止は点として現れない**（`../unverified.md` 34）。**未確認の前提として扱う。**
**速度が跳ねた点は濡れ衣を作らない**——**1点でも下回っていれば止まったと見なす**ので、
悪い測位が高い速度を出しても、止まった点が残っていれば不停止にならない。

### いつ計算するか

**取り込みのリクエストの中で計算しない**（下）。
**再計算は `POST /api/admin/recompute` で起こす**（決定済み・2026-09-01）。

**スクリプトではなく Worker のエンドポイントにする。**
不停止の判定は D1 の中身を読んで書き戻す処理で、**リモートの D1 を触れるのは Worker から**である
（`wrangler d1 execute --remote` は SQL しか送れず、判定のコードを持ち込めない）。
**手元へ D1 を落として計算し、結果を戻す経路を作るより、動いている Worker に1本足す方が短い。**

**この1本だけは共有トークンで守る**（`ADMIN_TOKEN`。`wrangler secret put` で登録し、
`wrangler.jsonc` に書かない。`CLAUDE.md`）。**下の「割り切っていること」で
書き込みに認証を置かないと決めているのに、ここだけ守るのは、壊せる範囲が違うから**である——
`POST /api/logs` で壊せるのは**足された行だけ**で（1回に数千行入るが、
**既にある行は上書きも削除もできない**）、**再計算は既存の行を丸ごと置き換える。**
**しかも重い。**誰でも叩ければ、**それだけで D1 の読み取りを使い切れる。**

**しきい値はリクエストで渡す。** サーバーに固定値を持たず、**その場で数字を変えて叩き直せる形にする。**

**しきい値を変えて何度でも走らせられることが、この設計の目的そのもの**である
（`../adr/0007-keep-raw-ride-logs.md`）。
**取り込みに埋め込むと、過去ぶんを作り直せなくなる。**

**同じ走行を再計算したら、その走行ぶんの行を置き換える**（積み増さない）。
**不停止が0件になった走行も対象にする**——消さずに終えると、
**しきい値を厳しくしても前回の行が残り続ける。**

**経路の形**（実装は `apps/web/src/worker/recompute/`）。

| | |
| --- | --- |
| リクエスト | `{ "thresholds": { "stopSpeedMps", "radiusM", "bearingToleranceDeg", "maxHaccM" }, "rides": [{ "deviceId", "logId" }], "skip": 0 }` |
| `thresholds` | **4つとも必須。** 省略を許すと、**「その数字を選んだ結果」と「省略した結果」が区別できない** |
| `rides` | **省略すると古い順に上限（20走行）ぶん。** 明示して上限を超えたら **400 を返して1行も触らない**——途中まで作り直すと、**どこまで置き換わったか呼んだ側に分からない**。**同じ走行を2度書いても1度しか計算しない** |
| `skip` | **`rides` を省略したときだけ意味を持つ**（併用は 400）。**上限を超えた走行を突き返さないためにある**——走行は増え続けるので、**突き返すだけだと 21 本目が入った時点で「全走行」の経路が永久に使えなくなる。しかも、どの走行があるかを知る API が無い** |
| 認証 | `Authorization: Bearer <ADMIN_TOKEN>`。**検証より先に見る**（形が合っていることを持たない相手に教えない） |
| 応答 | `200` と `{ "computed": { "rides", "points", "violations", "more" }, "thresholds" }`。**しきい値を返す**ので、叩き直しながら数字を詰めても取り違えない。**`more` が `false` になるまで `skip` を上限ずつ足して叩く**——無いと、**ちょうど上限ぶんで終わったのか続きがあるのかが区別できない** |
| 失敗 | `401`（トークンが無い / 違う）/ `503`（**`ADMIN_TOKEN` が未設定**）/ `400`（形が違う・`rides` が多すぎる・`rides` と `skip` の併用） |

**未設定を 401 にしない。** 空の秘密値を「認証なし」として扱うと、
**設定を忘れたデプロイが誰でも叩ける口になる**ので通さないが、**401 で返すと
正しいトークンを探して延々と試すことになる。**

### しきい値の既定値

**全部が暫定である**（`../unverified.md` 64・65）。**実走行のログを1回でも取れば動かす前提**なので、
**この表の数字を根拠に何かを設計しない。**

| 設定 | 既定 | 何に効くか |
| --- | --- | --- |
| 停止と見なす速度 | **1.5 m/s**（≒5.4 km/h） | 不停止の判定 |
| 標識から見る距離 | **20m** | 不停止の判定 |
| 進入方向のずれ | **60°** まで | 不停止の判定 |
| 判定から外す測位精度 | **30m** より悪いもの | 不停止の判定 |
| 順位に出す通過の下限 | **5走行** | ランキング |

- **速度を 0 にしない。** 1Hz の測位は止まっていても数十 cm/s のゆらぎを出すので、
  **0 を条件にすると誰も停止したことにならない。**歩く速度（約 1.4 m/s）より少し上に置いてある
- **距離の 20m は、規制地点が停止線とは限らないため**である。交差点中央部のこともあり
  （`../unverified.md` 62）、**その差は実測で中央値 20.8m**（規制地点↔進入方向）。
  **停止線ぴったりを狙うと、中央部に登録された標識で全員が不停止になる**
- **進入方向の 60° は広めに取ってある。** 点の並びから出す方角にはゆらぎがあり、
  **狭くすると本当の不停止を落とす。**
  ここは**見逃す側に倒す**——**濡れ衣を着せる方が悪い**という判断であって、精度の話ではない
- **測位精度の 30m は、市街地で GNSS が出す値の幅から置いた暫定値**である
  （`../unverified.md` 71）。**厳しくすると、ビルの谷間の交差点が丸ごと判定から消える**
  ——そこは一番見たい場所でもある。**緩めると、20m の半径が精度の中に埋もれる**
- **通過の下限 5走行は、走る人が数人しかいない規模に合わせた値**である。
  上げるとランキングが空になり、下げると1回しか通っていない場所で埋まる

## データの取り込み

**`POST /api/logs`。** スマホが走行後にまとめて送る。**配列で送る**（1件ずつだと往復が増える）。

**実在するエンドポイントはすべて `/api` 接頭辞を持つ**（`/api/health` / `/api/pings` /
`/api/stop-signs` / `/api/v2v/exchange`）。**ここだけ `POST /logs` と書いていたので揃えた**
（2026-09-01。実装は #80）。

**出どころが2つある**（`mobile-api.md`「走行後の同期」が正本）。

| 何を | どこから | `source` |
| --- | --- | --- |
| 走行ログ（測位の連続点）とスマホ発の検知 | スマホ自身 | `phone` |
| デバイス発の検知（後方物体） | デバイス → BLE → スマホ | `device` |

**一意キーは `(device_id, source, log_id, seq)`。**

**`source` をキーに入れるのは、名前空間が衝突するため。**
スマホは自分で `log_id` と `seq` を作るが、`device_id` はデバイスのものを使う
（`mobile-api.md`）。**入れないと、デバイスの `log_id=1, seq=1` とスマホの `log_id=1, seq=1` が
同じキーになり、片方が黙って消える。**

**同じキーが既にあるレコードは、上書きせず無視する。**

- **冪等でないと集計が嘘になる。** BLE の転送は途中で切れて取り直すことがあり、
  **重複は例外ではなく通常運転**である。数え直すたびに件数が増えるようでは、率も順位も意味を持たない
- **上書きにしないのは、認証を持たないため。** `device_id` を知った誰かが、
  **同じキーで空のレコードを投げて他人の走行を消せてしまう。**
  レコードは追記だけの記録なので、**上書きが要る場面がそもそも無い**

**このリクエストの中で重い集計をしない。** 不停止の計算も、集計表の更新もしない。
**取り込みが遅いと、スマホ側がリトライを繰り返して重複が増える。**

### 1回の送信は分割してよい（#80 で決めた）

**1リクエストの件数に上限を置く**（既定は測位点 5,000・検知 2,000・走行 20。
値は `apps/web/src/worker/logs/config.ts`）。**D1 の制限**——1文 100,000 バイト・
1クエリにバインド変数 100 個・**1回の呼び出しで 50 クエリ**（無料プラン）——から逆算した数字で、
**好みで決めた値ではない。長い走行はスマホ側が分割して送る**（冪等なので二重に積まれない）。

- **超えたら 400 を返し、1行も入れない。** 黙って切り詰めると、**送った側は成功したと思い、
  入らなかったぶんは誰にも見えないまま消える**
- **400 は「多すぎる」と「形が違う」を区別して返す**（`code`）。前者は分ければ入り、
  後者は送り直しても通らない。**区別しないと、通らない 400 に送り直しを繰り返す**
- **分割しても、走行の開始と終了は毎回同じ確定値を送る**（**最初の1通が残る**）。
  走行が終わってから送る経路なので1通目で確定している。**あとから延ばせないので、
  期間の外に出た検知は走行に結びつかず、地図にもランキングにも出ない**
- **測位点は、同じリクエストに走行（`rides`）の行があるものだけ受け取る**
  （分割時は毎回その行を一緒に送る）。**どの走行にも属さない点は、通過の分母が走行の数なので
  集計に出ないまま、位置情報だけが D1 に残る**
- **測位の値に上限を置かない**（見るのは緯度経度の範囲と、速度・精度が負でないことだけ）。
  **1点でも弾くと走行が丸ごと上がらず、スマホの手元は変わらないので送り直しても同じところで落ちる。**
  **足切りは計算する側**（上の「不停止の判定」）が、そのときのしきい値で行う
- **推定した時刻（`t_est`）を受け取るのはデバイス発の検知だけ**（打つのはデバイスである。
  `ble-log-transfer.md`）。**スマホ発で立つと、その検知は理由の分からないまま地図と
  ランキングから消える。同じ理由で `kind` も出どころで分ける**——`rear_object` を名乗る
  スマホ発のレコードを受け取らない（`detectors.md`）

## テーブル（D1）

**列の詳細は Drizzle のスキーマが正本。** ここには**なぜその表があるか**だけを書く。

| テーブル | 中身 | なぜ分けるか |
| --- | --- | --- |
| `rides` | 1回の走行。端末・開始と終了 | **走行単位で消せるようにする**（位置情報なので） |
| `ride_points` | 測位の連続点 | **生ログ。** 不停止の再計算と、通過の分母 |
| `detections` | 検知。種別・強さ・時刻・`source`・`t_est` | **端末が確定させたもの。作り直せない** |
| `stop_violations` | 不停止。標識・走行・判定に使ったしきい値 | **サーバーが計算したもの。作り直せる** |
| `stop_signs` | 一時停止の標識。位置・都道府県・版 | 外部データ（下）。**端末へ配る元でもある**（`mobile-api.md`） |

**Drizzle を書くために決めておくことだけを、ここに足す。**列の名前と型は書かない（正本が2つになる）。

- **`rides` の主キーは `(device_id, log_id)`。** スマホが走行ごとに `log_id` を作る
  （`mobile-api.md`「走行後の同期」）ので、**この2つが走行を一意に決める。**
  **サーバー側で別の ID を振らない**——振ると、同じ走行が2回送られたときに
  **同じ走行だと分からないまま2行できる**
- **`ride_points` の一意キーは `(device_id, log_id, seq)`。**
  取り込みの4つのキーから `source` が落ちているのは、**測位点はスマホ発しか無いから**である
  （デバイスは位置を知らない）。**`source` の列も持たない**——`'phone'` しか入らない列は、
  入っていることを確かめる手間だけを増やす
- **`detections` の主キーは `(device_id, source, log_id, seq)` の4つ**（取り込みのキーそのまま）。
  **こちらは `source` が要る**（上の「データの取り込み」）
- **`detections` は走行（`rides`）を指さない。** 外部キーも、`ride_id` の列も持たない。
  **デバイス発の `log_id` は電源を入れ直すと変わり、走行と1対1では対応しない**
  （`ble-log-transfer.md`）。**スマホ発だけ紐づけて、デバイス発は時刻で引く、という形にしない**——
  **同じ表の行が2通りの方法で場所と走行に結びつく**ことになり、集計のクエリが割れる。
  **`(device_id, t)` から `rides` の期間で引く。この規則1つで両方を扱う**
- **`detections` は位置も持たない**（上の「検知を場所に結びつける」）。**スマホ発は位置を知っているが、
  それでも入れない。**入れると、デバイス発だけが `NULL` の列ができ、
  **「位置が無い」と「突き合わせに失敗した」の区別がつかなくなる**
- **`stop_violations` は再計算のたびに作り直す。** 走行ぶんを消してから入れ直す
  （上の「いつ計算するか」）。**追記だけの他の表とは性質が違う**ので、
  **`POST /api/logs` からは絶対に書かない**

### 端末の表を作らない

**`devices` テーブルを持たない。`rides.device_id` に文字列で置くだけにする。**

**端末の登録口も作らない。** `device_id` は BLE のアドバタイズに出ている16進8文字で
（`ble-gatt.md`）、**誰でも名乗れる。**
**登録してあることが何も保証しない以上、登録の手続きは手間だけが残る。**

**端末の名前・持ち主・最終走行日時が要るなら、そのとき作る**
（`CLAUDE.md`「早すぎる抽象化を避ける」）。**いま要るのは、走行を端末ごとに分けることだけ**で、
それは `rides.device_id` で足りている。

**`device_id` を公開の画面に出さない**（`../adr/0007-keep-raw-ride-logs.md`）。表が無くても、
**行には入っている。**

- **`detections` にセルを持たせない。** デバイス発には位置が無く、時刻から引くしかないため
  （上の「検知を場所に結びつける」）。**位置を持つのは `ride_points` だけ**にしておくと、
  突き合わせの規則が1箇所で済む
- **`stop_violations` には判定に使ったしきい値を残す。** 残さないと、
  **どの設定で作られた行なのかが分からなくなり、作り直す判断ができない。**
- **集計結果のテーブルを最初から作らない。** データ量が小さいうちは読むときに集計すれば足りる。
  **遅くなってから足す**（`CLAUDE.md`「早すぎる抽象化を避ける」）。

### サンプルデータは列で見分ける

**デモとスライドのためにサンプルデータを入れる。**
**別のテーブルにせず、同じテーブルに「サンプルかどうか」の列を置く。**

分けると、**画面と集計のクエリが2つに割れる**——本番用とデモ用で別の経路を通ることになり、
**デモで動いたものが本番で動かない**という一番まずい形になる。

**列にしておけば、混ぜて見せることも、除いて見せることもできる。**

**置くのは `rides` と `detections` の2つだけ。** `ride_points` は `rides` を辿れば分かるので持たない
（**同じことを2箇所に持つと、片方だけ立った行ができる**）。
`detections` に要るのは、**それが走行を指していないから**である（上）。

**`POST /api/logs` はこの列を受け取らない。** 常に「サンプルではない」として入れる。
**受け取る形にすると、誰でもサンプルを名乗れる**——サンプルを除いた集計が、
**除いたつもりで除けていない**状態になる。**サンプルを立てられるのは投入スクリプトだけ。**

## 割り切っていること

**書き込み（`POST /api/logs`）にも認証を置かない。**

**これは走行中の中継（`v2v.md`「端末IDとプライバシー」）とは別の割り切りである。**
あちらは **Durable Object のメモリにしか無く、数秒で消える**データだった。
**こちらは永続する D1 の行で、しかも公開ランキングの入力になる。**

- **`device_id` を知った人が、偽の検知を投げて任意の交差点を1位にできる。**
  `device_id` は16進8文字で、BLE のアドバタイズにも出ている（`ble-gatt.md`）
- **他人の走行を消すことはできない**（上書きせず無視するため）
- **偽の位置を送る端末は止められない**

**ハッカソンの範囲では受け入れる。** 実利用に出すなら、
**書き込みだけを共有トークンで守る**（`wrangler secret put`。`wrangler.jsonc` に書かない）ところから。
**その仕組みは既に1本ぶんある**——再計算の経路（上の「いつ計算するか」）が `ADMIN_TOKEN` で
守られているので、**`POST /api/logs` に広げるのは同じやり方をもう一度使うだけ**である。
