# BLE の書き込みの安全と、運用で気をつけること

[`ble-gatt.md`](./ble-gatt.md) から分割した。**GATT の約束（UUID・向き・手順・Characteristic の役割）は
向こうが正本**で、ここには**誰が読み書きできるか**と、そこから来る割り切り・運用上の注意だけを置く。
`ble-gatt.md` が 400 行に達したため切り出した（`../../CLAUDE.md`）。

## ペアリング・認証

**ペアリングしない。** BLE のリンク層の暗号化・認証を使わず、**誰でも接続して読み書きできる。**
Characteristic に暗号化のフラグ（`encrypt-read` / `encrypt-write` / `encrypt-notify`）を付けない。

| Characteristic | 付けるフラグ |
| --- | --- |
| `device-info` | `read` |
| `control` | `write` |
| `log` | `notify` |
| `status` | `read`, `notify` |
| `alert` | `write` |
| `config` | `write` |

### なぜ外したか

**ハッカソンの期間内では、守ることより動くことを優先する。**

ペアリングを入れると、**動かなくなる要因の方が増える**。初回は購読が
`GATT_INSUFFICIENT_AUTHENTICATION` で失敗するのでボンド完了を待って張り直す処理が要り、
ボンドを受け付ける窓（`Pairable` のタイマー）を作る必要があり、
**片側だけペア設定を解除すると `/var/lib/bluetooth` を手で消すまで直らない**。
デモ当日にこれが起きると復旧に時間を取られる。

**書けるのは `control`（`read` / `stop`）と `alert` と `config` の3つ。** `control` は他人に書かれても
勝手に転送が始まる程度の害しかない。**`config` については下の「いまはペアリングを戻していない」。**

**`alert` は他人に書ける。** できることは2つあり、**どちらも「警告を止める」側にも効く。**

- **偽の警告を出させる。** 起きていない危険で鳴らし続けられる。
  **鳴りすぎる警告は無視されるようになる**ので、これは実質的に警告を殺せる。
- **警告を止める。** 接続枠を1つ占有すれば持ち主のスマホがつながらず、警告が1つも届かない。

**「偽の警告は出せるが、止めることはできない」ではない。** 止められる。

**そして、気づけるとも限らない。** 攻撃者が接続枠を取って `beat` を書き続けている間、
デバイスから見れば心拍は届き続けるので **`link` は `up` のまま**になり、
**「スマホとつながっていて、危険が起きていない」という表示になる。**
持ち主のスマホは接続できないので**スマホ側では気づける**が、**デバイスの表示は健全に見える。**
この方式で一番避けたい「静かに壊れる」が、ここには残っている。
**接続枠が1つであることが、そのまま「奪えば止まる」を意味している。**
**`0006` で判断がスマホへ移ったぶん、奪われたときに失うものは増えている。**

走行中に狙って行うのは難しく、**いまは**ペアリングを入れる代償（下）に見合わないと置いている。
**やらないと決めただけで、要らないわけではない。**
**#33 で `config` を作るときに、ここも一緒に見直した**（下の「いまはペアリングを戻していない」）。
**見直した結果も「決着」ではない。戻すかどうかは [#122](https://github.com/Hashimoto-Teppei/web-iot-makers-challenge-team-c/issues/122) で未確定のまま持っている。**

### 割り切っていること

- **近くにいる誰でも、汎用の BLE アプリで検知ログを読める。**
  **`0006` で位置がデバイスから消えたぶん、ここで漏れるものは軽くなった**——
  読めるのは「いつ後方に物体があったか」であって、どこかではない
  （どこかを知るには、スマホ側の走行ログと突き合わせる必要がある）。
  **軽くなっただけで、無くなってはいない。**
- **常時アドバタイズし、名前と `device-info` に固定の `device_id` が出る**ので、
  **特定の自転車がいつどこにいたかを記録できる**。これも持ち主の位置情報にほかならない。
  **こちらは `0006` で軽くならなかった**——固定の ID が電波に出続けること自体が原因なので、
  デバイスが何を持っているかに関係しない。**いま一番重いのはこれ。**
- **この経路に秘密値を流さない。** API トークンや Wi-Fi の PSK を `control` で書き込む設計にしないこと。

実利用に出すなら、ペアリング必須化・Characteristic への暗号化要求・
アドバタイズする識別子を定期的に変えること（Resolvable Private Address）が要る。**やらないと決めただけで、
要らないわけではない。**

### いまはペアリングを戻していない（#33 で確認・2026-09-05）

**戻すかどうかは未確定。**
[#122](https://github.com/Hashimoto-Teppei/web-iot-makers-challenge-team-c/issues/122)
**で持っている。期間内に手が回れば戻す。**

#33 で `config` の実体を作るときに、ここを見直した。**そのとき言えたのは1つだけである。**

> **`config` を足したことによって、新しく増えた危険は無い。**

効いているのは3つで、**3つが揃って初めてこれが言える。**

1. **保存しない。切断で既定へ戻る。** 書き換えは、**書いた側が接続している間しか続かない。**
2. **接続できるセントラルは1台。** つまり**他人が書けている間は、持ち主のスマホがつながっていない。**
   それは下の「運用で気をつけること」の「接続を占有されると検知が動かない」——**すでに警告が1つも届かない状態**である。
3. **範囲を切ってある。** 上書きできるのは保持時間（1000〜10000ms）と心拍のタイムアウト（2〜10秒）だけで、
   **どちらも下端・上端で警告が遅くなるだけ。黙らせる値が範囲に無い。**

**`config` で失えるものは、接続枠を奪えばもう失えるものの部分集合。**

**ただし、これは「ペアリングが要らない」ことの説明ではない。**
**上の「割り切っていること」は、`config` の前からあってそのまま開いている。**
`config` が増やさなかっただけで、**閉じてはいない。**

| | ペアリングで防げるか |
| --- | --- |
| 他人が検知ログを読む | **防げる** |
| 他人が `alert` に偽の警告を書く | **防げる** |
| 他人が `control` / `config` を書く | **防げる** |
| **接続枠を占有して黙らせる** | **防げない**（接続はボンドなしでも張れる） |
| 中間者攻撃 | **防げない**（下の Just Works） |
| 固定の `device_id` による追跡 | **防げない** |

**上がるのは機密性と、書き込みの真正性。可用性（黙らされないこと）は上がらない。**
#33 で見たのは可用性の側だけなので、**残りは #122 に持ち越している。**

**3つのどれかを外したら、#122 を待たずに見直す。** とくに **`config` を保存する作りにした瞬間**、
他人が一度書いて立ち去るだけで設定が残り、**持ち主が普通に接続できるのに鈍った装置**になる。
これは接続の占有では作れない状態で、しかも**心拍は届くので `link` は `up`**、
デバイスの表示は健全に見える。**この方式で一番避けたい「静かに壊れる」の、新しい入口になる。**

**戻すときに要るのは3つ。GATT の構造は変わらない**（手順と完了条件は #122）。

- Zero W の BlueZ に Agent を `NoInputNoOutput` で登録する（Just Works を無人で受けるため）。
- `device-info` 以外に暗号化フラグを付ける。**Notify は `encrypt-read` では効かず `encrypt-notify`**
  （`log` は `read` プロパティを持たないため。付け間違えると CCCD が保護されず、ボンドなしで購読できる）。
- モバイルはボンド完了（`ACTION_BOND_STATE_CHANGED`）を待って購読を張り直す。

なお **Zero W の Bluetooth は 4.1 で LE Secure Connections（4.2 以降）が使えない**ため、
戻したとしても Just Works になり、**中間者攻撃には守られない**。防げるのは
「ボンドしていない端末からの読み書き」まで。

### 書き込みを受ける側の約束

**ペアリングの有無と関係なく、「何を書かれるか」は受け取る側で検証する。**

- 知らないコマンド・知らない `k`・知らないキーは**無視する**（落ちない）。
- 数値は範囲を検証してから採用する。**範囲外は捨てて `status` の `last_error` に載せる。**
  **これは `control` と `config` の話**（`config` は**キーごとに**捨てる。
  [`ble-gatt.md`](./ble-gatt.md)「`config`」）。`alert` は
  「[デバイスへ渡すもの](./v2v.md#デバイスへ渡すもの)」で決めており、
  捨てたことは `last_error` ではなく `dropped` に出す。
  **`state` は変えない**（不正なコマンドが1つ来ても、流れている転送は止めない）。
- **検知のしきい値を無効化する値は、範囲に入れない。** 弾くのではなく**置かない**——
  上の「いまはペアリングを戻していない」は、**そういう値が書けないこと**の上に立っている。

### 運用で気をつけること

- **接続を占有されると検知が動かない。** つなげるセントラルは1台で、BlueZ は接続中アドバタイズを止める。
  デモ会場で他の人のスキャンアプリがつながったままになると、持ち主のスマホが接続できない。
  **`alert` が唯一の警告の出口なので、これは「ログ同期が後回しになる」ではなく
  「走行中ずっと車車間の警告が出ない」ことを意味する**（検知はスマホの中で動いているのに、伝わらない）。
  ただし**デバイスは黙らない。** `link` が `down` のまま出続けるので（上の
  「[心拍を必ず見せる](./v2v.md#心拍を必ず見せる)」）、乗っている人は気づける。
  後方物体検知も動き続ける。
  **つながらないときは、まずアプリの再スキャンで待つ。** デバイスは**心拍の来ない接続を
  30 秒で自分から切る**ので（[`ble-gatt.md`](./ble-gatt.md)「前提」）、
  **他人がつないだまま放置されている場合は、待てば戻る。再起動は最後の手段。**
  **ただし、執拗につなぎ直してくる相手には効かない**——切った直後にまた取られる。
  効くのは「つないだまま放置された」場合で、**デモ会場で実際に起きるのはこちら。**
