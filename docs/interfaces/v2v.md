# 車車間の位置共有

`../interfaces.md` から分割した。**境界の一覧と、他の境界へのリンクは
[`../interfaces.md`](../interfaces.md) にある。**

**自転車どうしが直接つながるのをやめ、スマホと Worker を経由して位置情報を配る。**
Zero W の内蔵 Wi-Fi は 802.11s（mesh point）を持たず ad-hoc（IBSS）も実質動かないため、
メッシュは成立しない。**Zero 2 W に替えても無線チップが同じなので解決しない。**
経緯と却下した案は `adr/0004-v2v-transport.md`。

```
[デバイス] --BLE 常時接続--> [スマホ] --HTTPS/LTE--> [Worker]
     ^                                                  |
     └──── 自車の位置・周辺車両の位置 ←─────────────────┘
```

| | 担当 | 仕様 |
| --- | --- | --- |
| スマホ | 測位（GNSS）と中継。**判断しない** | この節 |
| Worker | 近くにいる相手を選んで配る | 未確定（[#7](https://github.com/Hashimoto-Teppei/web-iot-makers-challenge-team-c/issues/7)） |
| デバイス | 受け取った位置で危険を判断し、その場で人に伝える | この節と #8 |

**ここで決めたペイロードがそのまま検知アルゴリズム（#8）の入力になり、
シミュレータ（#12）が流し込むデータの形もこれに揃える。**

**位置はスマホの GNSS から取る。デバイスに GPS モジュールを載せない。**
デバイスが自車の位置を知る唯一の経路もこの BLE である。

### 経路はデバイス ⇄ モバイルの BLE に相乗りする

**新しい通信路を作らない。** 「[デバイス ⇄ モバイル（BLE GATT）](./ble-gatt.md)」で決めた接続の上に、
`uplink`（Write）を1本足すだけにする。プロトコルバージョンもその節の `proto` を使い、
**この節で別のバージョン番号を持たない**（1つの境界に2つのバージョンがあると、どちらを上げるかで必ず迷う）。

**接続は常時維持する。** 走行後にまとめて同期する `log` と違い、この経路は走行中ずっと流れる。
スマホ側はフォアグラウンドサービスで接続を保つ（`unverified.md`）。

### メッセージ

`uplink` への 1回の Write に **JSON オブジェクト1つ**。`k` が種別を表す。

```json
{"k":"self","t":1756123456789,"lat":34.6617512,"lon":133.9344061,"spd":5.24,"crs":118.4,"hacc":4.0}
{"k":"peer","id":"7d02e5b1","t":1756123456650,"lat":34.6618891,"lon":133.9345121,"spd":6.11,"crs":300.2,"hacc":5.5}
```

**上の2行は2つの例であって、1回に2行書くという意味ではない。**
`log` の JSON Lines とは別物で、**この経路に `\n` の区切りは無い。1回の Write に1つ。**

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `k` | 文字列 | `"self"`（自車の測位） / `"peer"`（周辺車両1台ぶん） / `"nofix"`（測位が無い。**下の「[通信断を必ず見せる](#通信断を必ず見せる)」**。`k` 以外の項目を持たない） |
| `id` | 文字列 | 端末ID。**`k` が `"peer"` のときだけ入る**（`"self"` は自分なので要らない） |
| `t` | 整数 | **測位した時刻**（UTC ミリ秒）。スマホが測位を得た時刻であって、書き込んだ時刻ではない |
| `lat` / `lon` | 小数 | 緯度・経度（度、WGS84） |
| `spd` | 小数 | 対地速度（**m/s**） |
| `crs` | 小数 or `null` | 進行方角（度、真北 0、時計回り 0〜360未満）。**低速時は `null`** |
| `hacc` | 小数 | 水平位置精度（メートル）。小さいほど確か |

- **`id` は BLE の `device_id` と同じ形**（16進の小文字8文字）。同じデバイスを2つの名前で呼ばない。
- **単位は m/s と度で統一する。** km/h とノットを混ぜない。
  検知のしきい値（`config.py`）も同じ単位で書く。
- **`crs` は速度が出ていないと意味を持たない。** 止まっている自転車の進行方角は測位では決まらず、
  Android は直前の値を返したり `hasBearing()` が `false` になったりする。
  **`spd` が設定のしきい値（既定 1.0 m/s）未満なら `crs` に `null` を入れる。**
  受信側は `crs` が `null` の相手を「向きの分からない相手」として扱う（扱い方は #8）。
- **`hacc` はスマホが返す推定精度をそのまま入れる。** Android の `Location.getAccuracy()` は
  **メートルで返る**ので、換算も係数も要らない。
  **桁は丸める**（下の「[1回の Write に収める](#1回の-write-に収める)」）。換算が要らないだけで、
  `getAccuracy()` の戻り値をそのまま `JSON.stringify` に渡してよいという意味ではない。

  **`hasAccuracy()` が `false` のときは、その位置を送らない。**
  0 や適当な既定値で埋めると、**精度が分からない位置が「誤差 0 の確かな位置」として検知に届く。**
  デバイス側では見分けられないので、**送らない側で止める。**
  **`self` の場合は、代わりに `nofix` を送る**（黙ると「スマホは測位できているのにデバイスは永久に
  `nofix`」になり、原因が追えない。下の「[通信断を必ず見せる](#通信断を必ず見せる)」の不変条件を守る）。
  `peer` の場合はその1台を送らないだけでよい。
- **減速度・加速度は送らない。** 受信側が `t` と `spd` の履歴から出す。
  送る側で出すと**端末ごとに算出方法が違ってしまい**、検知の担当が前提をそろえられない。
  受信側は急接近の検知にも相手の履歴を持つので、**履歴を持つ仕組みはどのみち要る。**
- **知らないキーは無視する。** 項目が増えても古い実装が落ちないようにするため。
- **必要な項目が欠けているメッセージは捨てる。** 何が必要かは `k` ごとに違う。
  **上の表全体を「必須の一覧」として実装しないこと**（`id` は `peer` にしか無いので、
  表どおりに存在チェックすると**`self` が1通残らず捨てられ、自車の位置が永久に入らない**）。

  | `k` | 必須の項目 |
  | --- | --- |
  | `self` | `k` / `t` / `lat` / `lon` / `spd` / `crs` / `hacc`（**`id` は入らない**） |
  | `peer` | 上に加えて `id` |
  | `nofix` | `k` **だけ**。他は入らない |

  `crs` の `null` は「欠けている」うちに入らない。
- **知らない `k` は無視する。** エラーにしない。

#### 1回の Write に収める

**1メッセージの上限を 160 バイトとする。** 分割して組み立てる仕組みは持たない
（`log` の JSON Lines のような組み立ては、この経路では作らない）。
下の桁で丸めたときの最悪でも 119 バイト。**余白を持たせて 160 とする。**

**この 160 が、接続を成立させる MTU の下限（163）を決めている**（「[転送の約束](./ble-gatt.md#転送の約束)」の 7）。
**項目を足して 160 を超えるときは、MTU の下限も一緒に上げること。**
片方だけ直すと、超えた瞬間に**測位の書き込みだけが黙って失敗する。**

**送る前に丸める。桁数を決めておく。**

| 項目 | 小数の桁 | 例 |
| --- | --- | --- |
| `lat` / `lon` | **7桁**（約 1cm 刻み。測位の精度より十分細かい） | `34.6618891` |
| `spd` | 2桁 | `6.11` |
| `crs` | 1桁。**丸めた結果が `360.0` になったら `0` にする** | `300.2` |
| `hacc` | 1桁 | `5.5` |

**丸めないと上限を超える。** JavaScript の数値は倍精度で、`JSON.stringify` は最大17桁まで出す。
`getAccuracy()` が返す float をそのまま入れると `"hacc":5.500000238418579` のようになり、
**全項目がこの調子だと 160 を超える。**超えれば ATT の Write に載らず、
**測位の書き込みだけが黙って失敗する。**

**丸めた `crs` が `360.0` になったら `0` にする。** 受信側の範囲は **0 以上 360 未満**なので、
そのままだとその1通が丸ごと捨てられる。

**周辺車両は1回の Write に1台。** まとめて配列で送らない。台数が増えると必ず MTU を超え、
**超えた瞬間に「周辺が1台も見えない」形で壊れる**（一部が欠けるのではなく全部が届かなくなる）。
1台ずつなら、多すぎるときは**遠い相手から落とすだけ**で済む。

**同時に扱う周辺車両の数に上限を置く**（スマホ側の設定。既定 8台）。上限を超えたぶんは
**遠い相手から落とす。** 検知に効くのは近い相手だけであり、遠い相手を捨てても失うものはない。
**捨てた台数を数えて画面に出せるようにしておく**
（黙って捨てると、見えない自転車がいることに誰も気づけない）。

### 送る間隔

| 何を | いつ |
| --- | --- |
| `self` | **スマホの測位が更新されたとき。**時間で回さず測位に合わせる（実質 毎秒1通） |
| `peer` | **Worker から届いたつど。**自分の測位の更新を待たない |
| `nofix` | 測位が無い間、`self` と同じ間隔で |

**`self` を測位より速く送っても中身は前と同じ**で、BLE の帯域と両側の CPU を使うだけ増える。

**`peer` を自分の測位のタイミングまで溜めない。** 溜めると最大1秒ぶん古い位置を渡すことになり、
**この経路がもともと抱えている遅れ（150〜350ms）に上乗せされる。**
届いたものをそのまま流せば、デバイス側は `t` を見て正しい時刻の位置として扱える。

**送っていない間を埋めない。** 前回の位置をそのまま送り直す、といったことはしない。
受信側は下の失効で「居なくなった」と判断する。

**測位できていない間は `self` を送らない**（代わりに `nofix` を送る）。
位置か時刻のどちらかが欠けた `self` を作らない。
**屋内のデモでは `self` が1通も飛ばない。** 見せるときはシミュレータを使うこと。

### 受信側（デバイス）の約束

**ここに書くのは「守らないと検知が壊れること」だけ。**
受け取ったあとどう検知に渡すかは #8、何秒ぶんの履歴を持つかは実装が決めてよい。

1. **自分の `id` を持つ `peer` は捨てる。** Worker が自分の位置を配り返すことがある。
   捨てないと**自分自身を「距離 0 で並走する自転車」として検知する。**
2. **必要な項目が欠けているメッセージは捨てる。** 何が必要かは `k` ごとに違う。

   | `k` | 必須の項目 |
   | --- | --- |
   | `self` | `k` / `t` / `lat` / `lon` / `spd` / `crs` / `hacc`（**`id` は入らない**） |
   | `peer` | 上に加えて `id` |
   | `nofix` | `k` **だけ**。他は入らない |

   **上の表全体を「必須の一覧」として実装しないこと**（`id` は `peer` にしか無いので、
   表どおりに存在チェックすると**`self` が1通残らず捨てられ、自車の位置が永久に入らない**）。
3. **数値は範囲を検証してから使う。範囲外は捨てる。壊れた1通で落ちないこと。**

   | 項目 | 通してよい範囲 |
   | --- | --- |
   | `lat` | -90 〜 90 |
   | `lon` | -180 〜 180 |
   | `spd` | 0 以上、**設定の上限（既定 30 m/s ＝ 108km/h）以下** |
   | `crs` | **`null`**、または 0 以上 360 未満 |
   | `hacc` | 0 より大きく、**設定の上限（既定 50 m）以下** |

   **`crs` の `null` を範囲外として捨てない。** `null` は「止まっていて向きが分からない」という
   正常な値であり、捨てると**止まっている自転車と低速の自転車が丸ごと消える。**
   急接近の検知（#9）が一番見たい相手がこれなので、**検知が静かに効かなくなる。**
   Python で `0 <= crs < 360` を `None` に対してそのまま書くと `TypeError` で
   **受信のループごと止まる**ので、`null` かどうかを先に見ること。

   **`spd` と `hacc` に上限を置くのは、壊れた1通を検知に届かせないため。**
   桁違いの `spd` は相対速度も外挿した位置も桁違いにする。
   `hacc` が数十〜数百メートルの相手を「そこにいる自転車」として渡すと、**居ない自転車で警告が鳴る。**
4. **`peer` の新旧は `t` で判定する。同じか古い `t` は捨てる。`id` ごとに覚える。**
   1つの変数で持つと**一番新しい1台ぶんしか残らず、他の自転車を全部捨てる。**
   近傍が常に1台になり、検知は静かに発火しなくなる。

   **経路は TCP なので、詰まると古いものが「まとめて順番どおり」届く。**
   位置情報は古ければ捨てたいデータなので、**この判定が無いと、過ぎ去った位置で検知が走る。**

   **`self` には適用しない。** `self` は BLE 1本しか通らず、ATT が順序を保証するので入れ替わらない。
   **届いた最後のものを常に採る。**
   新旧判定を入れると、逆に**「1通の変な値が居座って、以後の正しい `self` を全部古いとして捨てる」
   という戻れない壊れ方**を作り込む。
5. **時刻の妥当性は「推定の現在時刻」を基準に見る。**
   デバイスには時計が無い（RTC が無く、システムクロックは信用できない）ので、
   **最後に採用した `self` の `t` に単調時計の経過を足したものを「いま」とする。**

   **`self` の `t` そのものを基準にしないこと。** それは測位が更新された時刻であって、いまではない。
   測位が数秒抜けている間、正常に届く `peer` が全部「未来」として捨てられ、
   **`link` は `up` のまま近傍だけが空になる**（この節が一番避けたい形）。

   **どれだけ先／どれだけ古い `t` まで通すかは設定で持つ**（`config.py`）。
   **既定値と、境界での細かい挙動は実装時に決める。** 実測しないと妥当な値が出ないため
   （`unverified.md`）。
6. **再送・ACK・順序の作り直しをアプリ層に作らない。** BLE のリンク層と TCP のどちらも再送する。
   三重に作ると噛み合わず、**待ち合って止まる形になりやすい。**
7. **最後に受信してから設定の時間（既定 3 秒）が過ぎた相手を、近傍から消す。**
   **消さないと、届かなくなった自転車が「その場に止まっている自転車」として残り続け、
   通り過ぎたあとも警告が鳴る。**
   **近傍から消すときは、覚えていた `t` も一緒に捨てる**（残すと戻ってきた相手を捨て続ける）。
   **既定の 3 秒は仮の値。** 短すぎると**近づいている最中の相手が消えて警告が途切れる。**
   実測して調整する（`unverified.md`）。
8. **`link` が `up` でない間は、`peer` を近傍として持たない。**
   自車の位置が無ければどの検知も成立しないので、持っても意味がない。
   **判定を別に作らず `link` を見る**（下）。しきい値を2か所に持つと、`peers` の中身と表示が食い違う。
9. **相手の位置を、受信した時刻ではなく `t` の時刻の位置として扱う。**
   届くまでの遅れを 0 と見なすと、速い相手ほど実際の位置とずれる。
   **この経路の遅れは 150〜350ms、詰まればそれ以上**あるので、直接通信より効いてくる。

### 通信断を必ず見せる

**この方式で一番危ないのは、静かに止まることである。**

直接通信なら、経路が死ねば全員がつながらず**全員が気づく**。スマホ経由では、
**1人のスマホが落ちてもその人だけ警告が来ず、他の全員からは正常に見える。**
落ちたことに気づかないまま「今日は危険が無いのだな」と思って走ることになる。

そこで**デバイス側にウォッチドッグを置き、`status` の `link` として出す。**

**「経路が死んだ」と「測位がまだ出ていない」を分ける。** どちらも検知は動かないが、
**人がすべきことが違う**（前者は端末を見る、後者は待つか外に出る）。同じ表示にすると、
待てば直るものと直らないものが区別できない。

そのために、**スマホは測位が無い間も書き続ける。**

| スマホの状態 | 書くもの | デバイスの `link` |
| --- | --- | --- |
| 測位できている | `self`（と `peer`） | `up` |
| **測位できていない** | **`{"k":"nofix"}`** を同じ間隔（毎秒）で | `nofix` |
| アプリが落ちた / BLE が切れた | 何も来ない | `down` |

**`nofix` に位置も時刻も入れない。** 入れるものが無いから送る通知であり、
**`self` の代わりにならない**（受け取っても自車の位置は更新しない）。

#### `link` を決めるときに外してはいけないこと

**秒数と判定の細かい形は実装時に決める**（`config.py`。実測しないと決まらない）。
ただし**次の5つを外すと、この仕組みが目的を果たさない。**

- **`up` から始めない。** `self` を一度も採用していない間は `up` にしない。
  `nofix` を送らない実装のスマホが `peer` だけ流すと、**自車の位置が無いまま近傍を持つ。**
- **「何か書き込みが来たか」だけで決めない。** `peer` だけ流れて `self` が止まる状態がありうる。
  書き込みは届くので `up` のままになり、一方で「受信側の約束」の 8 が `peer` を全部捨てる。
  **表示は健全なのに検知が1つも動かない**という、この節が防ぎたい形そのもの。
- **「受け取った」ではなく「採用した」で測る。** 範囲を外れた `self` が届き続けている間、
  到達だけを見ると `up` のままだが、自車の位置は入っていない。
- **`nofix` を「一度来たら立つ旗」にしない。** 見るのは**直近がどちらだったか**。
  旗にすると**再起動するまで `up` に戻らず**、停止中の情報表示が一度も出ない。
  また `peer` が挟まるたびに判定が変わらないよう、**見る対象は `self` と `nofix` だけ**にする
  （混ぜると `link` が毎秒ばたつき、**走行中の画面に文章が点滅して出る**）。
- **`t` が進んでいるかも見る。** `self` は上書きするだけなので、時計や測位が固まって
  同じ `t` を送り続けられても値の検証では気づけない。
  **ただし「控えた1点の `t` より進んだか」で実装しないこと。**
  変な値を1通採用した瞬間に基準がそこで固まり、**再起動まで戻らなくなる。**
  一定の窓の中で見るなど、**自然に回復する形にする。**

#### `up` でない間にすること

- **その旨を出力に出し続ける。** 出し方は `notifications.md`。
  **一度きりの通知にしない。** 見逃した人はそのまま走り続ける。
- **車車間の検知は「相手が居ない」ではなく「分からない」として扱う。**
  近傍を空にして黙るのは、この表示とセットで初めて成立する。
- **速度が分からないので、表示は「走行中」として扱う**（`notifications.md`）。
  止まっているように見えても、走行中の画面に文章を出さない。
- **ローカル層（センサーによる検知）は `link` に関係なく動き続ける**（`adr/0004`）。
- **屋内のデモでは `nofix` が出続けるのが正常。** これを故障として扱わないこと。

**スマホ側にも同じ問題がある**（デバイスが落ちても気づかない）が、そちらは画面があるので
アプリの表示で足りる。仕様はモバイル側に委ねる。

### 端末ID とプライバシー

`id` は BLE の `device_id` と同じ固定値で、**変わらない。**

- **経路上の位置情報は、BLE の区間では誰でも読める**（ペアリングしないため。「[割り切っていること](./ble-gatt.md#割り切っていること)」）。
  スマホと Worker の間は HTTPS で守られる。
- **なりすましを防ぐ仕組みは持たない。** Worker に偽の位置を送る端末を止められない。
  ハッカソンの期間内では、署名や端末認証を入れるより動くものを優先する。
  **やらないと決めただけで、要らないわけではない**（BLE 側と同じ）。
- **この経路に秘密値を流さない。** 位置と速度以外を載せない。
- **実走行のログをコミットしない。** 流れているのは個人の移動そのもの。
  テストとシミュレータには合成したデータを使う（`CLAUDE.md`）。

### シミュレータ・検知との関係

**検知は、データがどこから来たかを知らない。**

| | `self` と `peer` の出どころ |
| --- | --- |
| 実機 | スマホ（`uplink` への Write） |
| 開発機 | **シミュレータが「スマホ役」になり、同じ形の JSON を渡す** |

- **シミュレータ（#12）は自車と周辺車両の両方を流す。** 自車を含めるのは、
  **3つの検知がどれも自車の状態を入力に取る**ため。周辺車両だけでは1つも走らせられない。
- **受け取って近傍の状態を保つところまで**が車車間通信の責務で、
  **そこから先（何を危険と見なすか）は #8。**
- **層を分ける。** BlueZ を触る部分は Linux 専用なので `src/device/hw/ble.py` に置き、
  **受け取った JSON を検証して近傍の状態を保つ部分は `src/device/v2v.py`** に置く
  （`apps/device/README.md` のディレクトリ表）。
  `v2v.py` は BLE を知らないので、**開発機で pytest から直接叩ける。**
  差し替えるのは `main.py` の配線であって、**メッセージも検知の入力も変わらない。**
  具体的な渡し方は #12 で決める。
