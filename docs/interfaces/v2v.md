# 車車間の位置共有

`../interfaces.md` から分割した。**境界の一覧と、他の境界へのリンクは
[`../interfaces.md`](../interfaces.md) にある。**

**自転車どうしが直接つながるのをやめ、スマホと Worker を経由して位置情報を配る。**
Zero W の内蔵 Wi-Fi は 802.11s（mesh point）を持たず ad-hoc（IBSS）も実質動かないため、
メッシュは成立しない。**Zero 2 W に替えても無線チップが同じなので解決しない。**
経緯と却下した案は `../adr/0004-v2v-transport.md`。

**位置情報は BLE を通らない。** スマホの中で検知まで完結し、
デバイスへ流れるのは**表示指示と心拍だけ**である（`../adr/0006-decision-layer-on-mobile.md`）。

```
[スマホ] --HTTPS/LTE 1Hz--> [Worker] --> 半径内の他のスマホ
   |
   | BLE（表示指示・心拍のみ）
   v
[デバイス]  後方物体検知・表示・音
```

| | 担当 | 仕様 |
| --- | --- | --- |
| スマホ | 測位（GNSS）、**車車間の3検知**、**一時停止の事前通知**、中継 | この節 |
| Worker | 半径内の相手を配る | [`mobile-api.md`](./mobile-api.md) |
| デバイス | 指示されたものを表示・再生する。後方物体検知（この経路と無関係） | [`ble-gatt.md`](./ble-gatt.md) |

**ここで決めたペイロードがそのまま検知アルゴリズム（[`detectors.md`](./detectors.md)）の入力になり、
シミュレータ（#12）が流し込むデータの形もこれに揃える。**

**位置はスマホの GNSS から取る。デバイスに GPS モジュールを載せない。**

## メッセージ

**スマホと Worker の間で運ぶ。** 1Hz の HTTP POST 1本で、自分の位置を送り、
同じレスポンスで周辺車両を受け取る（正本は [`mobile-api.md`](./mobile-api.md)）。

```json
{"k":"self","t":1756123456789,"lat":34.6617512,"lon":133.9344061,"spd":5.24,"crs":118.4,"hacc":4.0}
{"k":"peer","id":"7d02e5b1","t":1756123456650,"lat":34.6618891,"lon":133.9345121,"spd":6.11,"crs":300.2,"hacc":5.5}
```

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `k` | 文字列 | `"self"`（自車の測位） / `"peer"`（周辺車両1台ぶん） |
| `id` | 文字列 | 端末ID。**`k` が `"peer"` のときだけ入る**（`"self"` は自分なので要らない） |
| `t` | 整数 | **測位した時刻**（UTC ミリ秒）。測位を得た時刻であって、送信した時刻ではない |
| `lat` / `lon` | 小数 | 緯度・経度（度、WGS84） |
| `spd` | 小数 | 対地速度（**m/s**） |
| `crs` | 小数 or `null` | 進行方角（度、真北 0、時計回り 0〜360未満）。**低速時は `null`** |
| `hacc` | 小数 | 水平位置精度（メートル）。小さいほど確か |

- **`id` は BLE の `device_id` と同じ形**（16進の小文字8文字）。同じデバイスを2つの名前で呼ばない。
  **スマホは、接続中のデバイスから `device-info` で読んだ `device_id` を自分の `id` として名乗る**
  （[`ble-gatt.md`](./ble-gatt.md)）。スマホ側で別の ID を作らない。
- **単位は m/s と度で統一する。** km/h とノットを混ぜない。検知のしきい値も同じ単位で書く。
- **`crs` は速度が出ていないと意味を持たない。** 止まっている自転車の進行方角は測位では決まらず、
  Android は直前の値を返したり `hasBearing()` が `false` になったりする。
  **`spd` が設定のしきい値（既定 1.0 m/s）未満なら `crs` に `null` を入れる。**
  受信側は `crs` が `null` の相手を「向きの分からない相手」として扱う。
  **捨てないこと**（扱い方は [`detectors.md`](./detectors.md)）。
- **`hacc` はスマホが返す推定精度をそのまま入れる。** Android の `Location.getAccuracy()` は
  **メートルで返る**ので、換算も係数も要らない。

  **`hasAccuracy()` が `false` のときは、その位置を送らない。**
  0 や適当な既定値で埋めると、**精度が分からない位置が「誤差 0 の確かな位置」として検知に届く。**
  受け取る側では見分けられないので、**送らない側で止める。**
- **減速度・加速度は送らない。** 受信側が `t` と `spd` の履歴から出す。
  送る側で出すと**端末ごとに算出方法が違ってしまい**、検知の担当が前提をそろえられない。
  受信側は急接近の検知にも相手の履歴を持つので、**履歴を持つ仕組みはどのみち要る。**
- **知らないキー・知らない `k` は無視する。** 項目が増えても古い実装が落ちないようにするため。
- **必要な項目が欠けているメッセージは捨てる。** 何が必要かは `k` ごとに違う。

  | `k` | 必須の項目 |
  | --- | --- |
  | `self` | `k` / `t` / `lat` / `lon` / `spd` / `crs` / `hacc`（**`id` は入らない**） |
  | `peer` | 上に加えて `id` |

  **上の表全体を「必須の一覧」として実装しないこと**（`id` は `peer` にしか無いので、
  表どおりに存在チェックすると**`self` が1通残らず捨てられる**）。
  `crs` の `null` は「欠けている」うちに入らない。

### 桁を丸める

**送る前に丸める。桁数を決めておく。**

| 項目 | 小数の桁 | 例 |
| --- | --- | --- |
| `lat` / `lon` | **7桁**（約 1cm 刻み。測位の精度より十分細かい） | `34.6618891` |
| `spd` | 2桁 | `6.11` |
| `crs` | 1桁。**丸めた結果が `360.0` になったら `0` にする** | `300.2` |
| `hacc` | 1桁 | `5.5` |

**BLE の MTU に収めるためではなくなった**（位置は BLE を通らない）。それでも丸めるのは、
JavaScript の数値が倍精度で `JSON.stringify` が最大17桁まで出すためで、
`getAccuracy()` の float をそのまま入れると `"hacc":5.500000238418579` のようになる。
**同じ測位の値が、経路によって違う桁で現れるのを避ける**（走行ログにも同じ形で積む。
[`ble-gatt.md`](./ble-gatt.md)）。

**丸めた `crs` が `360.0` になったら `0` にする。** 受信側の範囲は **0 以上 360 未満**なので、
そのままだとその1通が丸ごと捨てられる。

## 送る間隔

| 何を | いつ |
| --- | --- |
| `self` | **スマホの測位が更新されたとき。**時間で回さず測位に合わせる（実質 毎秒1通） |
| `peer` | **`self` を送ったレスポンスとして届く。**受け取ってから溜めない |

**`self` を測位より速く送っても中身は前と同じ**で、通信と CPU を使うだけ増える。

**測位できていない間は `self` を送らない。** 位置か時刻のどちらかが欠けた `self` を作らない。
**このとき、デバイスへの心拍には `nofix` を載せ続ける**（下の「[心拍を必ず見せる](#心拍を必ず見せる)」）。

**送っていない間を埋めない。** 前回の位置をそのまま送り直す、といったことはしない。
受信側は下の失効で「居なくなった」と判断する。

**屋内のデモでは `self` が1通も飛ばない。** 見せるときはシミュレータを使うこと。

## 受信側（モバイル）の約束

**ここに書くのは「守らないと検知が壊れること」だけ。**
受け取ったあとどう検知に渡すかも、何秒ぶんの履歴を持つかも
[`detectors.md`](./detectors.md) が決めている。**秒数をここに写さない。**

1. **自分の `id` を持つ `peer` は捨てる。** Worker が自分の位置を配り返すことがある。
   捨てないと**自分自身を「距離 0 で並走する自転車」として検知する。**
   （送らない側でも止めているが、両方で守る。[`mobile-api.md`](./mobile-api.md)）
2. **必要な項目が欠けているメッセージは捨てる**（上の表）。
3. **数値は範囲を検証してから使う。範囲外は捨てる。壊れた1通で落ちないこと。**

   | 項目 | 通してよい範囲 |
   | --- | --- |
   | `lat` | -90 〜 90 |
   | `lon` | -180 〜 180 |
   | `spd` | 0 以上、**設定の上限（既定 30 m/s ＝ 108km/h）以下** |
   | `crs` | **`null`**、または 0 以上 360 未満 |
   | `hacc` | 0 より大きく、**設定の上限（既定 50 m）以下** |

   **`crs` の `null` を範囲外として捨てない。** `null` は「止まっていて向きが分からない」という
   正常な値であり、捨てると**止まっている自転車と低速の自転車が丸ごと消える。**
   急接近の検知（#9）が一番見たい相手がこれなので、**検知が静かに効かなくなる。**

   **`spd` と `hacc` に上限を置くのは、壊れた1通を検知に届かせないため。**
   桁違いの `spd` は相対速度も外挿した位置も桁違いにする。
   `hacc` が数十〜数百メートルの相手を「そこにいる自転車」として渡すと、**居ない自転車で警告が鳴る。**
4. **`peer` の新旧は `t` で判定する。同じか古い `t` は捨てる。`id` ごとに覚える。**
   1つの変数で持つと**一番新しい1台ぶんしか残らず、他の自転車を全部捨てる。**
   近傍が常に1台になり、検知は静かに発火しなくなる。
5. **再送・ACK・順序の作り直しをアプリ層に作らない。** TCP が再送する。
   二重に作ると噛み合わず、**待ち合って止まる形になりやすい。**
   失敗した POST を送り直さない（[`mobile-api.md`](./mobile-api.md)）。
6. **最後に受信してから設定の時間（既定 3 秒）が過ぎた相手を、近傍から消す。**
   **消さないと、届かなくなった自転車が「その場に止まっている自転車」として残り続け、
   通り過ぎたあとも警告が鳴る。**
   **近傍から消すときは、覚えていた `t` も一緒に捨てる**（残すと戻ってきた相手を捨て続ける）。
   **既定の 3 秒は仮の値。** 短すぎると**近づいている最中の相手が消えて警告が途切れる。**
   実測して調整する（`../unverified.md`）。
   **この 3 秒は、サーバー側の失効に足し算で乗る**（[`mobile-api.md`](./mobile-api.md)）。
   相手が送信をやめてから近傍を出るまでは**最悪で約6秒**になるので、
   **2つの値は合計で決めること。**
7. **自車の測位が無い間は、`peer` を近傍として持たない。**
   自車の位置が無ければどの検知も成立しないので、持っても意味がない。
8. **相手の位置を、受信した時刻ではなく `t` の時刻の位置として扱う。**
   届くまでの遅れを 0 と見なすと、速い相手ほど実際の位置とずれる。
   **この経路の遅れは 150〜350ms、詰まればそれ以上**ある。

**時計の扱いはデバイスより楽になった。** スマホには時計があるので、
「最後に採用した `t` に単調時計の経過を足して『いま』を作る」という仕組みは要らない。
**ただし `t` は相手の端末の時計で打たれている**ので、**失効の判定に `t` を使わない**
（サーバー側と同じ理由。[`mobile-api.md`](./mobile-api.md)）。**自分の時計で到着時刻を打ち、それで測る。**

## デバイスへ渡すもの

**スマホからデバイスへ流れるのは、`alert`（Write）への2種類のメッセージだけ。**
GATT の約束は [`ble-gatt.md`](./ble-gatt.md)。

```json
{"k":"warn","kind":"approach","lv":2}
{"k":"beat","t":1756123456789,"st":"ok","mv":false}
```

| `k` | いつ | 内容 |
| --- | --- | --- |
| `warn` | **検知が発火したとき** | `kind`（何の検知か） / `lv`（強さ 1〜3） |
| `beat` | **毎秒1回、必ず** | `t`（UTC ミリ秒） / `st`（`ok` or `nofix`） / `mv`（走行中か） |

- **`kind` の一覧と `lv` の意味は [`detectors.md`](./detectors.md) が正本**（生むのは検知の側）。
  **それをどの出力でどう出すかは
  [`../notifications/arbitration.md`](../notifications/arbitration.md) が正本。**
  ここには**運び方**だけを書く。
- **`beat` は検知が起きていなくても止めない。** これが心拍であり、
  **止まった瞬間にデバイスが「スマホが落ちた」と判断する**根拠になる（下）。
- **`st` は「測位が取れているか」。** `nofix` の間は車車間の検知が1つも動かないので、
  デバイスはその旨を出し続ける。
- **`mv` は「走行中か」。** 速度を持っているのはスマホだけなので、**判定もスマホが行う。**
  デバイスは受け取った真偽値に従う。**`mv` が無い `beat` は「走行中」として扱う**
  （`../notifications.md` の「迷ったら走行中に倒す」）。
- **位置・周辺車両・標識をデバイスへ送らない。** 送ると `0006` で消したはずの帯域問題が戻る。

**必須の項目**（`ble-gatt.md` の `alert` は、これが欠けたものを捨てて `dropped` に数える）。

| `k` | 必須 | 任意 |
| --- | --- | --- |
| `warn` | `k` / `kind` / `lv` | — |
| `beat` | `k` / `t` / `st` | **`mv`**（無ければ「走行中」） |

**`mv` を必須にしないこと。** 必須にすると、**`mv` を載せ忘れた `beat` が1通残らず捨てられ、
`link` が `down` に落ちる。**「スマホが落ちた」とデバイスが言い続ける一方、
スマホは正常に動いている——**この境界で一番避けたい形**である
（`self` / `peer` の表と同じ罠。上の「メッセージ」を参照）。

**逆に `t` と `st` は必須にする。** `t` はデバイスがログに時刻を打つ唯一の供給源で、
`st` が無いと `nofix` と `ok` が区別できず、**測位が無いだけの状態が健全に見える。**

## 心拍を必ず見せる

**この方式で一番危ないのは、静かに止まることである。**

`0004` の時点では「測位が届かない」ことをデバイスが気づけばよかった。
**`0006` で判断そのものがスマホへ移ったので、危険は増している。**
スマホが落ちても、デバイスから見れば**「警告が来ていないだけ」＝「今日は危険が無い」**に見える。

そこで**デバイス側にウォッチドッグを置き、`status` の `link` として出す。**

**「スマホが落ちた」と「測位がまだ出ていない」を分ける。** どちらも車車間の検知は動かないが、
**人がすべきことが違う**（前者は端末を見る、後者は待つか外に出る）。同じ表示にすると、
待てば直るものと直らないものが区別できない。

| スマホの状態 | 送るもの | デバイスの `link` |
| --- | --- | --- |
| 測位できている | `beat`（`st: "ok"`）を毎秒。検知時は `warn` も | `up` |
| **測位できていない** | **`beat`（`st: "nofix"`）を毎秒** | `nofix` |
| アプリが落ちた / BLE が切れた | 何も来ない | `down` |

**POST が失敗しても `beat` を止めない。** サーバーに届かなくても自車の測位は生きており、
一時停止の事前通知は標識データさえあれば動く。止めると `link` が `down` になり、
**「スマホは動いているのに落ちたことになる」**という誤った表示になる
（詳細は [`mobile-api.md`](./mobile-api.md)「失敗したときの約束」）。

### `link` を決めるときに外してはいけないこと

**秒数と判定の細かい形は実装時に決める**（実測しないと決まらない）。
ただし**次の4つを外すと、この仕組みが目的を果たさない。**

- **`up` から始めない。** `beat` を一度も受け取っていない間は `up` にしない。
- **`warn` の到着で `up` にしない。** 警告は起きたときにしか来ないので、
  **来ないことが正常**である。到着を生存の根拠にすると、**静かなときと落ちたときが同じになる。**
  **見るのは `beat` だけ。**
- **`nofix` を「一度来たら立つ旗」にしない。** 見るのは**直近の `beat` がどちらだったか**。
  旗にすると**再起動するまで `up` に戻らない。**
- **`t` が進んでいるかも見る。** 時計や測位が固まって同じ `t` を送り続けられても、
  値の検証では気づけない。**ただし「控えた1点の `t` より進んだか」で実装しないこと。**
  変な値を1通採用した瞬間に基準がそこで固まり、**再起動まで戻らなくなる。**
  一定の窓の中で見るなど、**自然に回復する形にする。**

### `up` でない間にすること

- **その旨を出力に出し続ける。** 出し方は
  [`../notifications/arbitration.md`](../notifications/arbitration.md)「通信断の見せ方」。
  **一度きりの通知にしない。** 見逃した人はそのまま走り続ける。
- **表示は「走行中」として扱う**（`mv` が届かないため）。
  止まっているように見えても、走行中の画面に文章を出さない。
- **後方物体検知は `link` に関係なく動き続ける**（`../adr/0004-v2v-transport.md` のローカル層）。
- **屋内のデモでは `nofix` が出続けるのが正常。** これを故障として扱わないこと。

**スマホ側にも同じ問題がある**（デバイスが落ちても気づかない）が、そちらは画面があるので
アプリの表示で足りる。仕様はモバイル側に委ねる。

## 端末ID とプライバシー

`id` は BLE の `device_id` と同じ固定値で、**変わらない。**

- **位置情報が BLE を流れなくなった。** `0006` 以前は近くにいる誰でも
  周辺車両の位置を読めたが、**いまこの経路は HTTPS だけを通る。**
  BLE に残るのは表示指示と心拍で、**位置は含まれない。**
  ただし**走行ログの吸い上げ（`log`）には位置が含まれる**ので、
  [`ble-security.md`](./ble-security.md)「割り切っていること」はそのまま有効。
- **なりすましを防ぐ仕組みは持たない。** Worker に偽の位置を送る端末を止められない。
  ハッカソンの期間内では、署名や端末認証を入れるより動くものを優先する。
  **やらないと決めただけで、要らないわけではない。**
- **この経路に秘密値を流さない。** 位置と速度以外を載せない。
- **実走行のログをコミットしない。** 流れているのは個人の移動そのもの。
  テストとシミュレータには合成したデータを使う（`CLAUDE.md`）。

## シミュレータ・検知との関係

**検知は、データがどこから来たかを知らない。**

| | `self` と `peer` の出どころ |
| --- | --- |
| 実機 | 自分の測位（`self`）と Worker のレスポンス（`peer`） |
| 開発機 | **シミュレータが同じ形の JSON を渡す** |

- **シミュレータ（#12）は自車と周辺車両の両方を流す。** 自車を含めるのは、
  **3つの検知がどれも自車の状態を入力に取る**ため。周辺車両だけでは1つも走らせられない。
