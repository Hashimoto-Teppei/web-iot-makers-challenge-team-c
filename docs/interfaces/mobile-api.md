# モバイル ⇄ API

`../interfaces.md` から分割した。**境界の一覧と、他の境界へのリンクは
[`../interfaces.md`](../interfaces.md) にある。**

この境界は**走行後の同期だけでなく、走行中の中継も担う。**
経路を選んだ理由と却下した案は `../adr/0005-realtime-transport.md`。

```
[スマホ] --1Hz POST /api/v2v/exchange--> [Worker/Hono] --RPC--> [DO 1個]
[スマホ] <-- 200 { peers: [...] } ---------------------------┘
```

**エンドポイントの型はコードが正本。** `apps/web/src/worker/` のルート定義から
Hono RPC で型が伝播するため、**ここにリクエスト/レスポンスの構造を書き写さない**
（必ず実装とずれる）。このファイルには**型から読み取れないことだけ**を書く。

**流れるペイロードの中身は [`v2v.md`](./v2v.md) が正本。** `self` / `peer` の形、
単位、丸めの桁、受信側の約束はすべてそちら。**この経路のために別の形を作らない。**

Web の画面は API と同じ Worker 内にあるため単一オリジンで、CORS の考慮は不要。
モバイルアプリはネイティブなので CORS の対象外。

## 運び方

**WebSocket でも SSE でもなく、1Hz の HTTP POST 1本。** 自分の位置を送り、
**同じレスポンスで周辺車両を受け取る。**

- **測位が更新されたときだけ送る。** 時間で回さず測位に合わせる（`v2v.md`「送る間隔」と同じ理由）
- **測位が取れていない間は送らない。** 自分の位置が無ければ半径で問い合わせようがない。
  このときスマホは BLE に `beat`（`st: "nofix"`）を書き続ける（`v2v.md`「心拍を必ず見せる」）
- **離脱の通知を送らない。** サーバー側は失効（下）で勝手に消える。
  **アプリが落ちたときに送れない通知は、仕組みとして当てにできない**
- **再送しない。** 失敗した POST を送り直さない。位置情報は古ければ捨てたいデータであり、
  次の測位が1秒後に来る。`v2v.md`「受信側（モバイル）の約束」5 と同じ理由

## Worker と Durable Object の約束

**生きている状態は Durable Object 1個のメモリに置く。永続化しない。**

- **DO は1個。** `idFromName()` に固定の名前を渡す。**geohash などでセルに割らない**
  （境界をまたいだ自転車が互いに見えなくなる）
- **`locationHint` を明示的に渡す**（`apac-ne`）。**渡さないと、最初にリクエストした場所に
  置かれる。** US の CI からスモークテストを1回叩くと北米に固定される。
  ヒントは**作成時の1回しか効かず** best effort なので、**名前に世代を付ける**
  （`-v1`）。置き場所を間違えたら名前を変えて作り直す
- **状態はメモリ上の `Map<id, 最新の位置>` だけ。** `ctx.storage` を使わない。
  **飛んでも1秒で直る**（全員が再 POST する）ので、永続化する理由がない
- **DO は RPC メソッドとして呼ぶ。`fetch()` ハンドラにしない。**
  `fetch()` にすると引数を取り出すのに `await request.json()` が要り、
  **下の「`await` を入れない」が成立しなくなる。** RPC なら引数が復元済みで渡る
- **1回の交換は完全に同期処理で書く。`await` を入れない。**
  DO は単一スレッドだが `await` のたびにリクエストが割り込めるため、
  **`await` が無ければ競合が構造的に起きない。**
  ストレージや D1 を触ると必ず `await` が入る
- **`id` は BLE の `device_id` と同じ形**（16進の小文字8文字）。同じデバイスを2つの名前で呼ばない。
  **スマホは、接続中のデバイスから `device-info` で読んだ `device_id` を自分の `id` として名乗る**
  （`ble-gatt.md`）。スマホ側で別の ID を作らない
- **デバイスにつながっていない間は交換しない。** 名乗る `id` が無いだけでなく、
  **検知しても警告を出す先が無い。** ここで交換すると、
  **デバイスの無い「自転車」が他の人の近傍に現れる**

**1回の交換ですること（この順で）:**

1. **失効した相手を捨てる**（**DO が受け取った時刻**が失効の設定より古い）
2. **自分を更新し、受け取った時刻を DO 側で打つ**
3. **半径内かつ自分以外を返す**

**失効の判定に `t` を使わない。** `t` は送ってきた端末の時計で打たれた値である。
`v2v.md`「受信側（モバイル）の約束」が**失効の判定に `t` を使うことを禁じている**のと
同じ理由がサーバー側にも当てはまる。**時計が失効ぶん以上ずれている端末は、
入れた瞬間に失効して「全員から永久に見えない」状態になる**——
しかも本人の画面では POST が成功し続けるので気づけない。
**`0004` と `0005` が最も危険とした静かな部分故障そのもの**である。
**DO は自分の時計で到着時刻を打ち、それで失効を測る。`t` は中身として通すだけ。**

| 設定 | 既定 | 理由 |
| --- | --- | --- |
| 半径 | **300m** | 検知に必要なのは 50m 程度（`../adr/0004-v2v-transport.md`）。接近の履歴を作る余裕を足す。**広めでよい**——受け取った `peer` はスマホの中に留まり、BLE へは流れないので、広げても増えるのは JSON のバイト数とスマホの計算量だけ（`../adr/0006-decision-layer-on-mobile.md`。**ただし後者は `../unverified.md` 31**） |
| 失効 | **3秒**（**到着時刻**で測る） | 送信をやめた相手を配るのをやめるため。**モバイル側の失効（`v2v.md`「受信側（モバイル）の約束」6）とは足し算になる**（下） |

**サーバー側とモバイル側の失効は、同じ 3 秒だが同じものを測っていない。足し算になる。**
DO は「最後に届いてから3秒」で配るのをやめ、スマホは「最後に受信してから3秒」で近傍から消す。
**相手が送信をやめる直前の位置を受け取った人は、そこからさらに3秒持ち続ける**ので、
近傍に残る時間は**最悪でおよそ6秒**になる。6 m/s なら**約 36m ぶんの幻**である。
これは `v2v.md`「受信側（モバイル）の約束」6 が防ごうとした「通り過ぎたあとも警告が鳴る」そのものなので、
**2つの値を別々に決めず、合計で決めること。**
**既定の 3 + 3 は仮の値**で、`../unverified.md` 29 で測って決め直す。

- **API のレスポンスに台数の上限を置かない。** 20台ぶんでも 2KB 程度で、HTTPS には負担にならない。
  **BLE の区間にも上限は要らない。** 位置を運ばなくなったため
  （`../adr/0006-decision-layer-on-mobile.md`）
- **自分を返さない。** スマホ側にも同じ防御があるが（`v2v.md`「受信側（モバイル）の約束」1）、
  **送らない側で止めるのが先**
- **走行の記録（D1）をこのリクエストの中で同期に書かない。** 蓄積が要るなら
  DO のアラームでまとめて流すか `ctx.waitUntil()` で投げる。
  **リアルタイム経路の遅延に蓄積の書き込みを載せない**

## スマホの約束（受け取ってから警告まで）

**レスポンスをそのまま BLE に流さない。** 流すのは**検知の結果だけ**である
（`../adr/0006-decision-layer-on-mobile.md`）。

**以前ここには「周期ごとの窓」という節があった。** `peer` を毎秒 BLE で運んでいた頃、
**接続間隔ごとに1通という天井**（毎秒 20〜33通）に対して `self` 1 + `peer` 12 = 13通が必要で、
**超えると測位が詰まって検知ごと止まる**という問題を抱えていたためである。
**判断がスマホへ移り、この問題ごと無くなった。** 窓も台数の上限も接続間隔のレバーも要らない。

1. **レスポンスの `peer` を近傍として取り込む**（検証と失効は `v2v.md`「受信側（モバイル）の約束」）
2. **3つの検知と、一時停止の事前通知を回す**
3. **発火したものがあれば、`alert` に `warn` を書く**
4. **これとは別に、`beat` を毎秒書く**

**4 を 1〜3 の中に置かないこと。** 心拍は**検知や通信の成否と無関係に**毎秒出す必要がある。
POST の往復（150〜350ms）や検知の処理に心拍をぶら下げると、**通信が詰まるたびに心拍が遅れ、
デバイスが「アプリが落ちた」と表示する。**

**測位が無い間も1秒のタイマーで回す**（測位に合わせた実装だけだと `beat` が1通も飛ばない）。
**そして、タイマーだけでも足りない**——**Android は画面を消すと `setInterval` が事実上止まる**ので、
**測位の到着からも出すこと**（2026-09-03 実機。`apps/mobile/src/ride/loop.ts`）。黙るとデバイスは `down`
になり、**`v2v.md`「待てば直る」と「直らない」の区別が消える**（両方止まる場合は `../unverified.md` 89）。

**同じ警告を毎周期書き直さない。** 検知は毎秒発火し続けるが、**そのたびに `warn` を書くと
ブザーが鳴りっぱなしになる。** どう抑えるか（継続中の警告の扱い、優先順位）は
[`../notifications/arbitration.md`](../notifications/arbitration.md)
「送り続けるのはスマホの責務」が決める。**ここでは運び方だけを決めている。**

**書けなかった `warn` を溜めない。** 警告は古くなれば無価値であり、
**遅れて鳴る警告は、鳴らないより悪い**（もう通り過ぎた危険で鳴る）。
`v2v.md`「送っていない間を埋めない」と同じ考え方。

## 失敗したときの約束

**POST が失敗しても、スマホは黙らない。**

| 起きたこと | スマホがすること | デバイスの `link` |
| --- | --- | --- |
| POST が失敗した／返らない | **`beat`（`st: "ok"`）を書き続ける**（自分の測位は自分で取れている）。近傍が空になり、車車間の検知だけが止まる。**一時停止の事前通知は動き続ける**（**標識を手元に持っている場合に限る**。`stop-signs-delivery.md`） | `up` のまま |
| 測位が取れない | POST しない。**`beat`（`st: "nofix"`）を書く** | `nofix` |
| アプリが落ちた／BLE が切れた | 何も書けない | `down` |

**1行目が重要。** サーバーに届かなくても**自車の測位は生きている**ので、
心拍を止めてはいけない。止めると `link` が `down` になり、
**「スマホは動いているのに落ちたことになる」**という誤った表示になる。

**ただしこの状態は人に見えなければならない。** 近傍が空になるのは
「周りに誰もいない」と区別がつかず、**`0004` が一番恐れた「静かに止まる」そのもの。**
**`link` は `up` のままなので、デバイスの表示では気づけない。**
スマホ側は**連続して失敗している旨を自分の画面に出す**（走行前後に見る画面。
`CLAUDE.md` のとおり走行中に見る前提の UX にしない）。

**再接続やバックオフの作り込みは要らない。** 次の測位で次の POST が飛ぶ。
**1Hz のポーリングそのものが死活監視になっている**——これがこの方式を選んだ理由の1つ
（`../adr/0005-realtime-transport.md`）。

## なりすましとプライバシー

`v2v.md`「端末ID とプライバシー」と同じ立場を取る。**ここには差分だけを書く。**

- **スマホと Worker の間は HTTPS で守られる。** BLE の区間と違い、経路上では読めない。
  **`0006` 以降、位置は BLE を流れない**ので、走行中に経路上で読める位置情報は無くなった
  **走行後の `log` の吸い上げにも含まれない**——デバイスは位置を知らないため
  （`ble-log-transfer.md`）
- **なりすましを防ぐ仕組みは持たない。** Worker に偽の位置を送る端末を止められない。
  ハッカソンの期間内では、署名や端末認証を入れるより動くものを優先する。
  **やらないと決めただけで、要らないわけではない**
- **DO のメモリにしか置かないので、走行が終われば数秒で消える。**
  D1 に書くのは走行の記録で、**その設計は [`web-service.md`](./web-service.md)「テーブル（D1）」**
  （`../adr/0007-keep-raw-ride-logs.md`）。
  **こちらの割り切りを、そのまま向こうに持ち込まないこと**——
  あちらは**永続する行**で、割り切りの重さが違う（`web-service.md`「割り切っていること」）
- **実走行のログをコミットしない。** テストとシミュレータには合成したデータを使う（`CLAUDE.md`）

## 走行後の同期

**送るものが2種類ある。出どころが違う。**

| 何を | どこから | 経路 |
| --- | --- | --- |
| **走行ログ**（測位の連続点）と**スマホ発の検知**（車車間3つ + 一時停止） | スマホ自身 | スマホ → この API |
| **デバイス発の検知**（後方物体） | デバイス | `log`（BLE）→ スマホ → この API |

**走行ログをデバイスに残さなくなった**（`../adr/0006-decision-layer-on-mobile.md`）。
測位を持っているのはスマホなので、**わざわざ BLE で往復させる理由が無い。**

**スマホ発のレコードにも、デバイス発と同じ `(device_id, log_id, seq)` の形を使う**
（スマホが自分の `log_id` と `seq` を持つ）。
**ただし取り込み側は、これに出どころ（`source`）を足した4つをキーにする**——
`device_id` を共有しているので、**足さないとスマホ発とデバイス発が同じキーになりうる**
（`web-service.md`「データの取り込み」）。キーの意味は
[`ble-log-transfer.md`](./ble-log-transfer.md)「転送済みログの扱い」、
**取り込み側の約束は [`web-service.md`](./web-service.md)「データの取り込み」**が正本。
**ここに書くのはスマホが守ることだけ。**

**`device_id` は、スマホ発のレコードでも「接続していたデバイスの ID」を使う。**
スマホ側で別の ID を作らない（`v2v.md` の `id` と同じ理由）。
**デバイスにつながっていない走行を送らない**——`device_id` が無いレコードは、
上のキーが成立しないので取り込めない。

**蓄積したものをどう扱うか（集計・取り込み・D1）は [`web-service.md`](./web-service.md)、
どう見せるか（画面）は [`web-ui.md`](./web-ui.md) が正本。**

### スマホ側の約束（#73 で決めた）

**溜める場所は `app.db`**（[`../adr/0009-on-device-storage.md`](../adr/0009-on-device-storage.md)）。
**表の形は `apps/mobile/src/log/schema.ts` が正本**なので、ここに書き写さない。
**取り込み側の約束は [`web-service.md`](./web-service.md)「データの取り込み」**が正本。
ここに置くのは、そのどちらでもない「スマホが自分で守ること」だけである。

- **送信済みの印を持ち、送れたものを二度送らない。** 取り込みは冪等なので重なっても
  積まれないが、**印が無いと走行のたびに過去ぶんを全部送り直す**ことになる。
  **印を付けるのは送れたことを確かめてから**——先に付けると、落ちた1回ぶんが
  誰にも見えないまま消える
- **1回の送信に1走行しか載せない。** 取り込みは20走行まで受け付けるが、
  混ぜても速くならず、**「点はその走行の行と一緒に送る」を守れているかが読んで分からなくなる**
- **走行を閉じるまで送らない。** 開始と終了は確定値で、**あとから延ばせない**
  （`web-service.md`）。**閉じ忘れた走行は、次に走り出すときに最後の測位の時刻で閉じる**
  ——アプリが落ちた走行を `null` のまま残すと、**送信の対象から外れたまま端末に溜まり続ける**
- **足切りをしない。** 精度の悪い点も、速度が跳ねた点もそのまま溜めて送る
  （`../adr/0007-keep-raw-ride-logs.md`）。**捨てると二度と戻らない**
- **送れていないことを走行前後の画面に出す。** 走行後の同期は1日に1回しか走らないので、
  **黙って失敗すると「走ったのにデータが無い」と気づくのがデモの直前になる**

### 送り終えたものを端末に置き続けない（#90 で決めた）

**送り終えた行は、一定期間を置いてから端末から消す**（期間は
`../../apps/mobile/src/log/config.ts` が正本。**暫定の既定は3日**で、
根拠と未確認であることは [`../unverified.md`](../unverified.md) 69）。

- **送っていない行は、何日経っても消さない。** 消すと**二度と上がらない**——
  端末の手元が、送れていないぶんの唯一の在処である
- **送った直後には消さない。** 取り込みは**受け取った件数**を返し、
  **入った件数を返さない**（`web-service.md`「データの取り込み」）。
  **サーバー側にある確証は 200 が返ったことだけ**なので、
  **取りこぼしに気づいたときに手元を見に行ける猶予**を置く
- **置き続けもしない。** 走行ログは**個人情報**であり（`CLAUDE.md`）、
  **もうサーバーにあるものを端末に置く理由が無い。**
  1Hz で 3,600 行/時間なので、**消さなければ画面の件数集計もそのぶん重くなる**
- **「最後に送れた時刻」は走行ログとは別に持つ。** 行から数えていると、
  **掃除のあとに「一度も送っていない」に戻る**（画面がそれを送信の失敗として出す）

## 一時停止の標識を配る経路は別ファイル

**標識をスマホへ配る経路（`GET /api/stop-signs` とその周辺）は
[`stop-signs-delivery.md`](./stop-signs-delivery.md) にある。**
このファイルが 400 行に達したため切り出した（`../../CLAUDE.md`）。
**標識の配布に触るときは向こうを開くこと。**
