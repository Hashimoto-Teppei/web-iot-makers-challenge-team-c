# ADR 0009: 端末のデータは SQLite に置き、一時停止の標識はアプリに同梱する

- ステータス: 決定済み（**実機未確認** → `../unverified.md`）
- 日付: 2026-09-01
- 関連: `0006-decision-layer-on-mobile.md`（判断がスマホへ移った）/
  `0002-development-lifecycle.md`（実機なしで開発する）/
  `0007-keep-raw-ride-logs.md`（生ログを残す）/
  `../interfaces/mobile-api.md`（配る経路）/ `../interfaces/web-service.md`（D1 のテーブル）/
  `../interfaces/stop-signs-source.md`（標識の出どころ）

## 背景

**`0006` で判断する層がスマホへ移り、スマホが自分で持たなければならないものが3つ増えた。**

| 何を | いつまで持つか | なぜ端末に要るか |
| --- | --- | --- |
| **一時停止の標識** | ずっと（更新は月次） | **通信が死んでも動く唯一の検知**。手元に無ければ成立しない |
| **走行ログ**（測位の連続点） | 走行後に `POST /api/logs` が成功するまで | 送るのはスマホ自身になった（`0006`） |
| **スマホ発の検知** | 同上 | 同上 |

**これは `mobile-api.md`「失敗したときの約束」の1行に直結している。**
あそこに「POST が落ちても一時停止の事前通知は動き続ける」と書けているのは、
**標識が手元にある前提を置いているから**であり、置き場所が決まっていなければあの行は嘘になる。

**#63 の設計を始めた時点の案は「アプリ専用領域に JSON ファイル1つ」だった。**
読み取り専用のデータを丸ごと持つだけなら SQLite は過剰で、
`CLAUDE.md`「早すぎる抽象化を避ける」に触れると考えたためである。
**この案は下の「4. 同梱する」を決めた時点で成立しなくなった**ので、覆した。

## 決定

### 1. 端末のデータは SQLite に置く（`expo-sqlite` + Drizzle）

**`expo-sqlite` を使い、Drizzle ORM（`drizzle-orm/expo-sqlite`）で触る。**

- **Drizzle を選ぶのは、`apps/web` が D1 で既に使っているから**だけではない。
  **同じスキーマ定義を Node の `better-sqlite3` に差せる**ので、
  **実機なしで SQL そのものを Vitest から回せる**（下の「5」）。
  これが素の `expo-sqlite` を直に叩く案に対する決め手になった
- **マイグレーションは `PRAGMA user_version` を見て DDL を流す**（`apps/mobile/src/log/schema.ts`）。
  **当初は `drizzle-kit`（`driver: 'expo'`）+ `useMigrations` と書いていたが、#73 で変えた**
  （2026-09-01）——`babel-plugin-inline-import` と生成物が要るわりに、やることは
  「版を見て DDL を流す」だけで、**この形なら同じ SQL を Node のテストでも実機でも流せる**
- **小さな設定値（選んでいる都道府県、最後に更新した時刻）は `expo-sqlite/kv-store`。**
  AsyncStorage の drop-in なので、**`@react-native-async-storage/async-storage` は入れない**

### 2. ファイルを2つに分ける（`signs.db` / `app.db`）

| ファイル | 中身 | 誰が書くか |
| --- | --- | --- |
| **`signs.db`** | 一時停止の標識と、その版 | **アプリは書かない。**丸ごと差し替えるだけ |
| **`app.db`** | 走行ログ・検知ログ・設定 | アプリが書く |

**1つにまとめると、標識の更新で走行ログが消える。**
同梱した DB は**既にファイルがある時点で二度と上書きされない**ため、
アセットの再コピー（`forceOverwrite`）に頼ると**アプリが書いたものごと初期状態に戻る。**
分けてあれば、標識の更新は `signs.db` の中身を入れ替えるだけで済み、
**`app.db` に一切触れない。ライフサイクルが違うものを同じファイルに入れない**、というだけの話である。

### 3. 走行中は SQL で近傍のセルだけ引く

**起動時に全件をメモリへ読まない。**
セル（緯度経度を小数第3位で切り捨て。`../interfaces/web-service.md`「セルの切り方」）を列に持ち、
索引を張って、**毎周期 `自分のセル + 周囲8セル` を `SELECT` する。**

- **切り方を集計と揃えるのは、2通りの切り方を持たないため。**
  片方だけ変えると、**画面に出る場所と警告が出る場所がずれる**
- **索引付きの `SELECT` は 1Hz に対して誤差**である（`../unverified.md` 59 で測る）。
  代わりに**数万件を常時メモリに載せずに済む**
- **検知には近傍だけを渡す**（`../interfaces/detectors.md`「`signs` には近傍の標識だけを入れる」）。
  絞るのは呼び出し側の責務で、検知は渡されたものを全部見てよい

### 4. 標識はアプリに同梱し、API で更新する

**ビルド時に作った `signs.db` をアプリの資産として同梱する**（`SQLiteProvider` の `assetSource`）。
**インストール直後・電波の無い場所でも、一時停止の事前通知が最初から動く。**

**同梱が SQLite を選ぶ決め手になった。** JSON を同梱する道は2つとも副作用が大きい——
Metro の `assetExts` に `json` を足すと**リポジトリ内の全 JSON の import 挙動が変わり**、
バンドルに直接埋めると**数万件の配列が常にメモリに載る。**
`.db` の同梱は `expo-sqlite` が正式に持っている経路である。

### 5. 保存層に口を1つ置き、3つの実装を差す

**走行ループも検知も SQL を知らない。** `SignStore` のような口を1つ置き、そこにだけ実装を差す。

| どこで | 実装 |
| --- | --- |
| Vitest（既定） | メモリ実装 |
| Vitest（SQL を確かめたいとき） | `better-sqlite3`。**同じ Drizzle スキーマ** |
| 実機 | `expo-sqlite` |

**`0002` の「実機なしで開発する」を、SQLite を入れても壊さないための決定である。**
メモリ実装だけだと「メモリ実装は通るが実機の SQL が間違っている」が素通りするので、
**`better-sqlite3` を必ず併置する。**

### 6. 版はサーバーが決める。端末は ETag をそのまま持つ

`signs.db` の `meta` に `pref` / `version` / `count` / `builtAt` を1行だけ持つ。
**`version` にはサーバーが返した ETag をそのまま入れる。**

- **端末が独自の版番号を作らない。** 作るとサーバーと突き合わせられなくなる
- **同梱の時点でも版が入っている**ので、**一度も通信していない端末でも版が表示できる。**
  そして**最初の起動では `304` が返り、無駄な数 MB を落とさない**

### 7. 同梱物は生成物。リポジトリに置かず、API から1コマンドで作る

**`apps/mobile/assets/signs.db` は `.gitignore` に入れる。**
`../interfaces/stop-signs-source.md` が「CSV も生成した SQL も置かない」と決めているのと同じ理由
（public リポジトリで配布に当たる置き方をしない）。

**生成は `GET /api/stop-signs` から行う。**
**JARTIC の原本からではない**——原本は月次更新で前月ぶんが取れず、
**原本を持つ人しか同梱物を作れない運用になる。** API から作れば、
**原本を持たない人でも1コマンドで揃う。**

```
JARTIC の原本 --(抽出スクリプト。原本を持つ人が1回)--> D1
D1 --(GET /api/stop-signs)--> 各自の signs.db  ← 誰でも、原本なしで
```

**`signs.db` が無いときはビルドを即座に落とす**（`require()` が解決できない）。
**自動生成にしない**——API が落ちている日に「なぜかビルドが止まる」という、
**開発が初めての人が一番詰まる形**になる。手順は `../setup.md` に1行置く。

**そのうえで、起動時に `meta.count` が 0 なら走行開始を止める。**
ビルドを通り抜けた場合の保険で、走行前チェックリストの判定項目にそのまま乗る。

## 却下した案

| 案 | なぜ却下したか |
| --- | --- |
| **JSON ファイル1つ**（当初案） | **同梱の経路が無い**（上の「4」）。全件がメモリに常駐する。**走行ログの受け皿にならない**——追記・冪等キー・送信済みの印が要る |
| `AsyncStorage` | Android の実装に**既定 6MB の上限**があり、数 MB を扱うと触れうる。`expo-sqlite/kv-store` で置き換えられる |
| **端末に持たず、毎回サーバーへ問い合わせる** | `mobile-api.md`「失敗したときの約束」が嘘になる。**車車間の3検知が全部止まる状況で唯一残るはずの検知**まで一緒に止まる |
| **地域（タイル）で分割して配る** | 「どのタイルが欠けているか」という状態が端末に生まれ、**欠けたまま静かに黙る。** 走り出す前に現在地をサーバーへ送ることにもなる（`mobile-api.md`） |
| `app.db` に全部入れる | 標識の更新で走行ログが消える（上の「2」） |
| **抽出結果から直接 `signs.db` を作る** | **原本を持つ人しか作れない。** チーム全員で原本を配り合う運用になる（上の「7」） |
| **`packages/` を作って抽出を共有する** | **共有するのはコードではなく `signs.db` という成果物**なので、条件に触れない（`CLAUDE.md`）。スクリプトは `apps/web/scripts/` に置く |
| **端末と D1 で Drizzle のスキーマを共有する** | 列も目的も別物で、揃えにいくと片方の都合がもう片方に漏れる。**揃えるのは冪等キーの形だけ**（`mobile-api.md`「走行後の同期」） |

## 影響

- **`apps/mobile` の依存が増える** — `expo-sqlite` / `drizzle-orm` / `drizzle-kit` /
  `babel-plugin-inline-import`、開発用に `better-sqlite3` と `drizzle-studio-expo`。
  **`npx expo install` で入れる**（`CLAUDE.md`）。
  **`expo-file-system` と AsyncStorage 系は要らなくなった**
- **`docs/setup.md` に1コマンド増える**（`signs.db` の生成）。**Development Build を作る人だけ**
- **#19（D1 の作成）が、モバイル側の同梱物生成の前提になった。** 上の「7」の経路が
  D1 を通るため。**#19 は済んだ**（PR #77）が、**リモートの D1 はまだ空で Worker も未デプロイ**
  のため、いまは各自のローカルの D1 からしか同梱物を作れない。残りは #78
- **「早すぎる抽象化を避ける」との関係。** SQLite を入れる理由は抽象化ではなく、
  **同梱が要求する形式**（4）と**走行ログの受け皿**（背景）である。
  **標識だけのために入れるなら、この決定は成立しない**
