# ADR 0003: 回路・配線の管理方法

- ステータス: 決定済み（**一部は実機未確認** → `../unverified.md`）
- 日付: 2026-08-24

## 背景

1台の Raspberry Pi Zero W に、部品を**次々足していく**前提で進めている。
現時点で GPS と表示に加え、ウインカー（#24）・ブレーキランプ（#25）・マイクロ波センサー（#26）が候補にある。

ソフトウェアと違い、**配線の失敗は取り返しがつかない**。

- 間違った電圧をかけると基板が壊れる。台数が減ればメッシュの検証（最低2台必要）ができなくなる
- 2人が別々に配線すると、同じピンを取り合っていることに気づくのが「両方動かない」ときになる
- 誰がどこに何を刺したかは、**実物を見ないと分からない**。記録しないと配線を追う時間が積み上がる

チームには電子工作が初めてのメンバーもいる。**知っている人には自明なことほど、書いておかないと事故になる。**

## 決定

### 配線の正本は `docs/hardware.md` 1枚にする

ピンの割り当て・I2C アドレス・消費電流を**すべて同じファイル**に置く。部品ごとにファイルを分けない。
分けると「空いているピンはどれか」「アドレスが重なっていないか」を確認するのに全ファイルを開くことになり、
確認しないまま配線する人が必ず出る。**衝突を見つけるには一覧であることが要る。**

コードの中の GPIO 番号は正本にしない。実装が増えれば番号は複数のファイルに散り、一覧にならない。

### GPIO 番号をコードに直書きしない

しきい値と同じく設定として外に出す（`src/device/config.py`）。理由も同じで、
**配線は実地で変わる**ため。ピンを1本ずらすたびにコードを直して PR を出すのでは追いつかない。

### 3.3V を超える信号を GPIO に入れない

Raspberry Pi の GPIO は 3.3V で、**5V を直接入れると壊れる**。
5V で動くセンサーを使う場合は、出力側にレベル変換か抵抗による分圧を入れる。

「動いたから大丈夫」は通用しない。**壊れ方は即死とは限らず、しばらく動いてから不安定になる**ため、
原因の切り分けに時間を取られる。最初から入れる。

### GPIO から直接電流を取らない

GPIO 1本で流せるのは 16mA 程度、全体でも 50mA 程度が上限とされる。

- LED 1個を抵抗経由で光らせる程度なら直結してよい
- **ブザー・複数の LED・モーターはトランジスタや FET、ドライバ IC を経由する**
- 大きな電流が要るものは、ラズパイの 5V ピンではなく**電源側から直接取る**（GND だけ共通にする）

ウインカーとブレーキランプは LED が複数になる見込みで、ここに該当する。

### GPS を UART につなぐ場合は Bluetooth との競合を確認する

**Raspberry Pi Zero W 固有の落とし穴。** Zero W には UART が2つあり、
既定では性能の良い方（PL011）を Bluetooth が使い、GPIO14/15 に出ているのは簡易版（ミニ UART）である。
ミニ UART は CPU クロックに依存するため、**GPS のように連続してデータが流れるものでは取りこぼしやすい**。

対処は次のいずれか。

1. `dtoverlay=miniuart-bt` で Bluetooth を簡易版に移し、PL011 を GPIO へ回す
2. `dtoverlay=disable-bt` で Bluetooth を切る
3. GPS を UART ではなく I2C か USB でつなぐ

**2 は採れない。** モバイルアプリとの通信に BLE を使う設計（`interfaces.md`）と両立しないため。
1 を第一候補とするが、**実機で確認できていない**（`unverified.md`）。
GPS の型番が未確定（#13）のうちは 3 も選べるため、ここで確定させず選択肢として残す。

1 を選ぶ場合、overlay を書くだけでは動かない。**3つセットで必要**になる。

- `enable_uart=1` を `config.txt` に書く
- **`cmdline.txt` から `console=serial0,115200` を消す。** 消さないとシリアルコンソールが
  ポートを掴んだままになり、GPS のデータをそちらが食べてしまう
- `core_freq=250` で CPU クロックを固定する。**入れ替えた結果、今度は Bluetooth 側が
  クロック依存の簡易 UART に乗る**ため、CPU の負荷でクロックが変動すると BLE が不安定になる

「GPS が文字化けする」「BLE が切れる」で止まったときは、まずこの3つを確認する。

### 部品を足す手順を決める

1. `docs/hardware.md` のピン割り当て表で**空きを確認する**
2. 使うピンを**予約**として書き、消費電流の見積もりを足して PR を出す
3. マージされてから配線する
4. 動いたら状態を**使用中**に更新し、実測値が取れていれば書く

一人で作業する場合も 2 を飛ばさない。**この PR は「他の人が同じピンを取らないようにする」ためのもの**であり、
自分のためではない。

### 開発中はジャンパで、走行前に固定する

**自転車は振動する。** ブレッドボードとジャンパ線のままでは、走っている間に抜ける。
デモや実走行の前に、はんだ付けか、少なくともテープ・結束バンド・グルーで**物理的に固定する**。

配線を変えるうちは固定しない方が速いので、**固定するタイミングを「実走行の前」と決めておく**。

## 却下した選択肢

- **配線をコードのコメントで管理する** — 実装が増えると記述が散り、一覧にならない。衝突を見つけられない
- **部品ごとにドキュメントを分ける** — 同じ理由。1ファイルであること自体に意味がある
- **専用基板（HAT）を起こす** — 期間内に間に合わない。部品構成が変わり続ける前提とも合わない
- **最初から全部はんだ付けする** — 配線を変えるたびに作り直しになる。試行錯誤の速度が落ちる

## 結果

- 部品追加のたびに `docs/hardware.md` の更新 PR が挟まる。**1部品あたり数分のコストで、配線の衝突と破損を防ぐ**
- Zero W の UART と Bluetooth の競合は未検証のまま進む。GPS の接続方式が決まった時点で再確認する
