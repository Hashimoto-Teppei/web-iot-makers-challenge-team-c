# ADR 0006: 判断する層をデバイスからモバイルへ移す

- ステータス: 決定済み（**実機未確認** → `../unverified.md`）
- 日付: 2026-08-31
- **`0004-v2v-transport.md` の一部を覆す。** あちらが却下した
  「検知もスマホでやり、デバイスは表示器に徹する」を、こちらで採る。

## 背景

`0004` で車車間通信をスマホ経由にしたとき、**検知はデバイスに残した。**
理由は「警告はデバイス側の出力で完結させる決まりであり、判断をスマホに移すと
結果を BLE で送り返すことになって遅くなる」だった。

その後、仕様を詰める中で2つのことが分かった。

### 1. BLE が測位の運搬に耐える保証がなく、壊れ方が最悪だった

判断がデバイスにあると、**周辺車両の位置を毎秒すべて BLE で運ぶ**必要がある。
`uplink` は Write Request で、**ATT のトランザクションは同時に1つしか未応答にできない**ため、
天井はバイト数ではなく**「接続間隔ごとに1通」という回数**になる。
Android の既定（接続間隔 30〜50ms 程度）で毎秒 20〜33通が理論上の上限、
一方で必要なのが `self` 1通 + `peer` 最大12通 = **毎秒13通**。
悲観側では 650ms/1秒を使い、**1秒の周期にぎりぎり収まる程度**しかなかった。

超えたときに起きるのは「周辺車両が少し減る」ではない。
**キューが伸びて `self` が古い `peer` の後ろで待たされ、測位が止まり、検知が丸ごと止まる。**
しかも**自転車が多いときほど確実に起きる**——一番検知が要る状況で落ちる。
これを避けるために「周期ごとの窓」という仕組みを別に設計する必要があった。

### 2. 一時停止の事前通知を足すと、この経路がさらに苦しくなる

一時停止標識の位置を知らせる機能（[#27](https://github.com/Hashimoto-Teppei/web-iot-makers-challenge-team-c/issues/27)。
**やること自体は決めたが、標識データをどう配るかは未確定** → #7）を足すと、
**標識データもデバイスへ運ぶ**ことになる。標識は全県で数千〜数万件あり、
一括では運べないので「近傍の標識だけを毎周期送る」形になる。
毎秒13通で埋まっている窓に、さらに載せることになる。

**運ぶものが増えるたびに BLE の窓を削り合う**構造そのものが問題だった。

### そもそも、位置を持っているのはスマホである

`0004` でデバイスから GPS モジュールを外した時点で、**測位はスマホにしかない。**
デバイスは、スマホが測った位置を BLE で受け取って判断していた。
**判断に必要な情報を全部持っている側で判断すれば、運ぶ必要がなくなる。**

## 決定

**車車間の3つの検知と、一時停止の事前通知を、モバイルアプリで行う。
デバイスは「センサーで後方の物体を検知すること」と「指示されたものを表示すること」に絞る。**

```
[デバイス] <--BLE--> [スマホ] <--HTTPS/LTE--> [Worker]
 後方物体検知        測位・判断・中継           集約と画面
 表示・音
```

| | 担当 |
| --- | --- |
| **スマホ** | 測位（GNSS）、**車車間の3つの検知**、**一時停止の事前通知の判断**、中継 |
| **Worker** | 半径内の相手を配る。蓄積と画面 |
| **デバイス** | **後方物体検知**（センサー、通信に依存しない）。**表示・音**（指示に従う） |

### BLE を流れるものが変わる

**`uplink`（毎秒の測位供給）を廃止し、`alert`（表示指示）に置き換える。**
スマホからデバイスへ流れるのは、**「何を表示・再生するか」という指示と、心拍だけ**になる。

これにより、**接続間隔ごとに1通という天井が問題でなくなる。**
警告は起きたときだけ、心拍は毎秒1通。窓も `peer` の上限も要らない。
`mobile-api.md` の「周期ごとの窓」は丸ごと不要になった。

### 2つの層は残る。ただし中身が入れ替わる

`0004` の「ローカル層とネットワーク層」という分け方は維持する。**入れ替わるのは主従である。**

| 層 | 依存 | 中身 | 落ちたとき |
| --- | --- | --- | --- |
| **ローカル層** | 無し | **デバイスの後方物体検知**。センサーだけで完結する | 落ちない |
| **ネットワーク層** | スマホ + LTE | 車車間の3検知、一時停止の事前通知、Web への蓄積 | ローカル層が生き残る |

`0004` は「**看板は車車間通信、土台がローカル層**」としていたが、
**デバイスに残る機能はローカル層だけになった。**
デバイス担当の作業は後方物体検知と表示に集中する。

## この決定で失うもの

正直に書く。

- **スマホが落ちると、車車間の検知が3つとも止まる。** 以前は BLE が切れても
  デバイスが最後に持っていた近傍で少しは判断できた。今は判断そのものが向こう側にある。
  残るのは後方物体検知だけ。**これは `0004` の「デバイスは黙らない」を弱めている。**
- **静かな部分故障が悪化した。** 以前は「測位が来ない」ことをデバイスが気づけた。
  今は**スマホが判断をやめても、デバイスから見れば「警告が起きていないだけ」に見える。**
  → **緩和は必須。** スマホは**毎秒の心拍**を送り、デバイスは心拍が途切れたことを
  常時見える形で出す（`../interfaces/v2v.md`）。**これが無いならこの決定は採ってはならない。**
  `0004` が「静かな部分故障は派手な全損より危険」と書いた理由がそのまま強まっている。
- **デバイスから判断が1つも無くなる。** `0004` がこの案を却下した理由そのものである。
  `apps/device` の `detect/` と `hw/` を分ける構造は**後方物体検知のために残る**が、
  規模は小さくなる。**デバイス担当の作業量が減ることを、決定の前に共有すること。**
- **検知アルゴリズムの実装言語が Python から TypeScript に変わる。**
  #9 / #10 / #11 は**まだ着手していないので手戻りではない**が、担当を割り当て直す必要がある。
  `apps/device` の Python は後方物体検知（#26）が主になる。

## 得るもの

- **BLE の帯域制約が構造的に消える。** 「周期ごとの窓」「`peer` の上限」「接続間隔を上げる」
  といった仕組みと調整が、まとめて不要になる。
- **検知が開発機だけでテストできる。** TypeScript 側は Vitest でモックデータを流すだけで回り、
  BlueZ も実機も要らない。`0002-development-lifecycle.md` の
  「実機での動作確認を待たずに実装を進める」が、より素直に満たせる。
- **一時停止の事前通知が、標識データを運ばずに済む。**
  スマホが Worker から標識を取り、スマホの中で判定する。BLE には結果だけが流れる。
- **走行ログをデバイスに持たせる理由が消えた。** 測位を持つスマホが直接 Worker に送れる
  （`../interfaces/ble-gatt.md`）。デバイスが残すのは後方物体検知のログだけになる。

## 見直す条件

- **スマホの判断が間に合わないと分かった**（測位から警告までが体感で遅い）
  → 判断をデバイスへ戻す。ただし戻すと BLE の帯域制約も一緒に戻ってくる。
- **Android の常駐が保てないと分かった**（`../unverified.md`）→ この決定の前提が崩れる。
  判断がスマホにある以上、**アプリが止まれば検知も止まる。**
  `0004` の時点より影響が大きいので、常駐テストの優先度を上げる。
- **後方物体検知だけではローカル層として不足だと分かった**
  → デバイスに載せるセンサーを増やす（#13 / #26）。判断層を戻すより先にこちらを検討する。
