# ADR 0004: 車車間通信をスマホ経由にし、位置情報もスマホから取る

- ステータス: 決定済み（**実機未確認** → `../unverified.md`）
- 日付: 2026-08-26

## 背景

このプロジェクトは当初から「Raspberry Pi Zero W を載せた自転車同士が **Wi-Fi メッシュ**を組み、
GPS の位置情報を交換する」という前提で進めてきた。3つの危険検知はすべて
「周辺の自転車の位置と速度が手に入る」ことの上に成り立っている。

メッセージ仕様を決めるにあたって前提を確認したところ、**Zero W の内蔵 Wi-Fi では
標準的なメッシュが組めない**ことがわかった。

### メッシュが組めない理由

- **802.11s（mesh point）は使えない。** Zero W の Wi-Fi（BCM43438）を動かす `brcmfmac` は
  **FullMAC** ドライバで、MAC 層の処理が閉じたファームウェアの中で完結している。
  そのファームウェアが 802.11s を持たないため、Linux 側からは**インターフェースモードとして選べない**。
  `iw list` に出るのは managed / AP / monitor / P2P-\* で、mesh point は無い。
  **設定の問題ではなく、カーネルを上げても Raspberry Pi OS を変えても出てこない。**
- **ad-hoc（IBSS）も実質使えない。** モードとしては見えるが、動かない報告が
  Raspberry Pi 本家のリポジトリに複数ある（`raspberrypi/linux` の
  [#2093](https://github.com/raspberrypi/linux/issues/2093) /
  [#2629](https://github.com/raspberrypi/linux/issues/2629) /
  [#1384](https://github.com/raspberrypi/linux/issues/1384)、
  `raspberrypi/firmware` の [#990](https://github.com/raspberrypi/firmware/issues/990)）。
  `brcmf_cfg80211_change_iface: iface validation failed: err=-16`（EBUSY）で切り替えに失敗する、
  切り替わっても相手が見えない、といった内容で、**Broadcom 自身が「IBSS は検証しておらず、
  AP+STA か P2P を使え」と回答している。**
- **batman-adv も道連れ。** batman-adv は L2 のルーティングであって、下に IBSS か mesh point が要る。
  上の2つが使えない以上、batman-adv だけ入れても土台が無い。

### Zero 2 W に替えても解決しない

**同じ調査を繰り返さないために書いておく。** Zero 2 W は SoC が変わった（BCM2710A1、4コア）だけで、
**無線チップは Zero W と同じ CYW43438（BCM43430 系）のまま**である。ドライバも `brcmfmac` のままなので、
上の3点がそっくり当てはまる。**基板を替えてメッシュにする道は無い。**

つまり「メッシュを組む」は、やり方を調べれば実現できる類の未確認事項ではなく、
**この部品では成立しないことが判明した前提**である。

### 前提が崩れた結果、経路を選び直すことになった

内蔵 Wi-Fi でメッシュが組めない以上、自転車どうしを直接つなぐには
「1台を親にした AP 星型」か「USB ドングルを足す」しか残らない。
どちらも代償が大きい（下の「却下した案」）。

一方で**このシステムにはもともとスマホが居る**。BLE でデバイスとつながり、
LTE で Worker に届く経路が最初から設計に入っている。
**スマホを常時つないでよいなら、これがそのまま車車間通信の経路になる。**

## 決定

**自転車どうしの直接通信をやめ、スマホと Worker を経由して位置情報を配る。
位置情報もスマホの GNSS から取り、デバイスに GPS モジュールを載せない。**

```
[デバイス] --BLE 常時接続--> [スマホ] --HTTPS/LTE--> [Worker]
     ^                                                  |
     └──── 自車の位置・周辺車両の位置 ←─────────────────┘
```

| | 担当 |
| --- | --- |
| **スマホ** | 測位（GNSS）と中継のみ。**判断しない** |
| **Worker** | 近くにいる相手を選んで配る。蓄積と画面 |
| **デバイス** | **検知と通知。**受け取った位置で危険を判断し、その場で人に伝える |

**検知はデバイスに残す。** スマホの方が CPU は速いが、警告はデバイス側の出力で完結させる決まりであり
（`../notifications.md`）、判断をスマホに移すと結果を BLE で送り返すことになって遅くなる。
**検知の入力は「自車の状態＋周辺車両の状態のリスト」のままで変わらない**ので、
**3つの検知（#9 / #10 / #11）は書き直しにならない。**

**ただし #8 と #12 は影響を受ける。**

- **#8**（共通インターフェース）は、下の「2つの層に分ける」により
  **センサー由来の入力も受ける形で決める**必要がある。
- **#12**（シミュレータ）は UDP を撒く役ではなく、**「スマホ役」として同じ形のデータを渡す役**になる。

どちらも**まだ着手していないので手戻りではない**が、「影響なし」と読まないこと。

仕様は `../interfaces/` に書く（Characteristic は `ble-gatt.md`、メッセージの中身・送る間隔・受信側の約束は `v2v.md`）。
ここには**なぜこの方式にしたか**だけを書く。

### 2つの層に分ける

**この決定の中心はここにある。** 通信に依存する機能と、しない機能を分ける。

| 層 | 依存 | 中身 | 落ちたとき |
| --- | --- | --- | --- |
| **ローカル層** | **無し** | デバイスに載せたセンサーで周囲を見て、その場で警告する | 落ちない |
| **ネットワーク層** | スマホ + LTE | 車車間の位置共有、Web が集約した情報の表示 | **ローカル層が生き残る** |

ネットワーク層が死んでも**デバイスは黙らない**。これが、通信経路を1本に絞れる理由である。
Wi-Fi の第二経路を別に用意するより、**通信に依存しない検知を1つ持つ方が保険として強い**。

ローカル層は**1台で成立する**ため、確保台数が未定（#13）でも開発とデモが進む。
使う部品は未定（#13 / #26）で、`../hardware.md` に決まってから書く。

**看板は車車間通信（3つの検知）、土台がローカル層**という主従で進める。
逆にしない理由は、#8 〜 #12 がすでに車車間通信を前提に組んであり、
いま入れ替えると手戻りが出るため。

### この決定で失うもの

正直に書く。**「メッシュが要らなくなった」わけではない。**

- **依存が4つ増える。** BLE 接続・アプリの常駐・LTE 圏内・Worker 稼働のどれが欠けても
  ネットワーク層が止まる。直接通信なら、2台に電源を入れれば外部に何も要らなかった。
- **故障が「静か」になる。** 直接通信なら誰もつながらず全員が気づく。スマホ経由では
  **1人のスマホが落ちてもその人だけ警告が来ず、他の全員からは正常に見える。**
  安全装置において静かな部分故障は派手な全損より危険である。
  → **緩和は必須。** デバイスは「一定時間スマホから何も来ていない」を検出し、
  **通信断を常時見える形で出す**（`../interfaces/v2v.md`）。これが無いならこの決定は採ってはならない。
- **遅延のテールが伸びる。** 平常時は BLE 2ホップ + LTE 往復でおおむね 150〜350ms、
  対する測位は 1Hz（1000ms）なので**平均では埋もれる**。
  ただし会場の電波が混めば数百ms〜数秒に伸び、HTTPS は TCP なので**取りこぼすと順番待ちで後続が止まり、
  回復時に古い位置がまとめて届く**。位置情報は「古いなら捨てたい」データなので再送は害でしかない。
  → 受信側は `t` で新旧を判定して古いものを捨てる（`../interfaces/v2v.md`）。
  **誤動作はしないが、数秒の穴が開く。**
- **端末依存の当たり外れが出る。** Android の常駐は規格どおりに書いても、
  一部メーカーの省電力機構がフォアグラウンドサービスごと停止させる。
  → **デモに使う実機で早期に常駐テストを行う**（`../unverified.md`）。

**「到達範囲が無限になる」を利点として数えない。** 衝突検知に必要なのは 50m 程度であり、
1km 先の自転車の位置は検知にとって無価値である。直接通信でも要件は満たせていた。
スマホ経由で本当に得られるのは、**親役を決めなくてよいこと**と、
**Web に集約した情報がデバイスに返ってくること**の2つである。

## 却下した案

### 1台を親（`hub`）にした AP 星型 + UDP ブロードキャスト

**メッシュが使えないと分かった直後は、これを採る方針だった。**
1台が `hostapd` で AP を立て、残りが STA でぶら下がり、UDP ブロードキャストで撒く。
外部に何も依存せず、遅延も小さい。

採らなかった理由は3つ。

- **`hub` が単一障害点になり、`hub` が先に起動していないと誰もつながらない。**
  さらに実効範囲は「互いに 50m」ではなく「**全員が `hub` から 50m**」になる。
  走行中の集団で親が先行・後落すると、**隣り合っている2台が互いに見えなくなる。**
- **Web が集約した情報をデバイスに出せない。** この経路には Worker が居ない。
  「Web で集めたものを手元の画面に返す」という、この大会で見せたいものが作れない。
- **1台では成立せず、AP 役に1台取られる。** 確保台数が未定（#13）の段階で、
  検証に最低2台を要求する設計は置きにくい。

スマホ経由がこの3つすべてを解く一方で、AP 星型が勝るのは
「外部依存が無い」1点だけであり、**それは上の「2つの層」で代替できる。**

### USB Wi-Fi ドングルを足して本物のメッシュを組む

`nl80211` 系のドングル（Ralink RT5370 など）なら IBSS も 802.11s も通り、batman-adv も載る。
**Pi でメッシュを組んでいる事例はどれも外付けを使っている。**

採らなかったのは、**Zero W の USB が micro-USB 1ポート（データ側）しかない**ため。
OTG 変換と給電の分岐が要り、箱が大きくなる。消費電流も増える。ドングルの調達も台数分必要になる。
そして**これも Web を経由しない**ので、上の AP 星型と同じ問題を抱える。

### Nexmon で内蔵 Wi-Fi のファームウェアを書き換える

Nexmon は Zero W の Wi-Fi チップ（bcm43430a1）に対応しており、モニタモードとインジェクションを足せる。
アソシエーションなしで全方向に撒けるので、思想としては用途に合っている。

採らなかったのは、**壊れたときに直せないから**。閉じたファームウェアへのパッチであり、
カーネルを更新すると当たらなくなる。Bluetooth との共存も未知で、
**デモ当日に動かなくなったとき、原因の切り分けができる人がチームにいない。**

### Wi-Fi Direct（P2P）

`brcmfmac` が対応しており Broadcom の推奨でもあるが、P2P も**グループオーナーを1台決めて
残りがぶら下がる**形で、結局は星型になる。それでいて接続の確立に時間がかかる。
同じ星型なら、枯れていて情報も多い AP + STA の方がよく、そしてその AP 星型を上で落としている。

### ラズパイの BLE アドバタイズで直接撒く

スマホもクラウドも使わず、デバイスどうしが BLE のアドバタイズを撒き合う案。
接続不要・対等・完全オフラインで、**発想としては一番メッシュに近い。**
データも 31 バイトの枠にバイナリなら収まる。

採らなかったのは、**到達距離が Wi-Fi よりむしろ狭い**（BLE 4.1 のオンボードアンテナで実用 10〜30m）ため。
加えて、1つの無線で「スマホへのペリフェラル + アドバタイズ + スキャン」を同時にこなすことになり、
BlueZ が同一端末の連続アドバタイズを重複として間引く問題もある。
**当日詰まったときに切り分けられる人がいない領域**である。

### 検知もスマホでやり、デバイスは表示器に徹する

**動く確率は一番高い。** スマホは CPU も潤沢で、開発機だけで検知をテストできる。

採らなかったのは、**それをやるとデバイスに判断が1つも残らない**ため。
`apps/device` の構造（`detect/` と `hw/` を分ける）も、#8 〜 #12 の分担も前提を失う。
デバイス側はセンサーによるローカル検知と表示の強化に投資する方針であり、
**判断する層をデバイスに残すことがその前提**になる。

## 影響

- **`hw/gps.py` は作らない。** 位置はスマホから BLE で届く。
  シミュレータ（#12）は「スマホ役」として同じ形のデータを流し込む。
- **`../hardware.md` から GPS（NEO-6M）の行が消える。** GPIO14/15 と物理2番・6番が空き、
  消費電流の見積もりから 45mA が落ちる。
- **`0003-hardware-wiring.md` の UART と Bluetooth の競合が、いったん解消する。**
  ただし**空いた UART に別の部品を載せると同じ問題が再発する**（同 ADR に一般化して残した）。
  BLE がクリティカルパスになったぶん、以前より痛い。
- **`../unverified.md` から GPS と AP 星型に関する行が消え、スマホ側の前提が入る。**
- **`../notifications.md` に「走行中／停止中」の軸が入る。** Web が集約した情報を出せるようになると、
  画面が**読ませるもの**になりかねない。2024年11月施行の改正道交法で自転車の「ながら運転」は
  画像表示用装置の注視も対象であり、**自作ディスプレイが対象外である保証はない。**
  防ごうとしている違反を作り込まないため、**走行中は警告のみ・停止中に情報**とする。
- **検知アルゴリズム（#8）への影響は無い。** 検知が受け取るのは「自車と周辺車両の状態」であり、
  それがどう届いたかを知らない。**経路を差し替えてもペイロードは変わらない**ように仕様を決める。
- **#7（モバイル ⇄ API）の重みが変わる。** 走行後の同期だけでなく、
  リアルタイムの中継を担うことになる。**モバイル担当がクリティカルパスに乗る。**

## 見直す条件

**次のどれかが起きたら、この決定を見直す。**

- **デモ会場で LTE が使えない、または常駐が保てないと分かった** → ローカル層だけで見せる形に切り替える。
  それでも足りなければ AP 星型（上で却下した案）に戻す。**ペイロードは変えずに済む。**
- **BLE の常時接続が 1Hz の書き込みに耐えないと分かった**（`../unverified.md`）→ 送る間隔を落とすか、
  周辺車両の数を絞る。それでも駄目なら経路を選び直す。
- **スマホの測位精度が、置き場所のせいで検知に耐えないと分かった** → GPS モジュールを戻す。
  配線の手順は git の履歴に残っている（`../hardware.md` と `0003-hardware-wiring.md` の、
  この変更より前の版）。
- **ローカル層のセンサーで十分な成果が出て、車車間通信が要らないと判断した** → 主従を入れ替える。
