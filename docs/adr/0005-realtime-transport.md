# ADR 0005: 走行中の位置中継を HTTP ポーリングにし、状態を Durable Object に置く

- ステータス: 決定済み（**実機未確認** → `../unverified.md`）。**ただし「周期ごとの窓」の部分は [0006](./0006-decision-layer-on-mobile.md) が不要にした**
- 日付: 2026-08-29

> **この ADR を読むときの注意。** 経路（1Hz の HTTP ポーリング／状態は Durable Object のメモリ）は今も有効だが、
> **BLE の物理制約から来ていた「周期ごとの窓」（既定 12台）は無くなった。**
> [0006](./0006-decision-layer-on-mobile.md) で判断がモバイルへ移り、**周辺車両を BLE で運ばなくなった**ため。
> この ADR に出てくる「BLE に書く直前で絞る」という段は、いま存在しない。
> **半径 300m と失効 3 秒（サーバー側）はそのまま有効。**

## 背景

`0004-v2v-transport.md` で「自転車どうしの直接通信をやめ、スマホと Worker を経由して位置情報を配る」
と決めた。その結果、**走行中ずっと 1Hz で往復する経路がスマホと Worker の間に生まれた**が、
**それを何で運ぶかは決めていなかった**（`../interfaces.md` の「モバイル ⇄ API」が未着手、#7）。

決まっていたのはペイロード（`self` / `peer` / `nofix`）と送る間隔だけで、
**管の種類（WebSocket / SSE / ポーリング）も、周辺車両を選ぶための状態をどこに置くかも白紙**だった。

この ADR はその2つを決める。

### 何を最適化するのか

**遅延だけを見て決めると間違える。** `0004` が「この決定で失うもの」として挙げた4つのうち、
**一番危ないのは「故障が静かになる」**であり、`../interfaces/v2v.md` は丸ごと1節をその緩和に使っている。

> 安全装置において静かな部分故障は派手な全損より危険である。

したがって**この経路に求めるものは、速さより「壊れたことが分かること」**である。
その次に、`CLAUDE.md`「開発が初めてのメンバーが多い」を踏まえた実装の易しさが来る。
`0004` が書いたとおり**モバイル担当はすでにクリティカルパスに乗っている**ので、
そこに一番難しい実装を積む選択は取らない。

## 決定

**走行中の位置中継を HTTP ポーリング（1Hz の POST、レスポンスに周辺車両）で行う。
生きている状態は Durable Object 1個のメモリに置き、永続化しない。**

```
[スマホ] --1Hz POST /v2v/exchange { self }--> [Worker/Hono] --RPC--> [DO 1個]
                                                                      Map<id, 最新の位置>
[スマホ] <-- 200 { peers: [半径 300m 内の全員] } ---------------------┘
   |
   | 周期ごとの窓で近い順に選ぶ（BLE の物理制約）
   v
[デバイス] BLE Write: self / peer × N / nofix
```

仕様は `../interfaces/mobile-api.md` に書く。ここには**なぜこの方式にしたか**だけを書く。

**`../interfaces/v2v.md` のペイロードは変えない。** `self` / `peer` / `nofix` の形も、
160 バイトの上限も、受信側の約束もそのまま。したがって
**検知（#8 〜 #11）とシミュレータ（#12）はこの決定の影響を受けない。**

### 絞り込みを2つに分ける

**これがこの決定の中心にある。** 周辺車両の絞り込みには**性質の違う制約が2つ**あり、
1つにまとめると必ずどちらかが壊れる。

| | 何のための制約か | どこで効かせるか | 既定 |
| --- | --- | --- | --- |
| **半径** | **意味の制約。**それより遠い自転車は検知に無関係 | **Worker（DO）** | 300m |
| **周期ごとの窓** | **物理の制約。**BLE がそれ以上運べない | **スマホ（BLE に書く直前）** | 12台 |

**半径だけにして台数を無制限にしてはいけない。** `uplink` は Write Request（応答あり）であり
（`../interfaces/ble-gatt.md`）、ATT のトランザクションは同時に1つしか未応答にできないため、
**スループットの天井は「接続間隔ごとに1通」**になる。バイト数ではなく**回数**が効く。

Android の接続間隔は既定（`CONNECTION_PRIORITY_BALANCED`）で 30〜50ms 程度とされ、
**毎秒 20〜33 通が理論上の天井**になる。半径 300m 内の全員を無制限に流すと、
発表会場のように人が集まる場所でこれを超える。

**そして壊れ方が最悪である。** 書き込みキューが伸びると、`self` が古い `peer` の後ろで待たされる。
`CLAUDE.md` の言うとおり**BLE は測位の唯一の供給元**なので、これは
`../interfaces/v2v.md` のウォッチドッグが `link` を落とし、**検知が丸ごと止まる**ことを意味する。
**自転車が多いときほど確実に起きる。デモと発表の本番が、まさにその条件である。**

**逆に台数だけにして半径を持たないのも駄目で**、それは 300m 先の無関係な自転車を
近傍に入れることになる。`0004` が書いたとおり「1km 先の自転車の位置は検知にとって無価値」である。

### 上限は「台数」ではなく「周期ごとの窓」として持つ

**8台という持ち方をやめる。** 測位が更新されるたびに送信キューを作り直す。

1. **送信キューを空にする。** 前の周期の残りは捨てる（古い位置は無価値）
2. **`self`（または `nofix`）を先頭に入れる**
3. 半径内の相手を**近い順に、設定の上限まで**入れる
4. 1通ずつ Write Request を送る。次の測位が来たら 1 に戻る

**単位を変えるのは、壊れるものの単位に合わせるためである。** `../unverified.md` の 8 は
「測位の更新頻度 1Hz で検知が成立する。**足りなければスマホ側で上げられる**」と書いている。
**「8台」という持ち方だと、測位を 2Hz にした瞬間に BLE の負荷が黙って2倍になる**
（1 + 8 = 9通/秒 → 18通/秒）。誰も上限を変えていないのに天井を超える。
周期ごとの窓なら、2Hz にすれば窓が半分の頻度で来るだけで、`peer` が自動的に減る。

この仕組みには、上限の数字を当てにいかなくてよくなるという効き目がある。

- **`self` が絶対に遅れない。** 毎周期の先頭に固定されるので、`peer` がいくら多くても測位が詰まらない
- **実際に流れる台数をリンクの速さが決める。** 速ければ上限まで、遅ければ通った分だけ。
  **実測（`../unverified.md` 24）の前に正しい数字を当てる必要が無い**
- **キューが伸びない。** 毎秒リセットされるので遅延が累積しない
- **上限に張り付いているかどうかが、そのまま「上げてよいか」の答えになる**

**既定を 8 から 12 に上げるのは、この仕組みのおかげで上限が高すぎても危険でなくなったため。**
`BALANCED` の悲観側（毎秒 20通）に対して `self` 1 + `peer` 12 = 13通/秒、65% にあたる。
**切られるのは常に一番遠い相手**なので、切り捨ては常に正しい側に落ちる。

台数を増やしたくなったときのレバーは
`requestConnectionPriority(CONNECTION_PRIORITY_HIGH)`（接続間隔 11.25〜15ms 程度、**約3倍**）で、
アプリ側は1行で済む。電池を使い、端末と BlueZ が接続パラメータ更新を受けるかは端末依存。

### 生きている状態と蓄積を分ける

| | 生きている状態（いま誰がどこにいるか） | 蓄積（走行の記録） |
| --- | --- | --- |
| 置き場所 | **Durable Object のメモリ** | **D1** |
| 寿命 | **3秒**（`../interfaces/v2v.md` の失効と同値） | 永続 |
| 書き込み | 1Hz × 台数 | 走行後にまとめて／間引いて |

**これは二択ではない。役割が違う。混ぜると両方が壊れる。**

**1Hz の位置をリクエストの中で同期に D1 へ書かないこと。**
蓄積が要るなら DO のアラームでまとめて流すか `ctx.waitUntil()` で投げる。
**リアルタイム経路の遅延に蓄積の書き込みを載せない。**

### Durable Object は永続化しない

状態はメモリ上の `Map<id, 位置>` だけとし、`ctx.storage` を使わない。

- **メモリが飛んでも自己修復する。** エビクション・再デプロイでマップが空になっても、
  全員が1秒以内に再 POST するので**最大1秒ぶんの `peer` が抜けるだけ**。
  失効が元々3秒なので、この揺らぎは仕様の許容範囲に収まる
- **位置情報が残らない。** 誰も走らなくなった数秒後に、何もしなくても消える。
  `CLAUDE.md`「機密情報の扱い」が言うとおり位置情報は個人情報であり、
  **「消す運用」を作らずに済むこと自体が安全**である
- **`await` が消える。** DO は単一スレッドだが `await` のたびにリクエストが割り込める
  （Cloudflare 公式が "Race Condition Despite Single-Threading" として挙げている）。
  ストレージを触ると必ず `await` が入り `blockConcurrencyWhile()` を考えることになる。
  **メモリ上の `Map` だけなら処理が完全に同期で、割り込む隙が構造的に無い**

### 失効はサーバーの時計で測る

**DO は到着時刻を自分で打ち、それで失効を判定する。`t`（スマホが打った測位時刻）で測らない。**

`../interfaces/v2v.md`「受信側の約束」5 が**デバイス側で `t` を「いま」として使うことを禁じている**
のと同じ理由が、サーバー側にもそのまま当てはまる。**時計が失効ぶん以上ずれた端末は、
入れた瞬間に失効して全員から永久に見えなくなる**のに、本人の画面では POST が成功し続けるため
気づけない。**`0004` が「静かな部分故障は派手な全損より危険」と書いた形そのもの**である。

**そのうえで、サーバー側とデバイス側の失効は足し算になる。** DO は「最後に届いてから」で測り、
デバイスは「最後に受信してから」で測るため、**同じ 3 秒でも近傍に残る時間は最悪で約6秒**になる。
**2つの値を別々に決めず、合計で決めること**（`../interfaces/mobile-api.md`、`../unverified.md` 29）。

### DO は1個にする

`idFromName()` に固定の名前を渡し、**geohash などでセルに割らない。**

単一 DO のスループット上限は約 1,000 req/s、こちらは 20台で 20 req/s。
**セルに割ると境界をまたいだ自転車が互いに見えなくなる**という、
`0004` が AP 星型を却下した理由と同じ問題を持ち込む。数百台になってから考える。

**`locationHint` を明示的に渡す**（`apac-ne`）。既定では**最初のリクエストが来た場所**に
置かれるため、**US の CI からスモークテストを1回叩いただけで DO が北米に固定される。**
ヒントは作成時の1回しか効かず best effort なので、**名前に世代（`-v1`）を付けて、
間違った場所に作ったときに作り直せるようにしておく。**

## 却下した案

### WebSocket（Durable Object の Hibernation API）

**この ADR を書き始めた時点では、これを採る方針だった。** 双方向1本で、
下りが自分の送信を待たない。`0004` が「`peer` を自分の測位のタイミングまで溜めない」と
書いた要求に、構造的に一番素直に応える。

採らなかった理由は4つ。

- **コードのデプロイが全接続を切る。** Cloudflare の公式ドキュメントに
  "Code updates disconnect all WebSockets. Deploying a new version restarts every Durable Object,
  which disconnects any existing connections." とある。
  **ハッカソン中は1日に何十回もデプロイし、その中にはフィールドテストの最中も含まれる。**
  ポーリングならデプロイは次のリクエストが新バージョンに行くだけで完全に不可視。
  なお**ハイバネーションがまたげるのはエビクション／アイドルだけ**であり、
  そもそも 1Hz で流れ続けるこの用途ではハイバネートしないので、利点として数えられない
- **遅延の利点が測定のノイズより小さい。** `../interfaces/v2v.md`「受信側の約束」9 が
  **`t` の時刻の位置として扱う（＝外挿する）**ことを求めている以上、等速で走る相手なら
  500ms の遅れは外挿でほぼ消える。一方 `hacc` は実測 3〜8m 程度が見込まれ、
  2台ぶんが無相関に乗るので**車間距離の不確かさは 5〜10m**。
  **500ms ぶんの差はその下に埋もれる。**
  外挿が効かないのは前方急ブレーキ（#10）だけだが、**減速度は履歴から出す仕様**なので
  検出に最低2サンプル＝1秒以上かかり、どちらの経路でも元から遅い
- **死活検出を自前で作ることになる。** 下りは近傍が0台なら完全に無音なので、
  「周りに誰もいない」と「接続が死んだ」が区別できない。
  **これを解くために毎秒のハートビートを足すことになるが、ポーリングはそれ自体がハートビートである。**
  LTE のセルハンドオーバーで IP が変わった直後、死んだ TCP ソケットは書き込みが失敗するか
  キープアライブが切れるまで気づけない。**`0004` が一番恐れた「静かに止まる」に対して弱い**
- **クリティカルパスの担当に一番難しい実装が乗る。** 再接続バックオフ、死んだソケットの検出、
  ハートビート。加えて**Hono RPC の型が効かない**ので `src/shared/` に手書きのスキーマを
  維持することになる。ポーリングなら型はルート定義から伝播し、`curl` でも叩ける

**採る条件は下の「見直す条件」に書いた。ペイロードは変えずに移れる。**

### SSE（下りだけストリーム、上りは別の POST）

**Expo で動かないから落としたのではない。** `expo/fetch` は WinterCG 準拠で
`response.body` のストリーミングを Android / iOS ネイティブで扱える。

落とした理由は、**上下がそろって WebSocket とポーリングの両方に劣後するため。**

- **接続が2本になり、断の検出が上下で別々になる。**「上りは生きているが下りだけ死んでいる」
  という状態を作れてしまう。これは `../interfaces/v2v.md` が丸ごと1節を割いて防いでいる形そのもの
- **DO でハイバネートできない。** レスポンスストリームを握っている間 DO はメモリに居続ける必要があり、
  エビクトされるとストリームが黙って死ぬ
- **サーバー側から死んだ接続を検出しづらい。** 書き込みが失敗するまで気づけない。
  WebSocket には `webSocketClose` / `webSocketError` があるが、SSE には対応するものが無い

### 生きている状態を D1 に置く

**当初の想定はこれだった。** 半径での絞り込みは SQL の得意分野に見える。

- **3秒で消えてほしいデータに、耐久性の代金を払うことになる。** D1 への書き込みは
  1回ごとにネットワーク越しの永続化であり、1Hz × 台数ぶん往復が増える
- **位置情報が残る。** 走行が終わっても消すまで残り、**消し忘れが個人情報の滞留になる。**
  DO のメモリなら何もしなくても消える
- **`await` が入り、競合を考えることになる**（上の「永続化しない」）
- **空間インデックスが無いのは同じ。** SQLite に地理索引は無いので、結局 lat/lon の
  バウンディングボックスで絞って距離を出すことになる。**それは DO の中で `Map` を1周回すのと
  同じ計算**であり、20台なら 20回の距離計算で済む。SQL を挟む意味がない

**D1 を使わないと決めたのではない。走行の記録は D1 に置く**（上の「生きている状態と蓄積を分ける」）。

### 生きている状態を KV に置く

**書いてから読めるまで最大 60 秒かかりうる**（結果整合）。1Hz で更新する位置情報には使えない。
検討の余地なく落ちる。

### 1回の Write に複数台をまとめる

BLE の書き込み回数が天井なら、1通に2台以上詰めれば回数が減る。

**`../interfaces/v2v.md` が明示的に禁じており、その理由が正しい。**

> 台数が増えると必ず MTU を超え、**超えた瞬間に「周辺が1台も見えない」形で壊れる**

MTU の下限（163）は `../unverified.md` 13 でまだ確認できていない。
**未確認の前提の上に、壊れ方が全損の仕組みを積むことになる。**
そもそも天井はバイト数ではなくトランザクション回数なので、**まとめても効果自体が薄い。**

### 遠い相手だけ更新頻度を落とす

近い相手は 1Hz、遠い相手は 0.5Hz といった段階をつける案。

**3秒の失効より遅くできない**ため効果の幅が狭く、そのわりに実装と検証の手間が増える。
`CLAUDE.md`「早すぎる抽象化を避ける」に従い、**周期ごとの窓で足りなくなってから考える。**

## 影響

- **`../interfaces.md` の「モバイル ⇄ API」が決定済みになり、中身は
  `../interfaces/mobile-api.md` に分ける**（#7 のうち Worker の中継が閉じる）
- **`../interfaces/v2v.md` の「同時に扱う周辺車両の数に上限を置く（既定 8台）」が、
  周期ごとの窓（既定 12台）に置き換わる。** ペイロード・送る間隔・受信側の約束は変わらない
- **`../interfaces/ble-gatt.md` の `uplink` にある「1秒あたり数通」という見積もりを更新する。**
  周期ごとの窓の上限まで出ると毎秒 13通になる
- **`../unverified.md` 24 が合否の問いから測定に変わる。**
  「1Hz ×（自車1 + 周辺 8台）に追いつくか」ではなく、
  「`self` を先頭に固定した上で `peer` が毎秒何台通るか」。**失敗しようがなく、
  そのまま上限の調整値になる。** 新しい前提を2つ足す（30 / 31）
- **検知（#8 〜 #11）とシミュレータ（#12）への影響は無い。** 検知が受け取るのは
  「自車と周辺車両の状態」であり、それがどう届いたかを知らない
- **Durable Objects が技術スタックに加わる。** `0001-tech-stack.md` の選定時には無かった。
  Worker・D1 と同じ Cloudflare の上に載り、`wrangler.jsonc` の設定と
  `migrations` が増える。**新しいアカウントも課金も要らない**（SQLite バックエンドの
  Durable Objects は Workers Free プランで使える。今回はストレージも使わない）。
  **`migrations` は `new_sqlite_classes` で書くこと。** 例で多く見る `new_classes`
  （KV バックエンド）は**Free プランではデプロイに失敗する**

## 見直す条件

**次のどれかが起きたら、この決定を見直す。**

- **実測で `peer` の鮮度が検知に足りないと分かった**（`../unverified.md` 23 / 29）
  → WebSocket に移る。**ペイロードは変えずに済み、変わるのは
  `../interfaces/mobile-api.md` の「運び方」の節とスマホ側の接続処理だけ。**
- **同時に走る台数が増えて、単一 DO かリクエスト数が問題になった**
  → まず Workers Paid（$5/月）で足りるか見る。それでも足りなければ DO をセルで割る
  （境界の問題を持ち込むので、**そのときは隣接セルも見る形にすること**）
- **デモ会場の回線で 1Hz の POST が詰まると分かった**（`../unverified.md` 23）
  → 送る間隔を落とす。それでも駄目なら `0004` の「見直す条件」に従い
  ローカル層だけで見せる形に切り替える
- ~~**BLE が周期ごとの窓を埋められないと分かった**（`../unverified.md` 24）~~
  → **この条件はもう発火しない。**[`0006`](./0006-decision-layer-on-mobile.md) で位置が
  BLE を通らなくなり、窓という仕組みごと消えた（`../unverified.md` の 24 も欠番）。
  **消さずに残しているのは、当時この条件を見張っていたことが記録だから**である。
- **スマホが半径 300m ぶんの `peer` を毎秒処理しきれないと分かった**（`../unverified.md` 31）
  → **`0006` で BLE の天井と入れ替わりに現れた、新しい上限。**
  半径を狭めるか、スマホ側で近い順に絞る。**絞るのはスマホの中だけで、DO は広いまま返してよい。**
