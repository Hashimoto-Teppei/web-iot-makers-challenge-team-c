# ADR 0002: 開発ライフサイクル

- ステータス: 決定済み
- 日付: 2026-08-23

## 背景

ハッカソンのため開発速度を最優先する。一方で複数人が並行して開発するため、
仕様・設計・コードのレビューは省略できない。この2つを両立させる運用を決める。

**チームには開発が初めてのメンバーが多い。** これは運用の作り方を大きく変える前提であり、
「経験者だけなら暗黙で回ること」を明文化する必要がある。

あわせて、**実機での確認はスキップして進める**方針が決まった。
ラズパイの準備と検証に時間がかかり、実機を持たない開発者も多いためである。
理論上成立することを根拠に実装を進め、ある程度形になってから検証する。

## 決定

### レビューを2段階に分ける

**実装してからの設計やり直しが一番遅い。** 手戻りを避けるため、レビューを2回に分ける。

1. **仕様・設計レビュー** — `docs/` だけを変更する PR を出す。
   インターフェース（`docs/interfaces.md`）や技術判断（`docs/adr/`）をここで合意する。
   差分が小さいのでレビューが速く、認識のズレをコードを書く前に潰せる。
2. **コードレビュー** — 実装の PR。設計は合意済みなので、レビューは実装の正しさに集中できる。

小さな変更で 1 を省くのは構わない。ただし**コンポーネントの境界に触れる変更では省かない**。
境界は複数人の作業が依存する場所であり、ここでの手戻りは自分だけでは終わらない。

### 速度を落とさないための取り決め

レビューを厚くすると待ちが生まれる。それを打ち消す運用をセットで決める。

- **承認は1人でマージしてよい。** 4人規模で2人承認を必須にすると待ち時間が支配的になる。
- **CI を通してからレビューを依頼する。** 整形漏れや型エラーの指摘に人の時間を使わない。
- **PR は小さく、1つの関心事に絞る。** 大きな PR はレビューが雑になり、結局バグを通す。
- **方向性だけ先に見てほしいときは Draft PR を出す。** 完成を待たずに相談する方が速い。
- **レビューしてほしい点を PR に書く。** 「全部見て」は往復を増やす。
- **`main` は squash merge。** 履歴を追いやすく、revert も1コミットで済む。

### 実機確認をスキップする代わりに、未確認の前提を記録する

実機確認を待たずに進める。ただし**何を確かめていないかを見失うとデモ直前に詰む**ため、
実機未確認の前提は `docs/unverified.md` に積み、PR テンプレートのチェック項目で記録漏れを防ぐ。

レビューでは「実機で確認していない」ことを指摘しない（方針どおりのため）。
指摘するのは**記録していないこと**だけ。

この方針の裏返しとして、**検知ロジックは実機なしで pytest が回る形でなければならない**。
ハードウェアに依存したコードはレビューで差し戻す対象になる。

### タスク管理は GitHub Issues

Issue とコードとレビューが同じ場所にあり、PR から `Closes #12` で紐づけられる。
外部ツールを併用すると、初めての人が見る場所が増えて迷う。**見る場所を1つに保つ**ことを優先した。

- **30分以上かかる作業は Issue を立てる。** それ未満は直接 PR でよい。
- **着手するときに自分をアサインする。** 誰が何をしているか見えないと作業がぶつかる。
- **1 Issue = 1 PR = 半日〜1日**の粒度。大きい Issue は分割する。
- テンプレートを3種類用意する（タスク / 設計の相談 / 不具合）。
  「完了条件」を必須項目にしたのは、**何をもって終わりかが初めての人には自明でない**ため。

Projects のボードは使わない。Issue の open / closed と assignee で足りる規模であり、
ボードの更新を忘れて実態とずれる方が害が大きい。

### 開発が初めてのメンバーを前提にする

経験者だけのチームなら暗黙で回ることを、明文化して仕組みに落とす。

- **タスクの分解は経験者が行う。** 初めての人は「何をどこまでやればよいか」を自分で決められない。
  分解されていない Issue を割り当てると、着手できずに時間だけが過ぎる。
  手順まで書いた Issue には `good first issue` を付ける。
- **完了条件を Issue に必ず書く。** 自分で確認できる形（「`pnpm dev` で画面が出る」「CI が通る」）にする。
- **レビュー指摘に `[must]` / `[nits]` / `[ask]` を付ける。**
  分けないと、初めての人はすべてを必須と受け取って手が止まる。
  指摘には理由を添える。理由がなければ次に活かせない。
- **承認するのはその領域を理解している人。** 承認は1人でよいが、
  初めての人同士の承認だけでマージしない。判断できない承認は、レビューを通したという体裁だけを作る。
  初めての人がレビューに参加すること自体は歓迎する（学習になる）。
- **「30分詰まったら聞く」を推奨として明示する。** 初めての人は聞くこと自体を遠慮しがちで、
  遠慮の結果として溶ける時間の方がチームには高くつく。聞くのを推奨された行動にしておく。
- **環境構築で詰まらせない。** `mise install` と `pnpm install` の2コマンドに収め、
  手順を `CONTRIBUTING.md` に書く。ここで脱落させるのが最ももったいない。

これらは `CONTRIBUTING.md` に、実際に読む人の言葉で書いてある。
ADR にはなぜそうしたかだけを残す。

### CI で回すもの

`main` への push と全 PR で、lint / format / typecheck / test / build を回す。
ランタイムのバージョンは `mise.toml` から `jdx/mise-action` が読むため、CI に値を重複させない。

**自動デプロイはしない。** デプロイ担当が1人でデプロイ頻度も低いため、
public リポジトリに Cloudflare の認証情報を持たせる露出面を増やす理由がない。

### ブランチ保護は設定せず、運用で守る

GitHub のブランチ保護は設定しない。少人数で全員の作業が見えており、
設定によって強制するより運用で守る方がハッカソンの速度に合うと判断した。

守る内容は変わらない — `main` に直接 push しない、PR は CI 通過後にレビュー依頼、承認1件でマージ。
**仕組みで守られていない分、破っても誰も止めてくれない**ことをチームで共有しておく。

事故が起きたら（`main` への直接 push など）その時点で保護を設定すればよい。

### 履歴の読みやすさ

squash merge のため **PR タイトルがそのままコミットメッセージになる**。
`<種別>: <何をしたか>` の形（種別は `feat` / `fix` / `docs` / `chore` / `refactor` / `test`）で書く。
ブランチ名も `<種別>/<内容>` に揃える。

厳密な Conventional Commits の規約（スコープ、破壊的変更の記法、CI での検証）までは導入しない。
履歴が読めれば十分で、それ以上はハッカソンでは手間が上回る。

## 却下した選択肢

- **承認2人必須**: レビュー品質は上がるが、4人規模のハッカソンでは待ち時間の損失が上回る。
- **設計レビューを Issue で行う**: Issue でも合意は取れるが、`docs/` の PR にすれば
  合意内容がそのままリポジトリに残る。ドキュメントと実装の乖離を防ぐ仕組みを兼ねられる。
- **実機確認を必須にする**: 準備と検証のコストが期間に見合わない。方針として明示的に外した。
- **ブランチ保護の設定**: 少人数で目が届くため、設定の手間に見合わないと判断した。事故が起きたら導入する。
- **commitlint などによる規約の機械検証**: 履歴が読める程度で十分で、CI を増やす価値が薄い。
- **GitHub Projects のボード**: 状態を手で更新する運用は忘れられ、実態とずれる。Issue の open / closed で足りる規模。
- **外部のタスク管理ツール（Notion 等）との併用**: 初めての人が見る場所を増やさない方を優先した。
