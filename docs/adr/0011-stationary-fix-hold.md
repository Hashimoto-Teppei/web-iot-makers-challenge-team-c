# ADR 0011: 中継の 1Hz を測位の到着に依存させず、更新が来なければ直近の測位を使う

- ステータス: 決定済み（**実装は #167。実機での確認は未了**——`../unverified.md` 53 / 95 / 101）
- 日付: 2026-09-14
- 関連: `0005-realtime-transport.md`（中継を 1Hz のポーリングにした。**その 1Hz の出所をここで変更する**）/
  `0010-ios-primary-target.md`（主ターゲットが iOS になった）/
  `../interfaces/v2v.md`（「送る間隔」の正本）/ `../interfaces/mobile-api.md`（「運び方」の正本）

## 背景

**信号待ちで止まっている自転車が、周りの自転車のアプリから消える**（#167）。

### 実測（2026-09-14 / #166）

iPhone 13（iOS 26.6.2、Release ビルド）を**机の上に置いて画面を消し、60 分**走行させた。

| | |
| --- | --- |
| `POST /api/v2v/exchange` | 681 通（すべて成功） |
| 間隔の平均 / 最長 | **5.3 秒 / 30.0 秒** |
| BLE の心拍の途切れ | **0 回** |

**近傍の失効は 3 秒。**止まっている端末は「見えている時間」より「消えている時間」の方が長い。

### なぜそうなるか

**中継の POST は測位の更新だけが駆動している**（`apps/mobile/src/ride/loop.ts` の `onFix()`）。
そして **iOS は動いていない端末に測位を出さない。**
`distanceInterval: 0` と `pausesUpdatesAutomatically: false` を渡しても間引かれた
（**`timeInterval` は iOS では読まれてすらいない**——`EXLocationTaskConsumer.m` がソース）。

**心拍（BLE）は途切れていない。**心拍は1秒のタイマーと測位の両方から叩かれるため
（`loop.ts` の `beat()`）、測位が 5 秒に 1 回でも 1Hz を保てる。
**これは同時に、iOS の背景で `setInterval` が生きている証拠でもある。**

### 壊れているのは1箇所ではない

| | 何が起きるか | どこで決まっているか |
| --- | --- | --- |
| 1 | **他人から自分が消える** | `apps/web/src/worker/v2v/config.ts` の `expiryMs: 3_000` |
| 2 | **自分から他人が消える。** 自車の測位が古くなると近傍を全部捨て、**4つの検知が1つも動かない** | `NeighborsConfig.selfStaleMs: 3_000` |
| 3 | **デバイスが `nofix` を出し続ける** | `beat()` の `st` |

**2 が一番重い。**赤信号で止まっている自分は、急接近（#9）が一番危ない側でもある。

3 秒という数字は上の3つを含めて4箇所（検知の `maxFixAgeMs` も 3 秒）にあり、
**どれも「測位は毎秒来る」を前提に置かれている。**壊れているのは数字ではなく前提の方で、
数字を緩めると「居なくなった相手」と「止まっている相手」の区別が4箇所すべてで鈍る。

## 決定

### 1. 中継の 1Hz を、測位の到着に依存させない

`0005` は中継を 1Hz のポーリングにしたが、**その 1Hz を「測位が毎秒来ること」で実現していた。**
iOS ではこの前提が成り立たない。**心拍が2つの供給源を持つのと同じ形にする。**

### 2. 更新が来なければ、直近の測位を「いまの測位」として使う

**1秒のタイマーを `location.ts` に持ち、OS から更新が来ていなければ
直近の測位をそのまま流す。`t` だけを「いま」にする。**

**なぜ更新が来ないのかを当てにいかない。**「止まっているから」なのか「測位が死んだから」なのかは、
スマホの側からは見分けられない。**見分けようとせず、上限時間だけを置く**（決定 3）。
**アプリが生きて POST が通っていること自体が、直近の位置を使ってよい根拠**である。

- **`t` を進めるのが肝心。**（**進め方は実装時に精密化した**——「いま」は送る側の時計では
  なく**測位と同じ時間軸**で作る。測位は測った時刻より遅れて届くため、時計をそのまま入れると
  遅れのぶんだけ未来に出て、**飛んでいる最中の本物を追い越して捨てさせる。**
  `../interfaces/v2v.md`）
  測位した時刻のまま送り直すと、受信側は
  「同じか古い `t`」として捨て（`../interfaces/v2v.md`「受信側（モバイル）の約束」4）、
  **残った点は `maxFixAgeMs`（3 秒）を過ぎていて4つの検知すべてが何も言わない。**
  近傍から消えなくなるだけの、**「消えないが検知もされない」**状態になる。
  送り主の側でも同じことが起き（`acceptSelf` が `t <= last.t` を捨てる）、**故障 2 と 3 が残る。**
- **`spd` は 0、`crs` は `null` にする。** 前の値を持ち越すと、
  **止まっている自転車が「その向きに走っている」ことになる。**
  走っている最中に測位が死んだ場合は「最後に見えた場所に止まっている自転車」として配られるが、
  **それは危険側に倒れた読み方**であり、黙るよりよい。

### 3. 置くつまみは「上限時間」1つだけ

**保持し続ける時間に上限を置く**（設定。既定は仮に 120 秒）。
過ぎたら送るのをやめ、**失効に「分からない」を表明させる。**
赤信号より長く、鞄の中で測位が死んだまま1回の走行を送り切るより短い長さにする。

**速度で条件を分けない。**「止まっていたときだけ保持する」という案は検討して落とした
（→「却下した案」）。

### 4. 保持は測位の層（`location.ts`）に置く

**下流を1行も変えずに済むから。**上の3つの故障は走行ループ・近傍・検知・サーバーの
4箇所に散らばっているが、**測位の層で 1Hz を作り直せば、下流はもとの前提のまま正しく動く。**

- **`loop.ts` の `beat()` にぶら下げない。** 心拍に通信をぶら下げると、
  詰まるたびに心拍が遅れてデバイスが `down` を出す（`../interfaces/mobile-api.md`）。
- **Android に分岐を書かない。** Android は画面を消すとタイマーが止まるので**保持は動かない。**
  動かなくてよい——Android には 1Hz の測位が届いている（`../unverified.md` 22）。
  **「iOS のときだけ」と書かなくても、iOS でだけ動く。**
- **保持そのものは純粋な関数として `location.ts` の外に置き、Vitest で回す**
  （`0002-development-lifecycle.md`。`location.ts` にはテストを置かない）。

### 5. 保持したことを人に見せる

**保持した回数を `RideStatus` に出し、走行後の画面で見えるようにする**（走行中には出さない）。

**保持は故障を隠す仕組みでもある。**測位が本当に死んでいても、上限に達するまでは
画面もデバイスも正常に見える。`CLAUDE.md` が例外に挙げた「静かに黙る故障」の側である。

### 6. サーバーと失効の値は動かさない

**`expiryMs`（3 秒）も、モバイル側の 3 + 3 も変えない。**保持が入れば POST は 1Hz に戻る。
**`apps/web` はこの変更で1行も変わらない。**

### 7. ついでに `activityType` を渡す

`LocationActivityType.Fitness`。いまは渡しておらず iOS の既定は `CLActivityTypeOther` で、
**これだけで 1Hz が出る可能性がわずかにある**（`pausesUpdatesAutomatically: false` は既に
渡しているので見込みは薄い）。**1行なので入れるが、これの結果を待たない。**
効いていたかは次に実機を出したときに分かる（`../unverified.md` 102）。

## 却下した案

- **失効（`expiryMs`）を伸ばすだけ。** 直るのは故障 1 だけ。最長 30 秒に耐えるには
  30 秒以上が要り、6 m/s なら**約 180m ぶんの幻**が近傍に残る。
- **`t` を測位した時刻のまま送り直す。** 決定 2 のとおり検知が動かない。
  **近傍の台数だけが正しく見えるので、直ったと誤解しやすい。**
- **「止まっていたときだけ保持する」と条件を付ける。** 動いている最中に測位が死んだときに
  黙る、という点では正しい。**落としたのは、見分けようとしただけつまみと分岐が増えるから。**
  上限時間があれば嘘の長さは同じように抑えられ、**ハッカソンで要る精度はそこまでである。**
- **1秒ごとに一発測位（`getCurrentPositionAsync`）を叩く。** 本物の測位が取れるなら
  これが一番正直だが、expo-location の実装は**呼び出しのたびに新しい `CLLocationManager` を作り、
  `allowsBackgroundLocationUpdates = false` を設定してから `requestLocation()` を呼ぶ**
  （`LocationRequester.swift` / `BaseLocationProvider.swift`）。
  **背景で毎秒これを作るのは常駐している購読とは別経路**で、返るのが本当に新しい測位か
  （キャッシュされた直近の位置か）も**ソースからは決まらない。**
  キャッシュが返るなら結果は「`t` そのままの送り直し」と同じである。

## 影響

- **`apps/mobile` のみが変わる。** `apps/web` と `apps/device` は変わらない。
- **`../interfaces/v2v.md`「送っていない間を埋めない」を書き換える。**
  あの規則は「アプリが生きていれば測位は毎秒来る」を前提にしていた。
- **シミュレータ（`apps/mobile/src/sim/`）は変えなくてよい。** 保持は測位の層に入る。

## 見直す条件

- **決定 7 の `activityType` だけで 1Hz が出た場合。** 保持ごと落とす。
- **屋外で実測したら、止まっていても 1Hz が出た場合。** 実測は**屋内の机の上**で取っており、
  GNSS ではなく Wi-Fi 測位に落ちていた可能性がある（`../unverified.md` 101）。
- **Android のタイマーが背景でも動くようにした場合。** 保持が Android でも動き始める。
  意味は同じだが、**「iOS でだけ動く」という前提が消える。**
